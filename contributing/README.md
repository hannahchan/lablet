## Architecture rules

Explicit architecture. Inside `lablet/`, directory `foo/bar/` is package `lablet-bar`, except `apps/lablet` (`lablet`), `apps/lablet-cli` (`lablet-cli`, whose binary is `lablet`), `tests/conformance` (`lablet-conformance`), and `tests/mcp-server` (`lablet-test-mcp-server`).

| Ring                  | Path                                 | May depend on                                                                 | Forbidden crates                                                                                            |
| --------------------- | ------------------------------------ | ----------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| Domain                | `crates/domain/*`                    | domain                                                                        | tokio, reqwest, tracing, opentelemetry, rmcp, tonic, axum, hyper                                            |
| Application           | `crates/application/*`               | domain                                                                        | tokio, reqwest, rmcp, tonic, axum, hyper, and the opentelemetry family except `opentelemetry` itself        |
| Secondary adapters    | `crates/adapters/secondary/*`        | application, domain, adapter shared kernel; never a sibling adapter           | the opentelemetry family except `opentelemetry` itself                                                      |
| Adapter shared kernel | `crates/adapters/secondary/shared/*` | application, domain, other adapter shared kernels; never an adapter           | the opentelemetry family except `opentelemetry` itself; may be used by sibling adapters, implements no port |
| Root kernel           | `apps/shared/*`                      | domain, application, secondary adapters, other root kernels; never a root     | the opentelemetry family except `opentelemetry` itself; may be used by both roots                           |
| Library root          | `apps/lablet`                        | domain, application, secondary adapters, root kernels; never the CLI root     | the opentelemetry family except `opentelemetry` itself                                                      |
| CLI root              | `apps/lablet-cli`                    | domain, application, secondary adapters, root kernels; never the library root | none                                                                                                        |
| Test support          | `tests/*`                            | anything, dev-only                                                            | none                                                                                                        |

`cargo xtask lint-layers` enforces this on `[dependencies]` and `[build-dependencies]` (dev-dependencies are exempt) and runs at pre-commit: a workspace crate is placed by the path of its `[workspace.dependencies]` entry, an external crate is matched by name. The two roots are placed by their whole paths, so a third crate under `apps/` outside `apps/shared/` is in no ring, which is a finding, until a rule places it. `cargo xtask lint-manifests` refuses a binary target under `apps/shared/`, so a kernel has no `main()`. A forbidden name covers its family (`opentelemetry` also forbids `opentelemetry_sdk`), and the exception is the API crate itself: `opentelemetry` passes in every ring that forbids the family, and no other member of the family does. So the SDK lives in the CLI root alone. No crate outside `tests/` may depend on a `tests/` crate. `serde` and `serde_json` are allowed everywhere; the domain and application hold in-memory models, and the published document shapes live in `lablet-documents`. The lint reads direct dependencies only, so a third-party crate that would bring the SDK into the library root through its own dependencies is a review matter.

- Ports are object-safe `async_trait` traits, `Send + Sync`, defined in the application crate that consumes them, injected as `Arc<dyn Trait>` by constructor. No DI framework, no generics over adapters.
- Adapters implement ports and map their own errors into the port's error at the `impl` boundary. Adapter types never appear in application or domain signatures.
- Each root selects adapters from config through the root kernels and injects them itself. Adding an adapter is a new crate plus a match arm in the kernel that constructs its capability.
- No primary adapters: the binary and library entry points call the use case directly.
- Domain crates contain types and pure functions only: no runtime, no I/O, no clock, no port, no threads. The test is that a plain `#[test]` drives every domain function deterministically. An async function passes when its tests poll it to completion with `std::task::Waker::noop()` and futures the test controls, as `Pending::answer`'s do. Anything that needs a runtime to test is application or outward.

### Composition roots and their kernels

Lablet has two composition roots, and neither depends on the other. The library root, `apps/lablet`, is the API a host builds a `Lablet` through. It runs on the OpenTelemetry its host provides, the tracer provider, the logger provider and the propagator the host must hand in as one `lablet::Otel`, reads no global tracer provider or propagator of OpenTelemetry's, and configures no SDK. The CLI root, `apps/lablet-cli`, is the `lablet` command: it reads the config and the process's environment, configures the SDK from them, and extracts the inbound context. It hands its providers and its propagators in as a host would. Both run the same use case in `lablet-run`, so what a run does doesn't depend on which root started it.

A root kernel is a crate under `apps/shared/<capability>/`. Both roots may depend on a kernel, which is safe to share because it carries none of a root's role: it wires nothing, holds none of a run's behaviour, and has no `main()`. Selecting and opening one capability's adapter from config is capability-scoped construction, not object-graph composition: a kernel hands back the adapter, or the checked values, and each root still connects them, calling each capability's kernel and injecting what it gets into `RunService` and the `Runner` itself. A kernel may use sibling kernels, the application, the adapters and the domain, and never a root. A kernel that connects two capabilities' adapters, or holds a step of a run, is a review finding, since the lint can't see either.

Extract a kernel only when both roots need it, and give each capability its own crate rather than a `shared/common` one. What only one root needs stays in that root. The SDK, its export module and the seam that reads its environment are the CLI root's, and the `Otel` a host hands in is the library root's: an adapter is built with what its root hands it, and never reads a global itself. Every kernel is held to the library root's rule on the opentelemetry family, since the library root depends on them.

## Code conventions

- `thiserror` for errors. No `anyhow` (banned in `lablet/deny.toml`, so `cargo xtask deny` refuses it). In the `lablet/` crates, one error enum per port or boundary, owned by the layer that defines it, and variants carry `String`, not foreign error types; `xtask`'s errors keep their cause, because `xtask` has no ports and its errors are for a person to read.
- Workspace lints. Enforced by `cargo xtask clippy` with warnings denied (pre-commit): `unsafe_code = "forbid"`, `missing_docs`, `rust_2018_idioms`, clippy `all` and `pedantic`, and `unwrap_used`, `expect_used`, `assertions_on_result_states`, `todo`, `unimplemented`, `dbg_macro`, `print_stdout`, `print_stderr`, `allow_attributes`, `allow_attributes_without_reason`. Enforced by `cargo xtask doc` with warnings denied (pre-push and CI), because clippy never runs rustdoc: rustdoc `broken_intra_doc_links`, `private_intra_doc_links`, `redundant_explicit_links` at deny. Nursery isn't enabled and pedantic has no relaxations, so every public function returning `Result` needs an `# Errors` section and every one that can panic a `# Panics` section. Suppress a lint with `#[expect(..., reason = "...")]`; `#[allow]` is itself a lint failure.
- OpenTelemetry's global providers and propagator are never set or read by lablet. The root `clippy.toml` disallows `opentelemetry::global`'s tracer, meter and propagator functions, because a process may hold several `Lablet`s, each given the OpenTelemetry its host hands in. A library host hands in its tracer provider, its logger provider and its propagator as one `lablet::Otel`, and a host on the global ones reads them itself and hands them in. The one exception is test code, which may set or read a global, each call under its own `#[expect(clippy::disallowed_methods, reason = "...")]`: the library root's test binary `globals` sets the global tracer provider and propagator to show that lablet reads neither, and reads them to show that lablet sets neither, and runs its steps in one test, so no other test sees them, and the CLI root's canary `canary_the_global_propagator_is_a_no_op_after_a_lablet_is_built` reads the global propagator to show that nothing set it. The CLI root hands its SDK's providers and propagators in and sets no global.
- Tests may `unwrap`: the root `clippy.toml` allows it inside `#[test]` functions and `#[cfg(test)]` modules, for both the workspace and `xtask`. In an integration target, declare every module in `tests/it/main.rs` as `#[cfg(test)] mod name;` so shared helpers are covered too.
- `main.rs` writes to standard output in one place, and a write that fails is said on standard error rather than panicking. This is a review convention, not a gate.
- `clap` derive API in the binary.
- Every dependency is declared once, in `[workspace.dependencies]`, with a comment on the line directly above it saying why it's there. The gate checks that the line above is a comment: a comment block counts, a trailing comment or a comment above a blank line doesn't. It can't tell a group header from a reason, so a header is followed by a blank line and never stands in for an entry's own comment. A third-party entry is an exact `=x.y.z` pin from crates.io; an internal entry is `{ path, version }` with the path exactly as `[workspace] members` lists it. A member's manifest only inherits: `name.workspace = true`, or `{ workspace = true }` with `features`, `optional`, or `default-features` beside it, in every dependency table, and no version, path, git, registry, or package key of its own. So it needs no comments; the reason lives in the workspace table. `xtask/Cargo.toml` follows the same pin and comment rules. `cargo xtask lint-manifests` checks all of this. Grouping under `# Domain`, `# Application`, `# Adapters`, `# External` headers, the blank line after a header, and what a comment says are review conventions, not gates.
- The lints model only the Cargo features lablet uses. Member globs, `[workspace] exclude` or `default-members`, a `[package]` in the workspace root, `[patch]` or `[replace]`, and `patch`, `paths`, or `source` in a `.cargo/config.toml` fail the gates as unsupported. Using one means extending `xtask` deliberately, not working around the message.
- A comment says why something non-obvious is the way it's written, or states a contract a caller relies on. Nothing else. Don't narrate how the code came to be, don't record facts that drift (versions, dates, counts, build phases), and don't restate the code or these docs. Doc comments stay on public items because `missing_docs` is enforced; one sentence where one will do. This is a review convention.
- Test names are sentences: `a_tool_error_does_not_consume_the_retry_budget`. This is a review convention, not a gate.
- In the crates with a coverage floor (`lablet-model`, `lablet-policy`, `lablet-run`), unit tests live in a sibling file declared as `#[cfg(test)] mod tests;`: `src/foo.rs` and `src/foo/tests.rs`, or `src/tests.rs`, with helper modules below that file. Never an inline `mod tests { ... }`, and no other attribute that mentions `test` in a production file: no bare `#[test]` or `#[tokio::test]` function, no `#[cfg(test)]` on another item or on a `#[path]` module, no `#[cfg(all(test, ...))]`, `#[cfg_attr(test, ...)]`, or `#[cfg(not(test))]`. Coverage tells test code from production code by file name (`tests.rs` files and `tests/` directories are left out), so test code anywhere else would count as covered production lines; `cargo xtask coverage`, `cargo xtask mutants`, and an `xtask` test (pre-push) fail on such an attribute. The check reads lines that start with `#[` or `#![`; an attribute rustfmt has wrapped over several lines is left to review. Other crates may keep unit tests inline.
- One integration test target per crate: `tests/it/main.rs` declaring modules. This is a review convention, not a gate.
- Test doubles are hand-written fakes in the consuming crate. No mocking framework (the known ones are banned in `lablet/deny.toml`).

## Telemetry is contract-first

Every span, event, and attribute is declared in the Weaver registry under `lablet/telemetry/registry/` before it's emitted. The registry is in folders by the crate that emits each signal: `shared/` holds lablet's own attributes (`attributes.yaml`), the imported resource entities (`resource.yaml`) and the join group (`groups.yaml`), and generates nothing of its own; `application/run/` holds `lablet-run`'s, every span and event of a run, and an adapter gets a folder when it first emits a signal of its own. Each signal file names the semantic-convention attributes it refers to. Three rules hold, the first by review and the others by `weaver check`:

- A core or GenAI semantic-convention attribute is used wherever one exists. A `lablet.*` attribute is the last resort.
- Every `lablet.*` attribute is `development` and has a `note` that opens with `Justification:` and says why no convention covers it.
- Every attribute on a span or event states its requirement level, with the condition when it's conditional. Captured content is `opt_in`.

Two things are generated from the registry and checked in. A `src/telemetry/generated/` module in each crate that emits a signal, `lablet-run` alone today, rendered by the templates in `lablet/telemetry/templates/registry/rust-crate/` from that crate's registry folder: a typed struct for each of its spans and events, a closed enum for each value set they choose from, the `Join` struct of the six join keys (in `lablet-run`, which another crate's module would use from there), the registry's schema URL, and a `key` module of attribute name constants and, for each signal, the lists of its required keys, of all its keys and of its template keys, which tests read. And the reference under `lablet/docs/telemetry/`, from the vendored upstream templates. Everything in those directories is generated: don't edit it. Don't write an attribute name as a string literal in hand-written code either, in an adapter or anywhere else: `lablet-run` holds that with a test, and elsewhere it's a review convention. To add an attribute, edit the registry, run `cargo xtask weaver generate`, and fill the field the struct gains. Annotations under `lablet:` on a signal or on an attribute's reference say what the registry's syntax can't, a value that's fixed on that signal, the values a signal uses of an open attribute, the join keys, a span event and a record's severity; the table in [instrumentation.md](instrumentation.md) lists them.

A span is started and ended, and a log record stamped, at the times the loop measured on its injected `Clock`, never at a time the SDK reads from the system clock, and to the nanosecond: the run's start plus the `Duration` the loop measured, never its whole milliseconds. `lablet-run`'s scenario tests hold this for the loop's spans and records (`a_span_event_and_record_are_timed_to_the_nanosecond_and_their_ms_values_are_cut`, `the_span_of_a_failed_attempt_says_how_it_failed_and_what_the_loop_did_next`, `a_run_cancelled_during_a_provider_attempt_drops_it_and_makes_no_other` and `each_record_of_content_is_in_the_context_of_the_span_the_content_belongs_to`), and `the_run_s_own_span_and_its_wide_event_are_timed_to_the_nanosecond_from_its_start`, a test of `lablet-run`'s runner and again of the library, holds it for the root span and the wide event the runner writes. The tracer and lablet's logger are injected into the loop and the runner, never taken from or installed in OpenTelemetry's global providers there (`opentelemetry::global::tracer`, `set_tracer_provider` and the like; the `BoxedTracer` type is fine), and so is the propagator each adapter that injects a context is built with. Each root resolves them once. The CLI root hands in the tracer and the logger of the SDK its export module, `lablet_cli`'s `export`, builds, and the composite of the propagators `OTEL_PROPAGATORS` names. The library root takes all three from the `lablet::Otel` its host must hand in: the tracer and the logger of lablet's scope, taken from the host's tracer provider and logger provider when the `Otel` is made, and the host's propagator (the code conventions above). The `hosts` tests `two_lablets_given_their_own_providers_each_reach_only_their_own`, `two_lablets_built_from_one_otel_both_reach_its_providers` and `a_run_under_a_span_the_host_has_open_is_its_child_and_reaches_the_host_s_tracer` hold the effect; the `globals` test `lablet_sets_no_global_and_a_global_set_before_the_build_receives_nothing` holds that the library sets no global tracer provider or propagator, and that a global one set before the build receives nothing, with the host's pieces handed in and with the API's no-ops; the root `clippy.toml` refuses a call to the global tracer, meter and propagator functions but those in test code, each under its own `#[expect]`; and the canary `canary_the_global_propagator_is_a_no_op_after_a_lablet_is_built` holds that composing the command line's run sets no global propagator. `lablet-run` doesn't depend on `tracing`, though the application ring allows it, since the loop writes telemetry through the OpenTelemetry API and has no diagnostics of its own: a review convention, not a gate.

The lablet policies hold four rules on attributes: a `lablet.*` attribute has a note that begins `Justification:`, it's `development` until 1.0, nothing is defined here outside `lablet.*`, and every attribute on a span or event states `required`, `conditionally_required`, or `opt_in`. An omitted level resolves to `recommended` and would make a required field an `Option`, so lablet doesn't use that level. They hold the annotations too: what's under `lablet` is a map, on a signal or on a reference and never on an attribute's definition, since resolution copies a definition's onto every reference to it; a `value` is on a `required` reference, since it's emitted on every signal of its kind, and is one the attribute's type allows, a text for a string attribute or an open enum and a member for a closed one; `values` are texts a string attribute or an enum attribute allows, each a member of a closed enum and none listed twice; the join keys are one set, on every span and every record, each marked `join: true` and nothing else marked, with neither a `value` nor `values`, since a join key is filled from the run, and on no span event, which sits on a span that carries them already; `emit` is `span_event` or absent; `severity` is one of the API's levels and isn't on a span event, which has none; an annotation with any other name is refused; and no span or event is declared in `shared/`, which generates nothing, so it would be in no crate's module. The test `each_mistake_in_the_registry_is_refused_by_its_rule_and_the_registry_without_one_passes` in `xtask/src/gates/policies.rs` runs the gate's own `weaver check` against a copy of the registry with one mistake for each rule, and `every_rule_of_the_annotation_policy_has_a_case` holds that no rule goes without one. A class a signal lists of an open attribute is any text to the policy; the spellings tests beside the generated module hold that each is spelt as the loop spells it. Constants carry the conventions' own briefs as doc comments. When one trips clippy's `doc_markdown`, add the identifier to `doc-valid-idents` in `clippy.toml`.

```bash
cargo xtask weaver check               # the registry against the lablet, naming, and stability policies
cargo xtask weaver generate            # write each crate's module and the reference again
cargo xtask weaver generate --check    # fail when they differ from what the registry renders to
cargo xtask weaver live-check          # what fake-provider runs emit, checked by weaver over OTLP
```

Both forms of `generate` render into `lablet/target/` first, so a failed run leaves the tree alone, and `--check`, which pre-commit runs, never writes outside it. Both also refuse when the registry's folders and the modules part: a folder outside `shared/` that holds registry files and that no module is rendered from, a module whose folder holds none, or a `src/telemetry/generated/` directory that no module writes. The list of modules is `OUTPUTS` in `xtask/src/generated.rs`.

What a run emits is held by the golden comparison, `cargo test -p lablet-cli --test it golden`: three runs through the command line's composition on tokio's paused clock, the `init --provider fake` starter, `lablet/examples/two-turns` and the run under `lablet/tests/fixtures/golden/cancelled/`, each read from its config file with its relative paths rebased, so the runs can't drift from what a user runs. Each export is normalised, with trace and span ids named by their order of first appearance, times as offsets in nanoseconds from the root span's start, and every signal's attributes sorted by key, since their order isn't part of the contract, and the SDK's own `telemetry.sdk.version` as the word `normalised`, and compared with `lablet/tests/fixtures/golden/<run>/expected.json`. Lablet's version is in the fixtures as it is. When what lablet emits is meant to change, regenerate them with `LABLET_UPDATE_GOLDEN=1 cargo test -p lablet-cli --test it golden`, read the diff, and write the `Unreleased` entry the changelog gate asks for, since it watches the directory. CI never sets the variable, and the test refuses it there. The test also refuses an `OTEL_*` variable in its environment, and the context variables, `TRACEPARENT`, `TRACESTATE`, `BAGGAGE`, `B3` and the `X_B3_*` ones, which `cargo xtask test` strips, since lablet and the crates read them into the resource, the exporter and every run's parent. A fourth run is the two-turns run again, in a child process of the test binary, under an environment that sets every variable of the specification's SDK and OTLP exporter pages but `OTEL_SDK_DISABLED` and `OTEL_TRACES_SAMPLER`, whose honoured values would leave nothing to compare, and the context variables, each to a value that would change the export if it were read, held to `lablet/tests/fixtures/golden/hostile/expected.json`. It fails when an OpenTelemetry crate starts reading a variable lablet decides, or one it doesn't read at all, which the three runs, with none set, can't show. The canaries in `lablet/apps/lablet-cli/src/export/tests/canaries/` are its companions: each pins a behaviour of the 0.33 crates that some code of lablet's is there for, passes on 0.33, and fails on the release that changes it, and the commit that bumps the crates either deletes that code for each canary that fails or records in `product/decisions.md` why it stays.

`weaver live-check` checks the wire rather than the registry: it starts `weaver registry live-check` on two free ports, without `--v2` since that index leaves out every attribute a dependency defines, runs the `lablet init --provider fake` starter and `lablet/examples/two-turns` against it with content captured, stops it through its admin endpoint, and reads the report it keeps at `lablet/target/weaver-live-check/live_check.json`. A violation fails the step with every finding listed, and so does a report that saw less than the runs emit, since an idle listener reports nothing wrong; every `OTEL_*` variable, and `TRACEPARENT`, `TRACESTATE`, `BAGGAGE`, `B3` and the `X_B3_*` variables, is stripped from the runs so the environment can't redirect or silence them, or give them a parent, and each run states its endpoint and `telemetry.otlp.protocol=grpc`, which weaver listens for. The checker validates attributes and matches log records to events by name; it doesn't match spans to definitions, which `lablet-run`'s tests hold over the SDK's in-memory exporters and the CLI root's over the exported file. It builds lablet and takes some seconds of weaver, so it's a CI job of its own on Linux rather than a gate step; run it by hand after changing what lablet emits.

`weaver check` reads only the working tree. Weaver clones a git dependency on every run and keeps no cache, so everything it reads from upstream is vendored under `lablet/telemetry/deps/`: the `model/` trees of the core and GenAI semantic conventions, and the naming policies, stability policies, and Markdown templates from `opentelemetry-weaver-packages`. `lablet/telemetry/vendor.sh` holds the pinned commits and is the only thing that writes that directory. Each tree has a `SOURCES` file naming its repository, commit, and copied paths. The files are byte-identical to their source with one exception, which `SOURCES` records: the GenAI manifest names the core conventions by git URL, and the script points that line at the vendored copy, because Weaver would otherwise clone it on every run.

```bash
cargo xtask weaver vendor            # after changing a pin in lablet/telemetry/vendor.sh
cargo xtask weaver vendor --check    # fetch the pins again and fail on any difference
```

Both need the network, so neither is part of a gate. Changing a pin is its own commit.

Weaver's diagnostics go through lablet's templates in `lablet/telemetry/templates/diagnostics/`: `text` on a terminal and `github`, which writes workflow commands, when `CI=true`. They drop the warning Weaver prints for every file in the v2 format and the warnings about vendored files, and nothing more severe than a warning.

## Gates

Every rule on this page is enforced by a gate. If it's not enforced, it's a suggestion, not a rule.

```bash
cargo xtask pre-commit    # fmt (rustfmt and dprint), clippy, lint-layers, lint-manifests, weaver check, weaver generate --check, lint-shell, lint-prose
```

```bash
cargo xtask pre-push      # pre-commit plus cargo deny, changelog, rustdoc without warnings, tests, and the mutants of what changed
```

The test step strips every `OTEL_*` variable, and the context variables `TRACEPARENT`, `TRACESTATE`, `BAGGAGE`, `B3` and every `X_B3_*` one, from the environment it runs `cargo test` in, and so do `coverage` and `mutants` (`KEPT_FROM_TESTS` in `xtask/src/process.rs`): any of them would redirect or silence the network exporter, which is on by default, add to the resource, or give every run a parent, in every test that composes the command line's run in its own process, which can't scrub its own environment, and the capture variable would capture a library run's content. So the tests' configs state `telemetry.otlp.enabled: false`, or the endpoint of a receiver the test starts, wherever they don't test the default, and a hand-run `cargo test` doesn't export to `localhost:4318`; no gate checks that a config does, and a test that forgets is slow and noisy rather than wrong. A test of the binary removes the same variables from the process it starts, and gives one back only when it tests it.

Run `cargo xtask help` for every task, grouped in the order a developer works: development, quality checks in the order the gates run them, quality gates, analysis, project. Off a terminal a gate first says it's running, and a green one then prints one closing line; the step table appears only when something failed, lists the failed steps first, and names the task that runs each alone.

CI runs on every pushed branch as three jobs side by side: `cargo xtask ci` (the pre-push list), `cargo xtask coverage` (floors: every line and every region on `lablet-model`, `lablet-policy`, and `lablet-run`), which takes under a minute, and `cargo xtask weaver live-check` against the vendored registry. When every path the branch changed since its merge-base with `origin/main`, or on `main` every path the push moved `main` across, is documentation, `ci` runs only `fmt (dprint)`, `lint-prose` (after syncing its styles on a fresh clone) and `changelog`, which start no compiler, and the other two skip; `cargo xtask scope` prints the decision, and the gate's `scope` step says it with a warning. The whole branch is judged, never the last push, so a docs push on top of a code push still gets a full run. Documentation is Markdown under `product/`, `contributing/` and `lablet/docs/`, and `README.md`, `CLAUDE.md`, `CHANGELOG.md`, `lablet/README.md` and `lablet/examples/README.md`; anything else is a build input, the rendered telemetry reference under `lablet/docs/telemetry/` and the Markdown a run reads among them, and so is a removed document, which a test may read by name. An xtask test holds that no Rust source reads a document at compile time. A push to `main` whose commit already has a green run, which is its branch's run when it lands by fast-forward, runs only the changelog gate, over what the push moved `main` across, unless it changes what the build cache is keyed on, the manifests, lock files, cargo config, toolchain or `ci.yml`, since only `main` saves the cache. The `Floors` workflow runs the two slower floors on the same crates every day and on demand: `cargo xtask mutants` (floor: every viable mutant caught, except the ones named as equivalent) and `cargo xtask coverage --branch` (floor: every branch). A scheduled run skips the mutants when nothing that feeds the three crates changed since the workflow's last green run on `main`. A failure there isn't attached to a push, so the latest `Floors` run is read before work starts and before a phase closes, and it should be from the last day or two: in a public repository GitHub disables a scheduled workflow after 60 days without activity, runs on demand included, and no later push turns it back on. When the latest run is older, the workflow is turned back on with `gh workflow enable floors.yml` and, if `main` has moved since, run with `gh workflow run floors.yml`. This is a review convention, not a gate. The three are held to 100% because a branch no test can take is the signal these floors exist to raise: the type allows a state the caller has already ruled out, and the fix is to make the type rule it out rather than to guard it. A check that a second caller can genuinely fail stays, and that caller's tests cover it. The mutation floor is exact rather than a percentage, because an equivalent mutant can't be killed by any test and whether a mutant is equivalent isn't decidable: each survivor is judged once by a person and named in `EQUIVALENT_MUTANTS` in `xtask/src/floors.rs` with the reason; no floor crate carries one today. An entry names the package, the file, and what the mutant does, never its line, and it excuses one mutant the tests ran against and missed, so a timeout is never excused. The named mutants are still tested, so a full run fails on an entry that no longer matches a missed mutant. The floor covers what cargo-mutants mutates, and it mutates neither a function named `new` nor code a `macro_rules!` generates: a rule a checked constructor holds belongs in a function of another name, as `Rates::checked` and the retry policy's `validate` are, or is held by unit tests alone. A region is a span of source with its own counter, so a match arm, an `else` a line never spells out, and the far side of a `&&` are each counted apart; a line is covered when any region touching it ran, which makes regions the stricter of the two and 100% regions imply 100% lines. Branch coverage is finer again in the other direction, since it alone sees a side of a `&&` or `||` that always went the same way while the whole condition went both ways, but the compiler measures it only on a nightly toolchain: `--branch` runs on the nightly that `xtask/src/coverage.rs` pins, and fails with the `rustup toolchain install` command to run when that nightly is missing, while the workspace stays on its pinned stable one. A floor crate may measure nothing only while its `src/` defines no function; after that, a run with no lines, no regions, or no mutants for it fails. Branches are the exception, since only a function with a condition has one, but a run in which no floor crate has a branch fails. A trait method without a body counts as a function, so the first function with a body lands with its test in the same push as the first port. `cargo xtask mutants --changed` tests only the mutants in what differs from the merge-base with `origin/main`, untracked files included, and holds each to being caught or named; whether the list is current and whether a crate measured nothing are left to the full run. It's the last step of `pre-push`. A push fast-forwards `main`, so what differs from `origin/main` is what the push lands: a push that changes no floor crate passes the step at once, and one that does waits about a second and a half for each mutant in what it changes, after a build of some seconds. So a gap in changed code is refused before it reaches `main`, and the daily run is left what a scoped run can't see, a test that was weakened or removed and an entry that went stale. In `ci` on `main` the merge-base is the pushed commit, so the step finds nothing to test there. A builder runs it while editing a floor crate too, for the same answer sooner. Later phases add `cargo xtask bench` with a 20% regression threshold and the release builds (phase 11). `xtask` is a root-level crate reached through the alias, which is defined twice, in `.cargo/config.toml` and `lablet/.cargo/config.toml`; an xtask test keeps the two in step. It doesn't work from a crate directory below `lablet/`.

## Shell scripts

`cargo xtask lint-shell` runs shellcheck over every tracked shell script: `.sh` files and the git hooks, which have no extension and are found by their shebang. `product/research/` is left out, as Vale leaves it out, because it's a frozen record, and so is the vendored `lablet/telemetry/deps/`.

## Editor and agent setup

`.vscode/` recommends rust-analyzer, dprint, Vale, and Claude Code, and points rust-analyzer at both Cargo workspaces. `.claude/settings.json` runs `.claude/hooks/session-start.sh` when a Claude Code session starts. It says when the session is on `main`, when a branch is behind `origin/main` and so can't be fast-forwarded to, when the branch tracks an unexpected upstream, and when the git hooks aren't installed. It only advises; it never stops a session.

## Formatting

`cargo xtask fmt` formats Rust with rustfmt and JSON, TOML, Markdown, and YAML with dprint, configured in `dprint.json`; `fmt --check` verifies both and runs in pre-commit. The vendored and generated trees are excluded there, because they must stay byte-identical to their source. dprint downloads its pinned plugins on first use, so the first run needs the network.

## Prose

`cargo xtask lint-prose` runs Vale with the Microsoft writing style package over `README.md`, `CLAUDE.md`, `CHANGELOG.md`, `contributing/`, `product/` (not `product/research/`), `lablet/README.md`, `lablet/docs/` (not the generated `lablet/docs/telemetry/`), and `lablet/examples/`. The gate fails on errors only; `cargo xtask lint-prose --all` also shows warnings and suggestions. `.vale.ini` names the package by its release URL, so `vale sync` fetches a fixed version into `.vale/styles/`, which git ignores apart from our vocabulary. `scripts/setup.sh` runs the sync, and `lint-prose` runs it when the styles are missing, so only the first run needs the network. To move to a newer package, change the URL and run `cargo xtask setup`. Vale's own notes for agents are at <https://vale.sh/AGENTS.md>. A legitimate technical term that Vale flags as a misspelling goes in `.vale/styles/config/vocabularies/Lablet/accept.txt`, one per line, sorted. Fix an ordinary misspelling in the text. If a rule makes the docs worse, turn that one rule down in `.vale.ini` with a one-line reason.

## Reviews

A phase-end review is scaled to risk and has a budget.

- Scaffolding, configuration, and generated code get the gates, the builder's own read of the diff, and one reviewer. Logic-heavy code (the loop, policy, exporters, adapters) gets two or three focused reviewers.
- Each reviewer reports at most five findings of high or medium severity, then any lows it found, which go to triage unverified.
- The builder sorts the findings before anything is verified or fixed. A finding that isn't worth handling in a lightweight project is dropped, or the fix is to reject the input rather than to model it.
- One verifier for each surviving finding, reasoning from the code first. Reproduce only when the claim is disputed or cheap to run.
- A fix pass that adds a public item or changes a floor crate gets one reviewer before it lands on `main`, inside the review's budget.
- Each phase states a review budget of about 35 percent of the build's token cost when it adds a security boundary or a public contract, and 10 to 15 percent otherwise. The phase report gives the actual figure.
- Every gate or feature is exercised once with real input on a cold clone before the phase closes.
- [reviews.md](reviews.md) holds what to look for, drawn from defects that reached `main` and were caught by a later review.

## Versioning

One workspace version. Keep-a-changelog format in `CHANGELOG.md`. A change to `lablet/schema.json`, `lablet/telemetry/registry/`, `lablet/telemetry/templates/registry/rust-crate/`, `lablet/tests/fixtures/outcome.json`, `lablet/tests/fixtures/transcript.json`, or anything under `lablet/tests/fixtures/golden/` without an `Unreleased` entry fails `cargo xtask changelog`; CI checks out full history for it. Third-party crates are pinned to exact versions in `[workspace.dependencies]` and bumped only in dedicated commits; a crate `xtask` pins too carries the same version in both places. A bump of the workspace version regenerates the golden fixtures, which hold lablet's version as written, and carries its own `Unreleased` entry; a bump of the OpenTelemetry SDK doesn't, since the SDK's version is normalised out. MSRV is `rust-version` in the workspace manifest: the pinned toolchain minus two minor versions, raised only in a minor release. Windows isn't supported.

On a fresh clone run `scripts/setup.sh` once: it installs the pinned Rust toolchain, trusts and installs the `mise.toml` tools, and installs the git hooks (`scripts/install-hooks.sh` does only the last step). Plain cargo commands run from `lablet/`.

## Git and pull requests

- Work on a branch off `main`. When a logical piece is complete and `cargo xtask pre-push` passes locally, fast-forward `main` and push. A landing that merges parallel streams, or closes a phase, is pushed as its branch first and fast-forwarded once that branch's CI is green, since only CI runs what's Linux-only. No pull requests for now; this will be revisited as the process is learned.
- CI runs after the push. Check it; a red `main` is fixed forward before anything else lands.
- One logical change per commit. Moves and content edits in separate commits.
- A spec clarification (filling a gap, fixing an inconsistency, adding a missing test) goes in the same commit series with a note in the message.
- Architectural decisions may be made by whoever is building. Each gets an entry in `product/decisions.md` when it's made and is listed in the end-of-phase report for human review.
- Each build phase ends with a review of its diff, then a stop for human review. The next phase starts only on an explicit go-ahead.
