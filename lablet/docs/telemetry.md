# Telemetry

Lablet's telemetry is a contract. An [OpenTelemetry Weaver](https://github.com/open-telemetry/weaver) registry in [`lablet/telemetry/registry/`](../telemetry/registry/) declares every span, log record, and attribute before any code emits it, and the reference in [telemetry/](telemetry/README.md) is generated from that registry. The reference is the place to look up an attribute's type, meaning, and requirement level.

## What a run emits

| Signal                                                                                                          | Kind                | When                                        |
| --------------------------------------------------------------------------------------------------------------- | ------------------- | ------------------------------------------- |
| [`lablet.invoke_agent`](telemetry/lablet/spans.md#labletinvoke_agent)                                           | span, the root      | once for each run                           |
| [`lablet.chat`](telemetry/lablet/spans.md#labletchat)                                                           | span, child of root | once for each attempt of a provider call    |
| [`lablet.execute_tool`](telemetry/lablet/spans.md#labletexecute_tool)                                           | span, child of root | once for each tool call                     |
| [`lablet.run`](telemetry/lablet/events.md#labletrun)                                                            | log record          | once, when the run ends: the wide event     |
| [`lablet.retry`](telemetry/lablet/events.md#labletretry)                                                        | span event          | on the chat span of a failed provider call  |
| [`gen_ai.client.operation.exception`](telemetry/gen-ai/events.md#gen_aiclientoperationexception)                | log record          | with each failed provider call              |
| [`gen_ai.client.inference.operation.details`](telemetry/gen-ai/events.md#gen_aiclientinferenceoperationdetails) | log record          | only when `telemetry.capture_content` is on |

The resource carries [`service.name`, `service.version`](telemetry/service/entities.md), what the [OpenTelemetry SDK adds](telemetry/telemetry/entities.md), the `telemetry.resource` attributes from the config, and beneath them the attributes `OTEL_RESOURCE_ATTRIBUTES` names, with their escaped characters decoded. The config's and the environment's attributes have keys the composer chooses, so the registry can't declare them, and they appear on the resource only. `service.name` is the config's when `telemetry.resource` names one, else `OTEL_SERVICE_NAME`, else the one `OTEL_RESOURCE_ATTRIBUTES` names, and `lablet` when none does. `service.version` is lablet's and the SDK's attributes are the SDK's, whatever names them. That's the `lablet` command's resource: a library run's is its host's.

`gen_ai.conversation.id`, `session.id`, and `lablet.config.digest` are on every span and log record, so any of them groups a run's data without a join. So are `lablet.task.id`, `lablet.experiment.id`, and `lablet.trial`, each when the run request named it.

Every span starts when the loop measured its call to start and lasts as long as the loop measured it to take, as finely as the clock measured it: a sub-millisecond call is a span of its own length, not of none. The span events and log records are timed the same way. The `*_ms` attributes are whole milliseconds, each cut from the time or length it measures, so a latency the wide event totals is the sum of its spans' durations each cut to whole milliseconds, and can fall short of their summed durations by under a millisecond a span.

Captured content is a JSON string in the form the GenAI conventions give its attribute, and a text longer than 1 MiB is cut there. The wide event is emitted once the run's transcript is written, through the logger every destination shares, and the `lablet` command flushes the run's telemetry once after it. So it may share an export with the run's last content records, a batch a collector refuses for its size takes it along, and in a file it isn't always the run's last line. Lablet doesn't count what's lost on the way: a processor whose queue is full drops what doesn't fit, as the OpenTelemetry SDK's do.

## Where telemetry goes

This section and the next are the `lablet` command's. A library run's telemetry goes where its host's SDK sends it ([below](#running-lablet-as-a-library)).

The `lablet` command is configured as any application instrumented with OpenTelemetry is: it reads the variables of the OpenTelemetry specification from its environment, and its config's `telemetry` section overrides them field by field. A field the config states wins. A field it leaves `null`, the default of every field but `telemetry.resource`, is the environment's, and then the specification's default, but for `telemetry.file.path`: no variable names a file, so a null path writes none. `telemetry.resource`, `{}` by default, is stated over the environment's attributes key by key. `lablet check --resolved` prints the config as it's written, `null` included, and nothing the environment holds.

With nothing configured, in the config or the environment, a run writes no file, and sends its spans and log records over OTLP, HTTP/protobuf, to `http://localhost:4318`. A run whose config names a file sends there too, since the file is a destination the config adds beside the network's. With no collector listening, the telemetry sent there is lost, and the run's outcome is the same. The run's end costs about 0.9 s, the exporter's retries, and writes five lines on the diagnostic log: for spans and for log records, the exporter's line that it gave up and the SDK's line that the export failed, then lablet's warning that the run's telemetry wasn't exported whole. A collector that accepts the connection and never answers costs more: a run's end waits about five seconds for it, and a shutdown, and so the `lablet` command's exit, about five more.

| To send the telemetry                 | State or set                                                                                                                     |
| ------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| to a collector                        | `telemetry.otlp.endpoint`, or `OTEL_EXPORTER_OTLP_ENDPOINT`                                                                      |
| to a file, and to the network as well | `telemetry.file.path`, or `-` for standard error                                                                                 |
| to a file alone                       | `telemetry.file.path` and `telemetry.otlp.enabled: false`, or both `OTEL_TRACES_EXPORTER` and `OTEL_LOGS_EXPORTER` set to `none` |
| nowhere                               | `telemetry.otlp.enabled: false` and no file path, or `OTEL_SDK_DISABLED=true`, which also turns a named file off                 |

## The environment lablet honours

The `lablet` command reads each variable once, when `lablet check` or `lablet run` reads the config, and parses it as the specification does. An empty variable is unset, and a signal's own variable comes before the generic one. A name chosen from a list is matched in any case. A value lablet can't use is warned about on the diagnostic log, naming the variable and, unless the value may hold a secret, the value, and is then ignored, so the next source decides.

Lablet doesn't read the metrics variables, since it emits no metrics, nor `OTEL_LOG_LEVEL`, since its diagnostic log follows `RUST_LOG`, nor `OTEL_CONFIG_FILE`, nor the attribute value-length and log record limits, which the Rust SDK it's built on has no setting for. Every command a run starts inherits the OpenTelemetry environment as lablet has it, but for the context variables, and never the config's endpoint, headers or file. A command's context variables are its tool span's, injected through the propagators as it starts: it inherits none of `TRACEPARENT`, `TRACESTATE`, `BAGGAGE`, `B3` and the `X_B3_*` variables, a variable `tools.builtin.env` states wins over the one injected, and under `OTEL_PROPAGATORS=none` a command gets none but those it states. So with the default propagators, a `lablet run` that a command starts is a child of that command's tool span.

Three things are refused, by `lablet check` as by `lablet run`, before any run, each only for a signal whose network exporter is on: an endpoint the exporter doesn't accept, from the config or from a variable; a header in `telemetry.otlp.headers` whose name or value no header may have, where one in a header variable is warned about and dropped; and a certificate, client key or client certificate file that can't be loaded, or a key or certificate named without the other. The message names the variable or the header, or shows the endpoint as the config writes it, and never what a variable or a file holds.

## Rules of the contract

- **Semantic conventions first.** Where the core or GenAI semantic conventions define an attribute, lablet uses it under its own name and never adds a `lablet.*` twin.
- **Every `lablet.*` attribute is justified.** Its entry in the registry has a note that opens with `Justification:` and says why no convention covers it. The reference shows the note beside the attribute, and `cargo xtask weaver check` fails an entry without one.
- **Every attribute on a signal has a requirement level.** Required attributes are always present. A conditionally required one states its condition. Captured content is opt-in, and absent rather than blanked when capture is off.
- **Only raw values.** Counts, bytes, tokens, and durations in milliseconds. Ratios and averages belong to whoever aggregates.
- **Flat shape.** No nested maps. Per-tool values are template attributes such as `lablet.tool.calls.<tool name>`. The wide event has them for a tool the run offered and called, so the names in `lablet.tools.names` bound the keys.
- **Absent, never blank.** An attribute whose condition doesn't hold of a run is left out: the turn cap of a run without one, the cost of a run that isn't priced, a count the provider didn't report. A `0` is a count of zero.

A rename in the conventions lablet depends on is a breaking change to this contract, as is any change to a `lablet.*` attribute, and both get a `CHANGELOG.md` entry.

## Adding or changing an attribute

1. Look for a semantic-convention attribute first, in the vendored registries under `lablet/telemetry/deps/`.
2. Edit the registry: a new `lablet.*` attribute goes in `shared/attributes.yaml` with its justification, and every span or event that carries it, in the folder of the crate that emits it (`application/run/`, for every signal today), refers to it with a requirement level.
3. Run `cargo xtask weaver check`, then `cargo xtask weaver generate`, which writes the generated telemetry module of the crate that emits the signal, `lablet-run` for every signal today, and the reference again. The struct of the signal gains a field.
4. Fill the field where the crate builds the struct. The build fails until it's filled, which is the point: an attribute added to `lablet.run` is a field of the generated `LabletRun` that `lablet-run`'s runner must say the value of. Attribute names never appear as string literals; tests read them, and each signal's lists of required and declared keys, from the `key` module beside the struct.
5. Add an entry under `Unreleased` in `CHANGELOG.md`.

`cargo xtask pre-commit` runs the check and fails when the generated files are out of date.

## Running lablet as a library

A library run goes to the OpenTelemetry its host provides. A host builds a `Lablet` with `Lablet::builder(config, otel)`, or with `lablet::build(config, otel)`, where `otel` is a `lablet::Otel`: `Otel::new(tracer_provider, logger_provider, propagator)`, the three pieces a run's spans, its records and a command's context go through. Each is required, and lablet reads no global tracer provider or propagator of OpenTelemetry's: a host that wants none of a piece hands in the API's no-op for it, and `Otel::noop()` is the no-op of all three. A host on the global ones hands them in itself: `opentelemetry::global::tracer_provider()`, called once the host has set its global tracer provider, since the `Otel` takes its tracer when it's made, and the propagator it gave `set_text_map_propagator`, made again, or one of its own that asks the global one at each call. A run's root span is the child of the context that's current where `run` is awaited, so a run under a span the host has open is in the host's trace, and the host's sampler decides whether it's recorded. The host's SDK exports and flushes: a run returns without flushing anything, and `Lablet::shutdown` does no telemetry work.

Library mode leaves alone what configures an SDK, and says nothing of it: the config's `telemetry.file`, `telemetry.otlp` and `telemetry.resource`, the SDK's variables in the table above, `OTEL_SDK_DISABLED` among them, and the context variables. `telemetry.capture_content`, and then `OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT`, still decide whether content is captured. Lablet's secrets are still withheld from commands and cut from what they print, the values of `telemetry.otlp.headers` and the user information of `telemetry.otlp.endpoint` among them, and so are the values of the OTLP header variables and the user information of the endpoint variables. A command's context is its tool span's, injected through the propagator the `Lablet` was built with.

The host's own `tracing` subscriber sees lablet's diagnostics, such as a transcript that wasn't written, and none of its telemetry, which never passes through `tracing`. Two `Lablet`s in one process, each given providers of its own, each reach only their own. A run is stopped through its `CancelHandle`; dropping the future `Lablet::run` returns abandons it with no outcome. Dropped before the loop returns, it leaves no transcript or wide event either; dropped during the transcript write, it still leaves the transcript and no wide event.

The `traced_run` example is a host with an SDK of its own, which runs lablet beneath a span of its own and sends both over OTLP to `http://localhost:4318`, or where `OTEL_EXPORTER_OTLP_ENDPOINT` says (see [../examples/](../examples/README.md)).
