# Changelog

All notable changes to lablet are documented in this file.

The format is based on [Keep a Changelog 1.1.0](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning 2.0.0](https://semver.org/spec/v2.0.0.html). The workspace has one version. The public contract is the config schema, the outcome JSON, the transcript JSON, and the telemetry registry; a breaking change to any of them is a major version bump.

An entry under `Unreleased` is mandatory for any change to one of these files, and `cargo xtask changelog` fails without it:

- `lablet/schema.json`, the config schema
- `lablet/telemetry/registry/`, the telemetry registry
- `lablet/tests/fixtures/outcome.json`, the outcome JSON fixture
- `lablet/tests/fixtures/transcript.json`, the transcript JSON fixture
- `lablet/tests/fixtures/golden/`, the golden telemetry of three fake-provider runs
- `lablet/telemetry/templates/registry/rust-crate/`, the templates that render the registry into each crate's module

## [Unreleased]

### Changed

- The `init --provider anthropic` starter names `claude-opus-5-5`, where it named `claude-sonnet-5`, and its header says the model table lives in the examples README. Nothing else `init` writes changes.
- Root kernels: `lablet_provider_wiring::build(ready, model, propagator, capture_content)` builds the provider a checked config selects, and `Played::Live` stands for one over the network beside the fake's script; `lablet_prepare::Ready`, with `Ready::Anthropic(Target)`, is the provider `prepare` built, and `Wiring.provider: Ready` replaces `Wiring.script`; `lablet_config::host_and_port` reads the host and port of a URL as the config's reader finds them, and `lablet_config::AUTHORITY_ENDS` holds the characters that reader ends an authority at; `lablet_secrets::derived` takes the config and the client key's contents alone, since the values are held for every run, where it also took `with_values`; and `Settled::finish` returns a `Result`, refusing a `tools.builtin.env` entry whose value holds what the client key's file holds.
- Config schema: the descriptions of `telemetry.propagators` and of a `model.thinking` budget say what `check` and a run already do: the propagators inject each provider request's context as well as a command's, and a budget is at least 1,024 tokens.
- Telemetry registry: `lablet.request.thinking` on the `lablet.run` wide event carries `:summarized` or `:omitted` after the mode when the config states `model.thinking_display`, as `adaptive:omitted` or `budget:2048:summarized`, where the note named `:summarized` alone; its brief says the value is spelt as the wide event spells it, where it said as the config does, since the suffix is no config spelling. A run whose config leaves the setting out emits what it emitted before, so the golden fixtures hold.
- `FinishReason::from` reads lablet's own spellings alone, `end_turn`, `tool_use`, `max_tokens`, `context_window` and `refusal`, and keeps any other string as `Other`, a provider's own spelling among them, where it read `stop`, `stop_sequence`, `tool_calls`, `length`, `model_context_window_exceeded` and `content_filter` as the reasons they spell. Each adapter maps its provider's spellings before it calls it, so the domain holds no vendor's table; the fake provider's script still takes either vendor's spelling, through a table of the fake's own, so no script changes meaning.
- A `bash` command's context variables are its own. It inherits none of `TRACEPARENT`, `TRACESTATE`, `BAGGAGE`, `B3` and the `X_B3_*` variables, nor any variable the propagator names, and the context current as it starts, its tool span's, is injected into its environment in their place, through the propagator its `Lablet` was built with: in the command line the propagators `telemetry.propagators` names, and in the library the propagator of the `lablet::Otel` a host hands in. A key is set as the variable its normalised name names, and an empty value isn't set, so a command gets no empty `TRACESTATE`. A context variable `tools.builtin.env` states wins over the injected one, key by key, and under `telemetry.propagators: none` a command gets no context variable but those `tools.builtin.env` states. A dropped variable isn't injected either, so a context variable that filled one of lablet's credentials stays out of a command, though the context it starts in carries the value.
- Each provider call attempt runs with its own chat span current, retries included, where the run's root span was, so an adapter that propagates the context sends the attempt's own. Nothing a run emits changes.
- The command line reads the inbound context from the variables the keys of the propagators `telemetry.propagators` names map to, normalised as the specification's environment carriers are, where it read `TRACEPARENT`, `TRACESTATE` and `BAGGAGE` whichever propagators were configured.
- Breaking, for a library caller: the library configures no OpenTelemetry SDK, runs on the OpenTelemetry its host provides, and reads no environment variable. `lablet::build` takes a `lablet::Otel`, as `build(config, otel)`: the tracer provider a `Lablet`'s spans go to, the logger provider its records go to and the propagator a command's context is injected through, each required, as `Otel::new(tracer_provider, logger_provider, propagator)`. Lablet reads no global tracer provider or propagator of OpenTelemetry's, so a host on them hands them in, setting its global tracer provider before it makes the `Otel` and handing in the propagator it set, made again, or one of its own that asks the global one, and a host that wants none of a piece hands in the API's no-op for it, or `Otel::noop()` for all three. A run's root span is the child of the context that's current where the run is awaited, so a run under a span the host has open is in the host's trace, where it was a trace of its own. In library mode the config's `telemetry.file`, `telemetry.otlp`, `telemetry.propagators` and `telemetry.resource` do nothing, and nothing is said of them, so the telemetry a library caller got from its config stops; no `OTEL_*` variable is read, nor `TRACEPARENT`, `TRACESTATE` or `BAGGAGE` as a run's parent, nor the capture variable: `telemetry.capture_content` alone decides. The caller owns the config: a host that keeps the CLI's file fills its `${VAR}`s itself, through `RawConfig::substituted`, and a `Config` that still holds a `${VAR}` is refused when it's read; a host that builds its config in code sets the key as `config.model.api_key = Some(Secret::new(key))` and a tool's credentials under `tools.builtin.credentials` as `Secret`s. The environment every process a run starts begins from is what the host hands `Builder::with_process_environment`, which a config that enables `bash` needs, and lablet drops from it only what holds a credential the config names. `Builder::check` replaces `lablet::check`, since a check reports what `bash` inherits of what was handed in; it says nothing of the `telemetry` section. A client key's file isn't read in library mode, so its contents aren't cut there. `Lablet::run` flushes nothing, `Lablet::shutdown` does no telemetry work, and a run whose future was dropped no longer has its spans flushed before the next run. The command line configures the SDK from the config's `telemetry` section, and its input module is the one place lablet reads the process's environment: for the file's `${VAR}`s, the context variables, the environment every process a run starts begins from, and whether a retired variable is set.
- The OpenTelemetry SDK, its export module, the seam that parsed its environment, the OTLP settings and the inbound context are in the package `lablet-cli` alone, and the temporary root kernel `lablet-otel-sdk` is gone. `lablet-otel-env` holds the specification's parsing of the OpenTelemetry environment, which no production code calls now that the settings come from the config, and the `k=v` decoding the config's `headers` and `resource` text forms use, and `lablet-secrets`' `derived` takes from its caller the contents of the client key's file it cuts. `lablet-prepare` reads no telemetry setting: `prepare` stops before the telemetry, and `Settled::finish` goes on with what the root read of it. The diagnostic log's lines keep their targets, `lablet::lablet`, `lablet::propagation` and `lablet::otlp`, so a `RUST_LOG` filter written against them keeps working; `lablet::otel_env` has nothing left to say, since the environment's parsing no longer runs. The tests that read lablet's OTLP/JSON file or a receiver run through the command line's composition, `lablet_cli::compose`, and the library's tests hand in providers over the SDK's in-memory exporters. `cargo xtask lint-layers` holds the library root and every root kernel to the OpenTelemetry API, so the SDK is the CLI root's alone. The `traced_run` example is a host with an SDK of its own, which hands its providers in and runs lablet beneath a span of its own.
- The `lablet` binary is built from a package of its own, `lablet-cli`, and the package `lablet` is the library alone. `cargo run --bin lablet` builds the command as before, and it takes the same arguments, prints the same output and exits with the same codes as before. The two never depend on each other: what both need is in root kernels under `lablet/apps/shared/`, which the library re-exports, so its public items keep their paths. Some of those types gain public methods the kernels share, which a library caller can now call: `Config`'s `place_of`, `place_of_item`, `refused` and `written_text`, and `config::Model`'s `applies` and `stated`. `Checked::new` and `RunRequest::into_start`, which gives `lablet-run`'s `RunStart`, are public too, for the two roots and their kernels, and a host can't use them: it gets no `Derived` to call `Checked::new` with, and no `Runner` to start a `RunStart` with. The impl of `From<config::BuiltinTool>` for `lablet-tools-builtin`'s `Tool` is gone, since the config's kernel names no component. Nothing a run emits changes, which the golden comparison holds; the comparison now runs from `lablet-cli`'s directory, `cargo test -p lablet-cli --test it golden`.
- Telemetry registry: the root span `lablet.invoke_agent` and the wide event `lablet.run` move from `apps/lablet/` to `application/run/`, since `lablet-run` now makes both. Nothing a run emits changes, which the golden comparison holds. `lablet::telemetry::key` re-exports `lablet-run`'s `key`, so it holds every key it held and also those of the loop's spans and records, and `lablet::telemetry::SCHEMA_URL` is re-exported with the same value. `lablet-run`: `Runner` runs a run from its reading of the clock to its wide event, its id and context, its root span with the loop under it, its transcript and its wide event, and hands back a transcript that has no place or wasn't written for the caller to report. The transcript is written through the new `TranscriptWriter` port, which `lablet-transcript-json`'s `JsonTranscripts` implements. The `Clock` port gains `wall`, which a run reads once, as it starts. `RunCancellation` and `NeverCancelled` move to `lablet-run`, and `telemetry::SCOPE` names lablet's instrumentation scope. A run whose transcript has no place, because the path the config names can't take its id, is reported on the diagnostic log once the run ends, where it was reported as it started.
- Telemetry registry: `lablet.telemetry.dropped_records` is gone from the `lablet.run` wide event and from `shared/attributes.yaml`, and the golden fixtures lose it. Lablet no longer counts what its exporters lose: the SDK's batch processors drop what doesn't fit, warn on the diagnostic log at a processor's first drop, and log its lifetime total when it's shut down, so a `Lablet` that runs many times can't tell which run lost records. The wide event is emitted once for each run and every destination receives it, where each destination made its own with its own count. Its note no longer says it's exported alone after the run's other records: it goes through the logger they share and may share an export with them.
- The telemetry goes through the OpenTelemetry SDK's own batch processors. Lablet states the specification's defaults on the SDK, the batch processors' schedule, queue and batch sizes, the sampler, parent-based always on, the span limits and the attribute count limit, so the SDK's own defaults, which would read `OTEL_BSP_*`, `OTEL_BLRP_*`, `OTEL_TRACES_SAMPLER`, `OTEL_TRACES_SAMPLER_ARG` and the limit variables for themselves, never apply, and none of those variables is read; it sampled every trace and set its own limits and queues before. A run under an inbound parent that isn't sampled exports its log records and no spans. A run's end emits the wide event and flushes once, and waits at most about five seconds when a collector doesn't answer, as before; a collector that accepts the connection and never answers also holds the shutdown, and so the command line's exit, about five seconds more. In the file, the wide event is no longer always the run's last line.
- Telemetry is timed to the nanosecond. Every span's start and end, the `lablet.retry` span event, and every log record's time and observed time, the root span's and the wide event's among them, are the run's start as the wall clock gave it plus the offset the loop measured, whole, where each was cut to whole milliseconds and a call shorter than a millisecond made a span that lasted none. Every `*_ms` attribute, the outcome's `duration_ms` and the transcript's times stay in whole milliseconds, each the whole milliseconds of the time or the length it measures, so a latency total can fall short of the summed durations of its spans by under a millisecond a span. A wall clock that reads before the epoch starts a run at the epoch, in its telemetry as in its documents. The registry, the outcome JSON and the transcript JSON are unchanged. The golden fixtures give each time as an offset in nanoseconds from the root span's start, under `start_ns`, `end_ns`, `time_ns` and `observed_time_ns`, where they gave whole milliseconds under the same names ending in `_ms`; no time in them moved, since on tokio's paused clock every time those runs measure is a whole millisecond. `lablet-model`: `RunContext::started` is a `SystemTime` that holds the start whole, in place of the field `started_unix_ms`, which is now a method that cuts it, and `FinishedRun` gains `duration`, how long the run took as the loop measured it. `lablet-run`: `telemetry::time_at` is the time an offset into a run is, which the loop and the composition root both time their signals by.
- The library no longer has an observer. `build_observed`, `RunObserver`, `RunEvent`, `EventKind` and `ToolCall::trace_context` are gone, and nothing plugs into a `Lablet`: its telemetry goes to the providers its host hands in, through the OpenTelemetry API and lablet's own logger, and a host's `tracing` subscriber sees lablet's diagnostics and none of its telemetry. A tool executor finds the span of its own call in the current OpenTelemetry context, where it read `ToolCall::trace_context` before. `lablet::telemetry` is public with two items, `key` and the registry's `SCHEMA_URL`: a constant for each key of the root span and the wide event, and for each of the two the lists of the keys the registry requires of it and declares for it, and of its template keys where it has any (`LABLET_RUN_REQUIRED`, `LABLET_RUN_KEYS`, `LABLET_RUN_TEMPLATES`), so a caller may read a run's export by key and hold it to the registry; the keys of the loop's spans and records are `lablet_run::telemetry`'s. The generated structs that write the signals aren't public. A run's transcript is still written before its wide event is emitted and its telemetry flushed, so the transcript the wide event names is whole when it arrives. A run is stopped through its `CancelHandle`: dropping the future `Lablet::run` returns abandons the run with no outcome, and with no transcript or wide event when it's dropped before the loop returns, though one dropped during the transcript write still leaves the transcript, with no wide event, and one dropped during the flush leaves both. The spans it had open are exported unfilled, at the time they were dropped, before the `Lablet`'s next run starts. The telemetry on the wire is unchanged, which the golden comparison holds: every span, record and attribute a run emits has the same names, values, parents, times, severity and scope as before.
- Telemetry registry: the registry is organised by the crate that emits each signal, `shared/` for lablet's attributes, the resource and the join group, `application/run/` for the chat and tool spans, the failed-attempt and content records and the retry event, and `apps/lablet/` for the root span and the wide event. It states as annotations under `lablet:` what its prose said before: the value `gen_ai.operation.name` has on each span and on the failed-attempt record, `gen_ai.agent.name` on the root span and the wide event and `lablet.chat.purpose` on the chat span; each signal's classes of `error.type`, the failed-attempt record's classes of `exception.type`, the tool span's values of `gen_ai.tool.type` and `network.transport` and the content record's operations; that `lablet.retry` is a span event and the failed-attempt record is `warn`; and the six join keys, marked on the group's references. The brief of the chat span's `lablet.chat.purpose` reference now says it's always `turn`, as the briefs of the other fixed values do; that cell is the one change to the reference pages. Nothing on the wire changes: every signal keeps its name, attributes, values and severity. The changelog gate watches the templates that render the registry into each crate's module, `lablet/telemetry/templates/registry/rust-crate/`. They write each signal's lists of required, declared and template keys into its module's `key`, and refuse an enum attribute whose members aren't all text, which has no Rust type.
- Every export's resource carries the attributes `telemetry.resource` states, as a map or as OpenTelemetry's `k=v` text with each value's `%XX` escapes decoded, and nothing the environment names: `OTEL_RESOURCE_ATTRIBUTES` and `OTEL_SERVICE_NAME` aren't read, so a framework's labels, such as `deployment.environment`, reach lablet's own telemetry where the file writes `resource: service.name=${OTEL_SERVICE_NAME:-},${OTEL_RESOURCE_ATTRIBUTES:-}`. `service.version` stays lablet's whichever names it, and `service.name` is the first the config names, else `lablet`. Config schema: `telemetry.resource` takes the text form, and its description says so.
- The command line's settings come from the config alone, and a variable enters where the file writes `${VAR}` for it: no `OTEL_*` variable is read, and a field left `null` means not stated, never a fallback to the environment. `telemetry.otlp.endpoint: null` means nothing goes over the network, whatever else the section states, and a stated endpoint sends both signals there, so `telemetry.otlp.enabled` is gone, and a config that still writes the key is refused as it would be for any unknown key, naming `endpoint` beside it. Every value of `telemetry.otlp.headers`, in the map and in the text form, is one of lablet's own credentials and holds a `${VAR}`: cut from every result, dropped from every process a run starts, and refused without being shown when it's written out. An `OTEL_EXPORTER_OTLP_HEADERS` the file doesn't write is the framework's: every command inherits it uncut, and `check` names it on `unread:`. Config schema: `telemetry.otlp.enabled` is gone, `headers` takes OpenTelemetry's `k=v` text as well as a map, `telemetry.otlp.tls` is new with `ca_file`, `client_cert` and `client_key`, `telemetry.propagators` is new, `protocol` takes `null`, and the descriptions of `endpoint`, `protocol` and `telemetry.file.path` say what `null` means.
- `lablet check` refuses what `lablet run` refuses of the network exporter, an endpoint the exporter doesn't accept, a header whose name or value isn't one a header may have, and a TLS file that can't be read or loaded, where only a run refused them; and `check` makes the network exporters as `run` does, which loads the platform's trust roots and opens no connection, since a gRPC channel connects at the first export and an HTTP client at the first request, so trust roots that can't be loaded and an HTTP client that can't be made are refused by `check` as by `run`, and `run` sends through the exporters its check made rather than making them again. `check` builds the target of each provider adapter that exists too, the Anthropic adapter's with its HTTP client, and calls no provider, so a key a header can't carry is refused under `model.api_key` with nothing of it shown, a base URL with a query or a fragment under `model.base_url`, with no value shown when it's written out, or naming the variable that filled it, and an HTTP client that can't be made under `model.provider`. An endpoint a `${VAR}` filled that the exporter doesn't accept is refused under `telemetry.otlp.endpoint` as the file wrote it, naming the variable and never its value, as `"${OTEL_EXPORTER_OTLP_ENDPOINT:-}" is refused: `OTEL_EXPORTER_OTLP_ENDPOINT` holds what isn't a URL the exporter accepts`; a refused endpoint the config writes is shown as written, or with no value when that holds an `@`, since its user information is a secret and where that ends can't be told once it may hold a `/` not written as `%2F`. `telemetry.otlp.endpoint` set to nothing, written so or by a variable that came out empty, states no endpoint, so nothing goes over the network, where an empty endpoint was sent to. The authority of a URL ends at a `\` as at a `/`, since the `url` crate the Anthropic adapter sends through reads a `\` in an `http` or `https` URL as a `/`. `check` passed a user or password that holds one, as a gateway user `CORP\jdoe` does, and the adapter sent the key to the host `corp` with the password in the path; such a URL is now refused as one holding a `/` is, by its variable's name where a variable gives the `\` anywhere but straight after the `://` of `model.base_url`, and each fix names the `\` beside `/`, `?`, `#` and `@`. `model.base_url` names its host straight after `://`, so a `/`, `\`, `?` or `#` there is refused as a URL that names no host, whether the text or a variable put it there, where a `\` passed `check` and the adapter skipped it to send to the host after it. `check` then holds its reading of `model.base_url` to the Anthropic target's, and refuses, showing nothing of it, a URL in which the target finds a user or password where `check` finds none, or none where it finds one, or another host or port. A system prompt of whitespace alone, in `prompt.system` or in the file `prompt.system_file` names, is refused, where it was sent as a system block that says nothing; an empty one is still a run with no system prompt. One byte order mark at the start of that file is dropped, where it was sent as the prompt's first character, so a file that holds only one is empty. A credential's `${VAR}` written in a setting other than its field is refused by the setting's key and line, showing nothing of its text, where the text was shown with any default written beside the variable, and a library caller gets it as `ConfigError::Refused`, where it was `ConfigError::Invalid` with the text shown.
- Lablet protects the credentials it knows and nothing else, defined by the config's fields: its own are the model's key, `model.api_key`, every value of `telemetry.otlp.headers` and of an HTTP server's `headers`, and the user information of `model.base_url`, `telemetry.otlp.endpoint` and a server's `url`, and the given ones are the entries of `tools.builtin.credentials`, each given to `bash` under the name written there. A credential is written as a `${VAR}`, or set in code as a `Secret`, and never as the value itself, which is refused without being shown. The user and the password of a URL are each their own `${VAR}`, read off the URL as the file or an override wrote it: a user or password written out, beside a `${VAR}` or in a `${VAR:-default}`'s default among it, is refused by its line or as an override, showing nothing of the URL, with the fix `https://${GW_USER}:${GW_PASS}@gw/v1`, and a variable that fills a whole URL holding either is refused by its name, showing nothing of what it holds. A URL set in code is own and cut, since a host has no other way to give a gateway's password, and so is one set in code where the file wrote `null`, or a `${VAR}` that came out empty. No process a run starts inherits a variable that filled an own or given field, nor any variable of the environment it was handed whose value, as it stands or with its `%XX` escapes decoded, holds an own or given value of 16 bytes or more: both roots drop both, in one place, and `bash` then gets `tools.builtin.env` as set and each credential under its name. A `tools.builtin.env` entry is passed as set and makes nothing a secret: one filled from an own or given variable is refused with its fix, one whose filled value holds an own or given value of 16 bytes or more, as it stands or with its `%XX` escapes decoded, is refused by the field whose value it holds, whether another variable gave it or the file wrote it out, whole or split by a `${VAR}` or a default, and one that names its own variable is refused where `bash` inherits it already. Each is refused by its line with nothing of the entry shown; the entry's text was shown before, with what's written beside a `${VAR}` or in its default, unless the cut found a value in it, and a library caller gets each as `ConfigError::Refused`, where it was `ConfigError::Invalid` with the value shown. A fix names a variable only where a set one gave the whole value, and the fix of an entry whose value holds a credential's otherwise says to rotate the value if it was one. The contents of the file `telemetry.otlp.tls.client_key` names are cut by the command line, which reads them whenever the key is stated, endpoint or none, and `check` names the key under `own:`, and a `tools.builtin.env` entry whose value holds them is refused as one holding an own value is, once the command line has read the file; the library reads no telemetry setting, so it neither reads nor cuts them, and its check doesn't name them. Each value is cut out of every tool result with its bounded parts, each line of a value that has several and its `\n`-escaped form, and what follows `Bearer `, `Basic ` or `Token `, each when it's at least 16 bytes; the user information of a URL is cut whole and by each half, as written and with its `%XX` escapes decoded, and as the `Authorization: Basic` credentials an HTTP client makes of it, with and without `Basic `, since the Anthropic adapter sends that encoding to the host `model.base_url` names and a server may repeat it. The message of an executor error, and every other text the loop writes itself, is cut the same way, where an executor's message used to be sent as it came, and the message is bounded to 2,048 bytes only after the cut, so a value astride the bound shows nothing of itself. The values travel on the `ToolCall`, so an executor can't skip the cut, and are read for every run. Config schema: `model.api_key_env` is gone and `model.api_key` takes its place, `tools.builtin.credentials` is new, and the descriptions of `model.api_key`, `model.base_url`, `tools.builtin.env`, `tools.builtin.credentials`, `tools.mcp[].headers` and `telemetry.otlp.headers` say which values are credentials. A config that still writes `api_key_env` is refused as an unknown key, naming `api_key` beside it, and the `init` starters write `api_key: ${ANTHROPIC_API_KEY}` and `api_key: ${OPENAI_API_KEY}`.
- Config digest, per field: a setting that says what a run does enters the digest as it ran, so `name: ${MODEL}` with two values is two digests, while a setting that says where something is, a path, a `tools.builtin.env` value or what starts a server, enters as the file wrote it, `${VAR}` and all, so `root: ${REPO}` is one digest on every machine, and a credential leaves it, `model.api_key`, each value of `tools.builtin.credentials` and of an HTTP server's `headers`, and the user information of `model.base_url` and a server's `url`, so two runs that differ only in a rotated token share a digest, and a key set in code and one filled from a variable have the same digest. An entry of `tools.builtin.env` or `credentials` written as a lone `${VAR}` that came out empty, which no command gets, stays in `check --resolved` as the file wrote it, and in the digest, a credential's by its name alone, so a file has one digest whether or not the variable is set. Every digest changes once with this, since `api_key_env` leaves the resolved config and `credentials` joins it, and the golden fixtures' `lablet.config.digest` moves with them and nothing else in them.
- A relative path the file writes starts at the file's directory, wherever lablet runs, where it started at the working directory, and one given on the command line, by `--set`, `--config` or `--prompt-file`, still starts where lablet runs; `check --resolved`, every message and the digest keep each path as the file wrote it, so one file has one digest wherever it's run from. - The `lablet` binary: `lablet init [--provider anthropic|openai|fake] [dir]` writes a starter config into a directory, `.` by default, with a script beside it for `fake`, and writes over nothing. `lablet run --config <file>` takes the task prompt from `--prompt`, from `--prompt-file`, or from standard input, and a blank one is a `config:` error. `--run-id`, `--task`, `--experiment`, and `--trial` name the run as a run request does. It prints the outcome document on standard output as one line, and ends with one summary line on standard error, such as `completed: 2 turns, 342 tokens, 1 tool call, 1.2s`, which `--quiet` and a telemetry file path of `-` leave out. A run that completed exits 0, one that stopped any other way exits 2, and one that never started exits 1, as arguments the command line refuses do. The diagnostic log is on standard error, filtered by `RUST_LOG` and showing warnings when it's unset, and it's off when the telemetry is on standard error unless `RUST_LOG` asks for it. On Linux the process clears its `PR_SET_DUMPABLE` flag before anything else, so no other process of its user can read its environment through `/proc`. Ctrl-C and `SIGTERM` stop a run as a fired `CancelHandle` does, so it still prints its outcome, writes its transcript and its wide event, and exits 2. A run that the provider's error ended also prints `provider:` and the error on standard error. `lablet check --config <file>` checks a config as the library's `Builder::check` does and lists the tools a run is offered, a line each, or with `--resolved` prints the resolved config as YAML, and ends with a line such as `passed: 2 tools`; a config it refuses exits 1 with the refusal as a `config:` message. `--set key=value`, on `run` and `check`, states a setting over the config's. `lablet schema` prints the config's JSON Schema, as `lablet/schema.json` holds it. A reader that closes its end early, as `head` does, is told on standard error, and the exit code stays what the command's work says.
- The OTLP exporter is configured from `telemetry.otlp` alone: its endpoint, protocol, headers and TLS files are the config's, both signals go to the one endpoint over the one protocol, the timeout is the specification's 10 seconds, and `gzip` is compiled in for both transports. A request carries the config's headers and the exporter's own, whatever a header variable of the environment sets: the pinned exporter's user agent on both transports, and on HTTP the body's type and the encoding it's compressed in. The environment's endpoint, protocol, headers, timeout, insecure, certificate, client key and client certificate variables, `OTEL_TRACES_EXPORTER`, `OTEL_LOGS_EXPORTER` and `OTEL_SDK_DISABLED` aren't read; the one variable the pinned exporter reads for itself is `OTEL_EXPORTER_OTLP_COMPRESSION` and its signal forms, which `check`'s `telemetry:` line says when one is set and an endpoint is named, and a canary holds. - Inbound context: `TRACEPARENT` and `TRACESTATE` in lablet's environment make every run a child of that trace. They're read once, when the command line composes its run, through the propagators `telemetry.propagators` names, `tracecontext` and `baggage` by default, never through the global one; `none` turns them off, and a name lablet doesn't serve is refused.
