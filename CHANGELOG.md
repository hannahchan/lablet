# Changelog

All notable changes to lablet are documented in this file.

The format is based on [Keep a Changelog 1.1.0](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning 2.0.0](https://semver.org/spec/v2.0.0.html). The workspace has one version. The public contract is the config schema, the outcome JSON, the transcript JSON, and the telemetry registry; a breaking change to any of them is a major version bump.

An entry under `Unreleased` is mandatory for any change to one of these files, and `cargo xtask changelog` fails without it:

- `lablet/schema.json`, the config schema
- `lablet/telemetry/registry/`, the telemetry registry
- `lablet/tests/fixtures/outcome.json`, the outcome JSON fixture
- `lablet/tests/fixtures/transcript.json`, the transcript JSON fixture

## [Unreleased]

### Changed

- Lablet's secrets are defined by the config's fields, where only the model's key was one before: the model's key; every value of `telemetry.otlp.headers` and of an HTTP server's `headers`, written or substituted; the user information of `model.base_url`, `telemetry.otlp.endpoint` and a server's `url`; and every variable substituted into `tools.builtin.env` or a stdio server's `env`. A variable in the set is withheld from every command and reaches one only where `tools.builtin.env` names it. Each value is cut out of every tool result with its bounded parts, each line of a value that has several and its `\n`-escaped form, and what follows `Bearer `, `Basic ` or `Token `, each when it's at least 16 bytes. The message of an executor error, and every other text the loop writes itself, is cut the same way, where an executor's message used to be sent as it came. The values travel on the `ToolCall`, so an executor can't skip the cut, and are read whenever a run has an executor. Config schema: the descriptions of `model.api_key_env`, `model.base_url`, `tools.builtin.env`, `tools.mcp[].env`, `tools.mcp[].headers` and `telemetry.otlp.headers` say which values are secrets.
- Config digest: every value of an HTTP server's `headers` and the user information of `model.base_url` and a server's `url` leave it, so two runs that differ only in a rotated token share a digest. `tools.builtin.env` stays in it. The digest of a config that states none of these is unchanged.
- `lablet check` ends with three lines on standard error where it ended with one: `withheld:` and the variables no command inherits, `cut:` and the names whose values no result shows, each with a note when the value is unset, empty or under the 16-byte floor, then `passed: 2 tools`. No line holds a value.
- The diagnostic log holds the OpenTelemetry crates' targets to `warn` unless `RUST_LOG` names one, since at `debug` the exporter prints the endpoint it resolved.
- Config schema: `tools.builtin.env`'s description says a command inherits lablet's environment less the variables lablet reads its secrets from, where it still described the short list `bash` started with before.

- Cancellation stops what's in flight. A run cancelled during a provider call attempt, a wait before a retry, or a tool call drops it there and stops with `cancelled`, where it used to wait for the call to return, so it stops within the grace period a container's stop allows and still writes its outcome, its transcript and its wide event. A tool call that was stopped has the new `lablet.tool.status` member `cancelled`, which is also its span's `error.type` and, in the transcript, how it `ended`; it ran, so it counts in `lablet.tool_calls.total` and `lablet.tool_calls.errors` and in its tool's keys. Every call whose turn comes once the run is cancelled is `not_run` and starts nothing, so no later group runs. A provider call attempt that was dropped has a `lablet.chat` span that ends when it was dropped, with `error.type` `cancelled`, no usage, no `lablet.retry` event and no exception record, and it counts in `lablet.provider.retries` and the provider latencies as a failed attempt does. A cancelled MCP call returns nothing to read its `mcp.*` attributes and `network.transport` from, so its span isn't required to have them. The `Cancellation` port gains `cancelled`, which resolves once the run should stop, and observers are told of a dropped attempt with the new event `ProviderCallCancelled`.
- In explicit mode, a `task_complete` call whose arguments aren't valid JSON no longer completes the run with a null result. It's answered as `malformed_input`, like any call with bad arguments, the response's other calls run, and the model can call `task_complete` again. It counts as a tool error.
- Tool calls in one response run in groups rather than one at a time. Consecutive calls to tools that only read run together, at most `max_concurrent_tool_calls` at a time; any other call runs alone, and groups keep the order the model gave. Outcomes are recorded in call order whichever call finished first. Once calls overlap, `lablet.tool_calls.latency_ms.total` can exceed the run's wall time, since it sums each call's latency.
- A run cancelled while it waits to retry a provider call stops with `cancelled` and makes no further attempt, instead of spending the retries it had left. `lablet.retry.will_retry` is the decision made when the attempt failed, so on such a run it's `true` for an attempt that never came, and the root span's stop reason says why.
- A tool filter that names a tool no executor serves is refused when the run's tools are built, so a misspelt `deny` entry can't leave the tool it meant to deny on offer.
- `lablet.run.transcript_path` now reads "where the run's transcript is written," rather than "was written." It holds the path the run was given before it started, and the wide event carries it whether or not the write succeeded, so the attribute names a destination rather than reporting a file that exists. The key, its type, and its conditional requirement are unchanged.
- A provider call attempt that failed and reported usage counts toward `run.max_total_tokens` and the cost. The summary holds what failed attempts reported apart from the outcome's `usage`, which still counts the calls that succeeded, so a run that fails more often doesn't look cheaper than it was.
- A retry waits the longer of the backoff and the wait the server asked for. A server that asks for more than `run.retry_hint_max` ends the retries with `retries_exhausted`. Every wait is raised by up to `run.retry_jitter` of itself, read from the run id, the turn and the attempt, so runs that were throttled together come back apart and a replayed run waits as it did.
- The stop policy is asked again once a provider call attempt has failed, and before each retry. An attempt that used up the run's time or its token budget stops the run with `timeout` or `max_total_tokens`, whether or not the call had a retry left, where the reason used to depend on it.
- A provider that rejects the credentials fails with the error kind `auth`, which is never retried and ends the run with `provider_error`.
- The message of a provider error or a tool error is cut to 2,048 bytes.
- Outcome document: `usage.reasoning_output_tokens`, `usage.cache_read_tokens`, and `usage.cache_write_tokens` are `null` when the provider didn't report the count, where they were `0`, so a zero is a count of zero and never a gap. Several servers answer to one provider name and report different things, and a reader couldn't tell which zeros to believe. A run's total holds a count when any of its provider calls reported it, and the cost and the token budget read a missing count as nothing. The transcript's per-turn usage follows the same rule.
- The stop reason `tool_errors_exhausted` is now `invalid_calls_exhausted`, in the outcome document and as a member of `lablet.run.stop_reason`, and it stops a different run. The cap on consecutive tool error results is gone: an error result, a timeout, or an executor that failed never ends a run, since how a model recovers from a failing tool is part of what a run measures. The cap that replaces it counts invalid turns in a row. An invalid turn is one whose calls all reached no tool, because each named a tool the run doesn't offer or had arguments that didn't parse. A turn in which any call reached a tool ends the count, whatever the tool returned, so one response adds one to the count at most and the order of its calls never decides it. The stop policy takes the cap as `max_consecutive_invalid_turns`, and with none no run stops for it.
- A run may have no turn cap. The stop policy's `max_turns` is optional, and with none the timeout and the token budget bound the run. On the `lablet.run` wide event `lablet.run.max_turns` is required only when the run has a cap, where it was always required.
- In explicit mode, a `task_complete` call completes a run only when it's the response's only call. One made beside other calls, a second `task_complete` among them, used to complete the run, and the other calls never ran, so a run reported work as done that was only asked for. Now the other calls run, and the `task_complete` call is answered with an error result that asks for it on its own, under the new `lablet.tool.status` member `rejected`, which is also the `error.type` of the call's `lablet.execute_tool` span. A rejected call counts in `lablet.tool_calls.total` and `lablet.tool_calls.errors` and against `task_complete` in the per-tool keys, and a turn whose calls were all rejected is an invalid turn. In natural mode, a tool that an executor serves under the name `task_complete` runs like any other.
- Tool output cap: an output longer than the cap is cut in one of three ways, and each adds one line that says what was left out. `head` sends the start up to the cap and then `[truncated: the first 50000 of 5242880 bytes]`. `head_tail` sends half the cap from each end, around `[truncated: 5192880 of 5242880 bytes left out]`. `preview` sends a short preview of the start and then `[output too large: the first 2000 of 5242880 bytes]`, and a preview longer than the cap is refused. An output no longer than the cap is sent whole, whichever way is set. The loop hands a tool executor what the cap can use of an output, and the executor keeps that much and counts the rest. So a tool that never stops writing can't take lablet's memory, and `truncated_from_bytes` is still the size of the whole output. An executor may close an output with one line about the whole of it, as `bash` does with the exit code. The model is sent that line after everything else, whatever the cut leaves out. It counts in the size of the output but not against the cap, so an output whose text fits the cap is sent whole with it. No more than 256 bytes of it are kept, and the line of `head_tail` counts it among what was sent.
- No call's deadline is later than the run's. A tool call is given the time the run has left when its turn comes, of which its executor takes no more than its own limit, and a provider call the shorter of that and the provider timeout. So a run overruns its timeout only by the time a call takes to stop, and the one timeout that every tool shared is gone. No tool starts in a run whose time has gone: the run stops with `timeout`, and the turn's calls stay unanswered. When the time runs out inside a tool phase, each call whose turn comes later is answered with the new `lablet.tool.status` member `not_run`. Nothing is started for such a call, so it's in the transcript and nowhere else: `lablet.tool_calls.total` and every other total leave it out, no `lablet.execute_tool` span carries the value, and a turn that the timeout cut short never counts as an invalid turn. The member `timeout` now says which deadline a call ran past.
- A provider call attempt whose turn comes when the run's time has gone is never made. The run stops with `timeout`, the provider isn't called, and nothing reports an attempt, as nothing reports a tool call that was never run. Such an attempt used to be made with a deadline of zero, which broke the rule that no provider call follows the condition that should have stopped the run.
- A call begins once the observer has been told of it. The start and the latency of a provider call attempt and of a tool call are measured from there, so neither counts the time an observer took, and the call's deadline is the time the run has left then. A failed provider call attempt reports when it began and how long it took, as a successful one does, so the latencies a run's attempts report sum to `lablet.provider.latency_ms.total` and the longest is `lablet.provider.latency_ms.max`.
- A run's context holds each MCP server's name with the version it gave, and the servers with their lifetime, so a run reports both or neither. A model's provider is read from the API it's reached through, which decides it, and is no longer held beside it.
- Outcome document: `schema_version` is its first key, and its value is `1`. The version rises when a reader that knows the old form could misread the new one, which dropping a key, renaming one, or changing what one means all do and adding one doesn't. Reading a document refuses a version other than the one lablet writes, as it refuses a key it doesn't know and an outcome no run could have had. `lablet/tests/fixtures/outcome.json` now holds the document byte for byte, so it shows the keys of `result.structured` in the order lablet writes them, which is alphabetical.
- Transcript document: after `schema_version` comes what names the run, which is `run_id`, `labels`, `config_digest`, `lablet_version`, `model`, and `started_unix_ms`, and then `tools`, the specs the run offered in the order it offered them, ahead of `system` and `turns`. `model` holds the provider, the API it was reached through, the model's name, and whether reasoning was sent back. So a transcript found on its own says which run it's of and joins that run's outcome and telemetry, and the offsets in its turns count from `started_unix_ms`. Every change adds a key, so `schema_version` stays `1`. A block of a response refuses a key it doesn't know when it's read, whatever kind of block it is. `lablet/tests/fixtures/transcript.json` holds one example of the document byte for byte.
- The types of `lablet-model` no longer have a serde form, so a `RunOutcome`, a `Transcript`, a `RunSummary`, and what they hold don't serialise. The documents are `OutcomeDocument` and `TranscriptDocument` in the new `lablet-documents` crate, which maps them from a run's outcome and its transcript. A message and a tool spec still serialise, because the loop measures request bytes and the tools digest with them, and neither number changes.
- Telemetry contract: `gen_ai.usage.reasoning.output_tokens`, `gen_ai.usage.cache_read.input_tokens`, and `gen_ai.usage.cache_write.input_tokens` are left out when the provider didn't report the count, where the `lablet.invoke_agent` span and the `lablet.run` wide event required them, so a zero in telemetry is a count of zero, as in the outcome. The `lablet.chat` span of a failed attempt carries the usage the attempt reported. Its `error.type`, and the `exception.type` of its `gen_ai.client.operation.exception` record, may be `auth`. The `error.type` of a `lablet.execute_tool` span is its `lablet.tool.status` whenever that isn't `ok`, so it may be `malformed_input` or `rejected`. On the `gen_ai.client.inference.operation.details` record, `lablet.turn` is required of a record for a chat span or a tool span and no longer of every record, and `gen_ai.operation.name` may be `invoke_agent`, because the record of the tools a run offered belongs to the root span.
- Telemetry contract: on the `lablet.run` wide event `lablet.mcp.servers` is required only when the run has MCP servers, where it was always required. A run without any has none of `lablet.mcp.servers`, `lablet.mcp.server_versions`, and `lablet.mcp.lifetime`, where it would have had an empty list of servers and no lifetime to go with it.
- A run's summary groups its totals. `prompt` holds the sizes of the system prompt, the task prompt, and the tool specs. `provider` holds the retries and the latency of the provider call attempts, whose total and slowest are one value. `tool_calls` holds the counts, the latency, and the sizes of the tool calls. Each group of totals adds, as usage does, and a run's totals are the sum of what each of its calls adds. No number changes.
- The loop tells an observer more. `RunStarted` carries the request parameters every provider call of the run shares, which an observer reports on each call before the summary that holds them exists. `ToolCallFinished` carries when the call began, as the transcript holds it, so a tool span is timed by what the loop measured.
- A run's context no longer holds the composer's resource attributes. They're the telemetry's alone: a `Lablet` hands `telemetry.resource` to its observer when it's built, and every export carries them on its resource, so no second copy exists that could differ from the first.
- Config digest: a setting that nothing of the config applies is left out of the resolved config, so two configs that differ only in such a setting share a digest. Any other setting changes the digest whether or not it has an effect. `tools.output_cut` and `tools.output_preview_bytes` are left out when `tools.max_output_bytes` is `null`, `tools.mcp_lifetime` and `tools.mcp_result` when `tools.mcp` is empty, and the `root`, `timeout`, and `env` of `tools.builtin` when no built-in tool is enabled. So every config without an MCP server, which is every config this version builds, has a new digest.
- A refusal for a key variable that isn't set, or is empty, names the variable when `model.api_key_env` is written in capital letters, digits, and `_`, as `ANTHROPIC_API_KEY` is, where it said only "the variable it names." Any other value may be a key written in the name's place, so a refusal still shows nothing of it.
- Transcript document: `task_prompt`, the task the run was given, follows `system`. A run that no response reached has no turn, and its transcript now says what was asked. The change adds a key, so `schema_version` stays `1`, and `lablet/tests/fixtures/transcript.json` holds it.
- Every refusal of a config names the key, with its place in a list as `tools.allow[1]`, and the line it's written on, or says that an override set it. It shows the value as the config writes it, as JSON writes it, and before `${VAR}` substitution, so nothing a variable holds reaches a message; a refusal of a value a setting doesn't take lists the values it takes. An unknown key is `ConfigError::UnknownKey`, where it was a `Syntax` error, and names the keys beside it. `BuildError::Refused` is gone: a file the config names that can't be read, a script that's refused and a root that's no directory are `ConfigError::Invalid`, and `BuildError::KeyVariable`, `RootHolds` and `UnknownTool` say where the setting was written.
- The config digest is a `ConfigDigest`, in `Config::digest` and in a run's context, which holds 64 lower-case hex digits and nothing else. It's taken of the config as it's written, so a value a variable gives never enters it.
- `RunRequest::run_id` refuses an id that isn't one component of a path, `.` and `..` and any id that holds a `/` or a NUL, and an id longer than 128 bytes, since a run's files are named with its id.
- A YAML config that holds `.nan` or `.inf` is refused when it's read, since JSON has no such number, and a JSON config that writes a key twice in one object is refused, where the last one was kept.
- `model.base_url` is refused when it isn't a URL that begins `http://` or `https://` and names a host.

### Added

- `lablet/schema.json`, the config's JSON Schema, which `lablet::schema` returns. It states every key, the values each takes, and each default, from the types a config is read into.
- `RawConfig`, the tree a config's text is read into, which keeps the line of each key. `RawConfig::set` states one setting over the text, as `lablet run --set run.max_turns=5` does, and `RawConfig::config` reads the tree into a `Config`.
- `${VAR}` in a setting that holds text is replaced by what the variable holds when a config is checked or a `Lablet` is built, and an unset variable is a config error. `$${` is the text `${`.
- `lablet::telemetry_on_stderr`, which says whether a `Lablet` built from a config writes its telemetry to standard error, as `build` decides it once `${VAR}` is substituted, for a caller that has to know before the build.
- `lablet::check`, which checks a config as `build` does and stops before the provider is selected, so a config whose provider has no adapter yet passes it. What it returns holds the resolved config and the tools a run is offered, which `Lablet::tools` also lists.
- `CancelHandle`, which a library caller gives a run with `RunRequest::cancellation` and fires to stop it.
- `ErrorClass` and `BuildError::class`, which say whether a failure takes the prefix `config:`, `mcp:` or `provider:`.
- `Config::with_prompt_file` names the file a run's task prompt is read from, and the root of the built-in tools may not hold it, as it may not hold the system prompt's file.
- Project scaffold: the `lablet/` Cargo workspace with an empty crate for every ring of the architecture, the root `xtask` gate crate (`lint-layers`, `lint-manifests`, `fmt`, `clippy`, `deny`, `doc`, `test`, `coverage`, `mutants`, `changelog`, `pre-commit`, `pre-push`, `ci`), the pinned Rust toolchain and `mise.toml` gate tools, `scripts/setup.sh` and the git hooks, the `cargo deny` policy, and the GitHub Actions workflow.
- Telemetry contract plumbing: the Weaver registry under `lablet/telemetry/registry/` with its justification policy, the core and GenAI semantic conventions and the shared Weaver policies and templates vendored under `lablet/telemetry/deps/` at pinned commits, `cargo xtask weaver check` in the pre-commit gate, and `cargo xtask weaver vendor [--check]`.
- Telemetry contract: the registry declares the `lablet.invoke_agent`, `lablet.chat`, and `lablet.execute_tool` spans, the `lablet.run` wide event, the `lablet.retry` span event, the `gen_ai.client.operation.exception` and `gen_ai.client.inference.operation.details` log records, and every `lablet.*` attribute with its justification. `cargo xtask weaver generate` renders the `lablet-telemetry-registry` crate and the reference under `lablet/docs/telemetry/` from it, and `cargo xtask weaver generate --check` holds them to the registry in the pre-commit gate.
- Domain model: the `lablet-model` crate holds the conversation, tool, usage, stop reason, run identity, transcript, and run summary types. The outcome JSON is now fixed by `lablet/tests/fixtures/outcome.json`: `duration_ms` is a whole number of milliseconds, `result.structured` and `error` are always present and `null` when there is nothing to report, and `usage.input_tokens` includes the cached tokens.
- Domain policy: the `lablet-policy` crate decides when a run stops, how long a failed provider call waits before its next attempt, and what a run's tokens cost. A limit stops the run when it's reached, not when it's passed: `max_turns: 2` stops after the tool phase of turn 2, and the timeout, the token budget, and the cap on consecutive invalid turns stop the run on the value that equals them. `run.max_retries` counts the retries of one provider call, so `3` allows four attempts and `0` never retries. Cost prices cached tokens once, at the cache rates, and only the rest of `input_tokens` at the input rate.
- Refusals and truncation: a response the model refused, or that a content filter withheld, stops the run with the new stop reason `refused`. A response cut off at `max_tokens` stops the run with `output_truncated` whether or not it called tools, and none of its tool calls runs. One cut off at the context window stops it with `context_exhausted`.
- Telemetry contract: `lablet.run.stop_reason` gains the member `refused`. The `lablet.run` wide event gains `server.address` and `server.port`, present when the provider is reached over the network, and `lablet.tool_calls.unknown`, the calls to a tool name the run didn't offer; such a call counts in the totals and gets no `lablet.tool.*.<name>` key, so those keys stay bounded by what the tool executor resolves, which is the set it offered when the run was built. `lablet.provider.retries` now counts the attempts made beyond the first of a call, so a run whose only provider call fails reports none. On the `lablet.execute_tool` span, `gen_ai.tool.type` and `lablet.tool.source` are required only for a tool the run offered. `gen_ai.request.reasoning.level` follows `model.effort`, and the note of `lablet.request.bytes` says what's measured.
- Tool output cap: `tools.max_output_bytes` (`null` for no cap) cuts a tool's output at a character boundary before the model sees it and adds one line that says what was cut, for every tool alike.
- Transcript: the transcript document is now `system` and `turns`. Each turn holds its input, which is the task prompt for the first turn, the model's response, a record of the provider call behind it (usage, finish reason, start offset, latency, attempts), and the outcome of each tool call it made: a status that says whether a tool ran and, when one did, where it came from and how it ended, with the start offset, latency, truncation, and the content the model was sent.
- Telemetry contract: the `lablet.execute_tool` span gains `lablet.tool.output.truncated` and, when the output was cut, `lablet.tool.output.original_bytes`; `lablet.tool.output.bytes` is the size the model was sent. Its `error.type` is `tool_error`, `unknown`, `timeout`, or `failed`, present whenever the model was sent an error result. The `lablet.run` wide event gains `lablet.tool_calls.truncated`.

- Reasoning tokens: `usage.reasoning_output_tokens` joins the outcome document and `gen_ai.usage.reasoning.output_tokens` the wide event and each chat span. Both providers report the number and both bill it at the output rate, so it's a part of `output_tokens` rather than an addition to it, exactly as the cache counts are parts of `input_tokens`. An adapter builds a `Usage` from a named `TokenCounts` rather than five positional numbers.
- Pricing on the wide event: the four rates a run was priced at are emitted beside `lablet.run.cost_usd` as `lablet.pricing.*_usd_per_mtok`, so a consumer can recompute the cost rather than trust it. A run whose provider reported cache counts above its own input count is priced for its cached tokens alone, and the rates are what let a consumer see that. Reasoning needs no rate of its own.
- Request settings on the wide event: `gen_ai.request.temperature` joins it, having been on the chat span alone, and the new `lablet.request.thinking` carries the thinking mode, its budget, and whether the reasoning text was asked for. A reasoning budget is the setting a run is most often varied by, and neither it nor the temperature reached the one row an analyst reads.

- Tool arguments that aren't valid JSON: the call is kept with the model's own text, runs nowhere, and its outcome is the new `lablet.tool.status` member `malformed_input`, an error result the model can correct from. It counts in the tool statistics rather than as a retried provider error, because a model that can't serialise against an awkward tool schema is a tool-surface problem and reporting it as provider flakiness points at the wrong component. A `ToolUse` input is now written `{"json": {...}}` or `{"unparsed": "..."}`.
- Run labels: the outcome document gains `labels`, which holds the `task`, the `experiment`, and the `trial` that the run request named, each a string, or `null` when the request named none. They're what a composer groups runs by, and the document echoes them so a composer doesn't have to keep a table of run ids. A label the document doesn't know is refused when it's read.
- Transcript writer: the `lablet-transcript-json` crate writes a transcript document as compact JSON to the file a run is given. The path may hold `{run_id}`, which is replaced by the run's id wherever it appears, so two runs write two files. A run id that isn't one component of a path is refused for such a path, so an id that holds a `/` or a NUL, or that's `.` or `..`, can't move the transcript out of the directory the path names. The directories the path is missing are made, so a path may hold the run id as a directory. A transcript is written whole or not at all: it's written to a temporary file beside the path, which is synced and then takes the path's place with the permissions of the file it replaces, so a write that fails leaves what the path held. A path that can't be written is an error that names the path and the reason.
- Telemetry contract: the registry declares what the design review of 2026-09-28 added, each `lablet.*` attribute with its justification. On every span and every log record, beside the join keys: `lablet.task.id`, `lablet.experiment.id`, and `lablet.trial`, each present when the run request named it. On the `lablet.chat` span: `lablet.chat.purpose`, whose one value is `turn`, so a consumer that counts chat spans as turns stays right when lablet makes a provider call that isn't one. On the `lablet.run` wide event: `lablet.tools.digest`, `lablet.prompt.system_digest`, and `lablet.prompt.tools_bytes`, which say what the model was shown; `lablet.request.api`, `lablet.request.reasoning_replayed`, and `lablet.request.cache_scope`, which say how it was reached; `lablet.mcp.server_versions` and `lablet.mcp.lifetime`, present when the run has MCP servers; `lablet.provider.failed.input_tokens`, `lablet.provider.failed.output_tokens`, `lablet.provider.failed.cache_read.input_tokens`, and `lablet.provider.failed.cache_write.input_tokens`, present when a failed attempt reported them; and `lablet.telemetry.dropped_records`, the count of the run's spans and log records that the exporters lost. On the `gen_ai.client.inference.operation.details` record: `gen_ai.tool.definitions`, the tool specs as the run offered them.
- Telemetry: the `lablet-telemetry-otel` crate maps a run's events to the spans and log records the registry declares, and exports them as OTLP/JSON lines to a file for each run named `lablet-<run_id>.otlp.jsonl`, to one file that every run is appended to, or to standard error. Each line is one export, the JSON form of the request a collector would have been sent, so a file can be replayed into a collector. Every attempt of a provider call has a `chat` span, a failed one included, and every span starts and lasts as the loop measured, on the run's clock. Captured content is a JSON string in the form the GenAI conventions give its attribute, and a text longer than 1 MiB is cut there. A span or a log record that a full queue turned away, or whose export failed, is counted. The wide event is made when the observer is flushed after the run, once everything else of the run has been exported, and goes in an export of its own, so it's the last line of its run and its count is whole. A destination that can't be written changes nothing about the run. Each run opens the file it writes to, so a file that was moved after a run holds that run, and its path holds the next. A line that follows one that a failed write left in part begins on a line of its own, so it's read whole.
- Telemetry: shutting the observer down waits five seconds in all, where it waited up to five seconds for each of its queues in turn, so a stuck exporter held it for fifteen. The bound can be set on the builder with `shutdown_timeout`. A shutdown that reaches it returns and says so, and what was still being exported is left to finish on its own, since nothing can take it back.
- Telemetry: the `lablet.run` wide event holds every attribute the registry declares for it, from the run's context and its summary. An attribute whose condition doesn't hold of a run is left out, and never written as a zero or as an empty text: the turn cap of a run without one, the cost and the rates of a run that isn't priced, the labels a request didn't name, the MCP attributes of a run without servers, and a count no provider call reported. A total of nothing is written as `0`. A tool has its `lablet.tool.calls.<name>`, `lablet.tool.errors.<name>`, and `lablet.tool.latency_ms.<name>` when the run offered it and called it, so the names in `lablet.tools.names` bound those keys. `lablet.request.thinking` is written `provider_default`, `adaptive`, `disabled`, or `budget:` and the tokens of the budget, as `budget:2048`. `lablet.result.text` and `lablet.result.structured` are there only when the run captures content. The registry crate has the keys of the wide event as an enum, and the observer fills them in one match over it, so a key added to the registry doesn't build until the observer says what it holds.
- Conformance: `lablet-conformance` has the cases every observer is held to. A run has exactly one wide event, whatever its stop reason. The token counts of the wide event are the ones the run returned. The numbers of the wide event are the sums of what the spans say of each step, with a latency within 5 ms of how long its spans lasted. A destination that can't be written changes nothing about what the run returns.
- What the record names: a run's summary holds the SHA-256 of the system prompt the run sent and of the tool specs it offered, with the size of the specs. Two variants that differ in a tool's description or in the text of a prompt have the same config, and now differ in the record. The specs are hashed as compact JSON, in the order they're offered, and the loop takes both digests from what it sends. The summary also names the API the provider is reached through, whether reasoning is sent back on later calls, and the cache scope. With the cache scope `run`, every provider request carries the run id as a cache key, which is no part of the system prompt, its size, or its digest. A run's context gains the run's labels, which the loop copies to the outcome, the time the run started, and the lifetime and the versions of its MCP servers.
- Scripted provider: the `lablet-provider-fake` crate plays a script in place of a model, so a run needs no key. A script is a list of entries in YAML or JSON, and each entry answers one attempt of a provider call. An entry is a `response`, with its content blocks, its finish reason, its usage, and how long it takes, or an `error` of any kind a provider call fails with, with its message, the usage the failed attempt reported, and the wait the server asked for. A script is checked when it's read and not while it's played: a key it doesn't know, a key written twice, a missing key, and a value a run would refuse are each an error that names the entry and the block, and never a default. An attempt whose entry takes as long as its deadline or longer fails as `retryable` once the deadline is reached. An attempt made after the last entry fails as `fatal`, so the run ends with `provider_error` and an `error` that names the script and says what to add.
- Built-in tools: the `lablet-tools-builtin` crate serves `bash`, `read_file`, and `write_file`, and an executor serves only the ones it's built with, which is none by default. `bash` runs each command as `bash -c` in a new process, which starts in the root and leads a process group of its own, so no working directory and no variable carries from one command to the next. A command starts with lablet's environment, less the variables lablet reads its own secrets from, and with what the settings add on top, which may name a withheld variable to pass it on. A command can still find a secret another way, in a file or in lablet's environment through the process table, so the value of each of lablet's secrets is cut out of every result before the output is kept, and `[secret withheld]` stands in its place. A value that two pieces of a command's output split is cut whole, and only a value of at least 16 bytes is cut. The result is what the command wrote, standard output and standard error in the order they were written, then one line with the exit code, as `exit code: 3`, which the model is sent whatever the output cap leaves out of what the command wrote. A command that exits with a code other than 0 is a result and not an error. At the shorter of the call's deadline and the executor's timeout the whole process group is killed, and the call returns `timeout` once the group has gone. A process that left the group, as one started with `setsid` does, is beyond the kill. A call returns `failed` when `bash` can't be started, and when a group that was killed is still in the process table five seconds later, which happens where lablet is the first process of a container that has no init. `read_file` returns the text of a file, or the lines that `offset` and `limit` choose. `write_file` makes a file, with the directories that are missing on the way to it, or replaces what it held. A path is resolved under the root after symbolic links are followed. One that leads outside the root is an error result, and so is a symbolic link whose target doesn't exist, a file that can't be read, and anything that isn't a file. Arguments that don't fit a tool's schema are an error result that says what's wrong with them. Every tool feeds its text to the call's `KeptOutput` as the text arrives: of 1 MiB that a command writes, an executor that's told to keep 4 bytes of each end holds 8, and it reports the size of all of it.
- Conformance: `lablet-conformance` has the cases every tool executor is held to. A call that runs past its deadline returns `timeout`, no sooner than the deadline and only once the work it started has stopped. An executor keeps of a call's text what the call says to keep, which is the text's own start and its own end, and reports the size of all of it, and it keeps everything of a call that says nothing. Calls to a tool that may run beside other calls are each answered with their own answer when they're made together. A name the executor doesn't offer is `unknown`.
- The library: the `lablet` crate builds a `Lablet` from a config and runs it. `Config::from_str` and `Config::from_path` read a config from YAML or JSON, `build` makes the `Lablet`, and `Lablet::run` takes a `RunRequest` and returns the finished run, whose summary holds the outcome. A request holds the task prompt, which may not be blank, and may name a run id and the run's labels. A `Lablet` runs many times, one run at a time. Each run has the id its request names or a fresh ULID, a start time of its own, and the script of a `fake` model from its first entry. When `run` returns, the run's transcript is written, where `run.transcript_path` names a place for it, and the run's telemetry is in its file, with the wide event as the run's last line. A transcript or telemetry that can't be written is reported on the diagnostic log and changes nothing about the outcome. `Lablet::shutdown` flushes the telemetry and stops its exporters. `build_observed` takes observers of the caller's own, which hear every event of every run after lablet's telemetry has.
- Config: the library reads every setting of the config with its default. A key the config doesn't know is an error, in every section, and so is a key written twice. A duration is text in humantime syntax, as `500ms` and `10m` are. `null` turns off a cap that has a default, as `run.max_consecutive_invalid_turns: null` does. `build` checks a config whole before it selects an adapter, and each refusal names the key and the value: a backoff that starts above its cap, a jitter that isn't a share, a thinking budget that isn't below `model.max_tokens`, a rate that isn't a price, a preview longer than the output cap, a config that states both `prompt.system` and `prompt.system_file` or neither, a `fake` model without `model.script`, and a name in `tools.allow` or `tools.deny` that no tool name could be. `tools.allow: []` is refused, because a list that names no tool would offer none and the loop reads an empty list as every tool. A setting that the config states and the selected provider can't apply is refused by name with the provider, as `model.seed` is with `anthropic` and `model.base_url` with `fake`. With `anthropic`, the variable `model.api_key_env` names has to be set. A `model.api_key_env` that isn't the name of a variable is refused without showing what the config holds there, since a key may have been written in the name's place.
- Config digest: `Config::digest` is the SHA-256, in lower-case hex, of the resolved config as compact JSON with the keys of every object in order. `Config::resolved` is the config with every default filled in and without the defaults the selected provider can't apply. The digest leaves out `run.transcript_path`, `run.transcript_format`, and the `telemetry` section, so two runs that differ only in where they write share a digest. A default that's spelled out, a duration that's written another way, and the order a config lists its keys or its built-in tools in don't change the digest. Neither does the order of `tools.allow` or `tools.deny`, or a name that's in one twice, since each is resolved as a set. `tools.output_preview_bytes` is resolved only under `output_cut: preview`, and `model.base_url` only for a provider that's served somewhere.
- Build refusals: `build` refuses a built-in tool without `tools.builtin.root`, a root that isn't a directory, and a root that holds the config's file, the file `prompt.system_file` names, the transcript, or the telemetry file, with symbolic links followed. It refuses a name in `tools.allow` or `tools.deny` that no tool of the run has, and names the list. In explicit mode that includes `task_complete`, which the lists don't apply to. It refuses a script that can't be read or played, by `model.script` and the script's path.
- What a later version adds: a config may state `model.provider: anthropic` or `openai`, a server in `tools.mcp`, `telemetry.otlp.endpoint`, a skill in `prompt.skills`, `run.context: mask`, `run.transcript_format: atif`, `run.completion_schema`, and a `tools.max_description_chars` other than its default. Each is read and checked as config, and `build` answers `BuildError::Unsupported`, which names the setting and the build-plan phase that delivers it.
- A run id can be made from a ULID's value, which is how the library makes a fresh one, and a task that was checked can be put under another system prompt, so neither step has an error no caller could meet.
- The `lablet` binary: `lablet init [--provider anthropic|openai|fake] [dir]` writes a starter config into a directory, `.` by default, with a script beside it for `fake`, and writes over nothing. `lablet run --config <file>` takes the task prompt from `--prompt`, from `--prompt-file`, or from standard input, and a blank one is a `config:` error. `--run-id`, `--task`, `--experiment`, and `--trial` name the run as a run request does. It prints the outcome document on standard output as one line, and ends with one summary line on standard error, such as `completed: 2 turns, 342 tokens, 1 tool call, 1.2s`, which `--quiet` and a telemetry file path of `-` leave out. A run that completed exits 0, one that stopped any other way exits 2, and one that never started exits 1, as arguments the command line refuses do. The diagnostic log is on standard error, filtered by `RUST_LOG` and showing warnings when it's unset, and it's off when the telemetry is on standard error unless `RUST_LOG` asks for it. On Linux the process clears its `PR_SET_DUMPABLE` flag before anything else, so no other process of its user can read its environment through `/proc`. Ctrl-C and `SIGTERM` stop a run as a fired `CancelHandle` does, so it still prints its outcome, writes its transcript and its wide event, and exits 2. A run that the provider's error ended also prints `provider:` and the error on standard error. `lablet check --config <file>` checks a config as `lablet::check` does and lists the tools a run is offered, a line each, or with `--resolved` prints the resolved config as YAML, and ends with a line such as `passed: 2 tools`; a config it refuses exits 1 with the refusal as a `config:` message. `--set key=value`, on `run` and `check`, states a setting over the config's. `lablet schema` prints the config's JSON Schema, as `lablet/schema.json` holds it. A reader that closes its end early, as `head` does, is told on standard error, and the exit code stays what the command's work says.

### Removed

- Telemetry contract: `lablet.provider.calls` leaves the `lablet.run` wide event and the registry. `lablet.run.turns` counts the model responses a run received, which is the same number on every row, and chat spans now number `lablet.run.turns` plus `lablet.provider.retries`, plus one when the run ended on a failed provider call.
