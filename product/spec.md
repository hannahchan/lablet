# Lablet specification

Status: draft for build. Companion to [brief.md](brief.md), [quality-bar.md](quality-bar.md), [build-plan.md](build-plan.md), and [acceptance.md](acceptance.md).

This document describes what lablet will be, and the code reaches it phase by phase. The status table in the build plan says which phases are done. §1, §3, §4 and §5 describe the domain and the loop as phase 4 left them. §6 and §7 describe the adapters and the composition root that phases 4 to 10 build: what phase 4 built is described as it's built, and the rest is ahead of the code.

## 1. What a run is

A run takes a config and a task prompt and executes one agent loop:

```
transcript = (system, turns: []);  input = prompt
loop:
    if cancelled or stop policy says stop (timeout, tokens): break          # point A
    response = provider.complete(system, messages(transcript, input), tool specs)   # retried per call on transient error; point A is asked again before each retry; cancellation drops the attempt, or the wait before a retry, and stops the run
    transcript.turns += turn(input, response);  input = nothing             # the input it answers, the response, and the record of its provider call
    if stop policy says stop (refused, output_truncated, context_exhausted, completed, ended_without_completion): break   # point R; a task_complete call made on its own is recorded here, never executed
    if the run has no time left: break                                       # timeout; no tool starts, and the turn's calls stay unanswered
    for each group of the response's tool_use blocks, in call order:       # consecutive shared calls are one group, run concurrently; an exclusive call is a group of its own
        run the group's calls                                               # errors become error results; output over the cap is cut; a call whose turn comes when the run's time has gone, or once it's cancelled, is never run; cancellation stops the calls in flight
    the turn's tool_calls = one outcome for each call, in call order        # rendered as ONE message of results
    if cancelled or stop policy says stop (invalid turns, turn cap, timeout, tokens): break   # point B
emit outcome
```

A turn is one model response with what prompted it and what came of it: the input the user supplied, the record of the provider call that produced the response, and the outcome of each tool call it made. The first turn's input is the task prompt; a later turn follows a tool phase and has none. The flat list a provider call sends is rendered from the turns: before each response comes one user message holding the results of the previous turn's tool calls and then the turn's input. The loop never assembles a message.

A turn's tool calls run in groups, in call order. Consecutive calls to tools marked `shared` form one group, which runs concurrently, at most `tools.max_concurrent_calls` at a time; a call to an `exclusive` tool is a group of its own. So a read the model placed after a write still runs after it. Outcomes are recorded in call order whichever call finished first, so the order of the transcript's outcomes and of the results the model is sent doesn't depend on timing, though each outcome's start and latency do (§5).

The stop policy is evaluated at three points: before each provider call (point A), after each provider response and before any tool runs (point R), and after each tool phase (point B). Between point R and the tool phase it's asked one thing more, whether the run has any time left. Cancellation, the run timeout, and the token budget are checked at A and B, and at A again before each retry of a provider call, since a retry is a provider call; the turn cap, when there is one, and the cap on invalid turns at point B only. Cancellation is asked once more when each tool call's turn comes, and it doesn't wait for a point to be asked: it stops a provider call or a tool call in flight (below). A run therefore never makes a provider call after the condition that should have stopped it. Point R reads only the response, so a response that finishes the task completes the run even when it also used up the timeout or the token budget. It reads the finish reason before the tool calls: a response the model refused, or one that was cut short, stops the run there and none of its tool calls runs.

When several conditions hold at one point, the first in this order is the stop reason, so one state always gives one reason:

| Point | Order                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| ----- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| A     | `cancelled`, `timeout`, `max_total_tokens`                                                                                                                                                                                                                                                                                                                                                                                                 |
| R     | finish reason `refusal`: `refused`. Finish reason `max_tokens`: `output_truncated`. Finish reason `context_window`: `context_exhausted`. All three hold whatever the response called, in both modes. Otherwise explicit mode and `task_complete` called on its own with arguments that parse: `completed`. Otherwise any tool call: the run goes on. Otherwise `completed` in natural mode and `ended_without_completion` in explicit mode |
| B     | `cancelled`, `invalid_calls_exhausted`, `max_turns`, `timeout`, `max_total_tokens`                                                                                                                                                                                                                                                                                                                                                         |

Cancellation leads because the loop polls its port before it asks the policy, which doesn't see cancellation at all. The cap on invalid turns comes next at B because it alone says the run was failing, not merely long. At R the finish reason leads because a response cut off at `max_tokens` or at the context window can end inside a tool call's arguments, and a cut-off input can still parse as a valid, smaller one. So a truncated response never has its tool calls executed, and a `task_complete` call in one doesn't complete the run. A finish reason lablet doesn't know (`FinishReason::Other`) is read as a normal end: from an OpenAI-compatible server that's the usual case, and the wide event carries every finish reason for whoever needs to tell.

Every limit is met when the run reaches it, not when it passes it. With `max_turns` 2 the run stops after the tool phase of turn 2, having made two provider calls; a response on turn 2 that finishes the task still completes the run, because point R comes first. The run stops with `timeout` once the elapsed time equals `run.timeout`, with `max_total_tokens` once input plus output tokens equal the budget, and with `invalid_calls_exhausted` after the third invalid turn in a row when the cap is 3.

An invalid call is one the model got wrong, so the loop answered it without a tool: its name is one no tool has, its arguments didn't parse, or it was a `task_complete` call the loop rejected. An invalid turn is one whose calls were all invalid calls. A call that was never run isn't an invalid call, so a turn the run's timeout cut short is never an invalid turn. The cap counts invalid turns in a row. The count is read at point B, once every call of the turn has its outcome. So the order of a turn's calls never decides it, and one response can't reach the cap alone, before the model has been told of its mistake once. Any other turn that made calls ends the count: one in which a call reached a tool, whatever the tool returned. So an error result, a timeout or a dead server never ends a run: no reference loop ends one for them, and how a model recovers from a failing tool is part of what a run measures. A model that can only produce invalid calls is a run that has failed, and the references that stop for it count responses, as this does. `run.max_consecutive_invalid_turns` is 3 by default and `null` turns the cap off.

When point R lets a run go on and the run has no time left, the tool phase doesn't start: the run stops with `timeout`, and the turn's calls stay unanswered. When the time runs out inside a tool phase, every call whose turn comes later is answered `not_run` by the loop, which starts nothing for it, and point B stops the run with `timeout`, unless a reason ahead of it in the order holds. `run.max_turns` is `null` by default, which is no cap, as in the primary reference: the run timeout and the token budget bound a run.

`run.max_total_tokens` counts tokens, not money: the input plus output tokens of every provider call, summed, a failed attempt's among them when the provider reported them. A token read from the cache counts whole. Each call sends the whole conversation again, so context that's re-sent counts on every turn. A ten-turn run whose context grows evenly to 20,000 tokens counts about 110,000 input tokens (2,000 + 4,000 + ... + 20,000), not 20,000, so it reaches a budget of 100,000 on its tenth call.

Every provider call, tool call, retry, and stop decision is reported to an observer, which is how telemetry leaves the process.

### ProviderResponse modes

| Mode                | Completes when                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        | Ends without completing when                                                         |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| `natural` (default) | The model returns a turn with no tool calls whose finish reason isn't `refusal`, `max_tokens`, or `context_window`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   | Never. Other stop reasons still apply.                                               |
| `explicit`          | The model calls the built-in `task_complete` tool on its own, with arguments that parse, in a response with none of those three finish reasons. The call is intercepted by the loop, never executed, not counted in `tool_calls`, and its JSON argument is the run's structured result. A `task_complete` call whose arguments don't parse completes nothing: it's answered as `malformed_input`, like any call with bad arguments. One whose arguments parse, in a response that makes any other call, completes nothing either: the other calls run, and it's answered as `rejected`, with text that asks for it on its own once they've returned, so a run never reports work as done that was only asked for. The other call may be a second `task_complete`, and then both are rejected. From phase 10 an argument that doesn't fit `run.completion_schema` is rejected too, with text that says what didn't fit; the check reads five keywords of the schema: `type`, `required`, `properties`, `items` and `enum`. Every one of these is an invalid call, and the run goes on. | The model returns a turn with no tool calls. Stop reason `ended_without_completion`. |

### Stop reasons

`completed`, `ended_without_completion`, `max_turns`, `timeout`, `max_total_tokens`, `output_truncated` (finish reason `max_tokens`; the response's tool calls, if any, aren't executed), `context_exhausted` (the provider rejected the request as too long, or cut the response short at the context window), `retries_exhausted`, `invalid_calls_exhausted` (`run.max_consecutive_invalid_turns` turns in a row made no call that reached a tool), `cancelled`, `provider_error` (any other error that isn't retried, a rejected key among them), `refused` (the model declined to answer or a content filter withheld the response; a refusal is never a completed run).

### Retries

- **Provider errors** are classified by the adapter as retryable (transport failure, rate limit, 5xx, overloaded, per-call timeout), context exhausted (the provider's context-length error), auth (the provider rejected the credentials), or fatal (bad request, unknown model). Retryable errors are retried with exponential backoff up to `run.max_retries` times **per provider call**; the counter resets on success. `max_retries` counts retries, not attempts: `3` allows four attempts, and `0` never retries. `RetryPolicy` takes the same number. Attempts are numbered from 1, as `lablet.attempt` reports them. When attempt `n` fails and `n` is at most `run.max_retries`, the loop waits and tries again; otherwise the run stops with `retries_exhausted`. So with `max_retries: 3`, two failures and a success is a completed call with two retries, and four failures exhaust it. After a failed attempt that could be retried the loop asks point A before it asks for a retry, so an attempt that used up the run's time or its token budget ends the run with `timeout` or `max_total_tokens`, whether or not a retry is left. Before each wait the loop asks `StopPolicy::allows_wait`, so backoff can't carry a run far past the run timeout: if the elapsed time plus the wait reaches `run.timeout`, the run stops with `timeout` instead of sleeping. The backoff after attempt `n` is `base * factor^(n - 1)` capped at `max`; `base` and `max` come from `run.retry_backoff_base` and `run.retry_backoff_max`, and `factor` is 2. When the server said how long to wait, the wait is the longer of that and the backoff, and a hint longer than `run.retry_hint_max` ends the retries with `retries_exhausted`: the server has asked for a wait lablet won't make. Jitter of up to `run.retry_jitter` of the wait is added to it, whichever of the two it came from, because lablets that were throttled together would otherwise come back together. The jitter is derived from the run id, the turn and the attempt, so a run's waits are the same every time it's replayed.
- **Malformed provider responses** (the adapter can't map the payload to the domain model, including a tool call whose name or id isn't a valid `ToolName` or `ToolCallId`) count as retryable. A tool call whose arguments aren't valid JSON isn't one of them: the arguments are kept as the model wrote them, the call runs nowhere, and its outcome is `malformed_input`, an error result the model can correct from. Refusing the response instead re-rolls the same prompt against the same schema and reports a tool-surface problem as provider flakiness. That differs from a well-formed name that no tool has, which is an error result for the model. An OpenAI-compatible server that sends an empty or repeated call id gets a synthesised unique one from the adapter, not a `Malformed`.
- **Tool errors** aren't retried by lablet, and never end a run. The error is returned to the model as an error tool result. A call to a tool name that's not in `specs()` is also an error result, and an invalid call: after `run.max_consecutive_invalid_turns` turns in a row that made no other kind, the run stops with `invalid_calls_exhausted` at point B.
- **Tool timeouts** are tool errors. The limit is the executor's: `tools.builtin.timeout` for the built-in tools and `call_timeout` for an MCP server. A call that timed out has stopped by the time its result is recorded (§5).
- **Tool output** longer than `tools.max_output_bytes` is cut by the loop, not by the tool, in the way `tools.output_cut` names. `head` keeps the tool's own text from the start up to the cap and ends it with one line such as `[truncated: the first 50000 of 5242880 bytes]`. `head_tail` keeps half the cap from each end, around one line such as `[truncated: 5192880 of 5242880 bytes left out]`. `preview`, the default, keeps the first `tools.output_preview_bytes` and ends them with one line such as `[output too large: the first 2000 of 5242880 bytes]`, which is what the primary reference sends for a long MCP result. Text is cut at a character boundary. The cap bounds the tool's text, not the result: the line is added on top of it, once per call that was cut. A tool may close its output with one short line about the whole of it, as `bash` does with the exit code, and every cut sends that line last, after the line that says what was left out, so a long output never hides whether a command passed. The closing line, like the line that says what was left out, isn't counted against the cap, so an output whose text fits the cap is sent whole with it. No more than 256 bytes of a closing line are kept. Every tool is cut the same way, an error result included, and a cut result isn't an error.
- **Provider timeouts** (`run.provider_timeout`) are enforced per call by the adapter's HTTP client via the deadline on the request. The run-level `run.timeout` is checked at points A and B, and once more before a tool phase starts, but no call's deadline is later than the run's: a provider call gets the shorter of `run.provider_timeout` and the time the run has left, and a tool call gets the time left, of which its executor takes no more than its own limit. So a run overruns `run.timeout` only by the time a call takes to stop.

### Cancellation

Cancellation is asked at points A and B, before each retry of a provider call, and when each tool call's turn comes, through the `Cancellation` port; the CLI wires it to Ctrl-C and `SIGTERM`. The loop also races each provider call attempt, each wait before a retry and each tool call against the port's `cancelled`, and when the run is cancelled it drops whichever is in flight and stops with `cancelled`. So a run stops in the time its futures take to drop, and nothing waits for a call to return: a `bash` command's process group is killed and not waited for, which keeps the stop inside the grace period a container's stop allows, ten seconds by default. A retry is a provider call, so a run cancelled during a backoff stops waiting and makes no further attempt. An attempt that was dropped answered nothing and reported nothing, and it counts among the run's attempts and in its provider latency as a failed attempt does; its chat span ends when it was dropped, with `error.type` `cancelled`. In a tool phase, a call in flight is stopped and answered `cancelled`, which says it ran, and every call whose turn comes after the run is cancelled is answered `not_run` and starts nothing, so no later group runs and the turn's outcomes still answer every call. The run then writes what every run writes: the outcome, the transcript and the wide event.

### Transcript

When `run.transcript_path` is set, the whole conversation is written there as JSON when the run ends, whatever the stop reason. The path may hold `{run_id}`, so a `Lablet` that runs twice doesn't write its second transcript over its first. The directories the path is missing are made, and the file is written whole or not at all: it's written to a new file beside the path and synced before it takes the path's place, so a write that fails leaves what the path held and a crash leaves one whole transcript or the other. The new file keeps the permissions of the file it replaces. The document is `TranscriptDocument` (§3), rendered by the transcript writer adapter rather than by the model: `schema_version`; then what names the run, which is its id, its labels, the config digest, lablet's version, the model and when the run started; then the tool specs the run offered; then the transcript's `system`, the `task_prompt` the run was given, and the `turns`. The crate `lablet-documents` holds both documents and builds each from the run's values (§3). The version is the document's and not the run's, which is why the document is a type of its own; `TRANSCRIPT_SCHEMA_VERSION` is 1, and it rises when a reader that knows the old form could misread the new one, which dropping a field, renaming one, or changing what one means all do and adding one doesn't. Each turn holds its `input`, which is the task prompt for the first turn and empty after that, since a run takes one prompt (the shape keeps room for a user who speaks again, which the loop doesn't offer yet); the model's `response`; the `record` of the provider call behind it (usage, finish reason, response id and model, when the call started as an offset from the start of the run, how long it took, and how many attempts it needed); and `tool_calls`, the outcome of each tool call the response made (call id, status, which says whether a tool ran and where it came from, start offset, latency, the size before the output cap when it cut, and the content the model was sent). A grader can therefore see a truncated or refused turn, which call failed and how, and where the time went, and the numbers agree with the run's totals because the totals are computed from them. A turn with no outcomes either called no tools or its tools never ran; its response says which. A run that received no response has no turns, so its transcript holds the system prompt and the task prompt and no turn, and it still says what was asked. This is independent of telemetry and `capture_content`; it's what a grader lablet or a composing framework reads.

### Outcome

Written to stdout as one JSON document on one line when the run ends, whatever the stop reason:

```json
{
  "schema_version": 1,
  "run_id": "01J...",
  "labels": { "task": null, "experiment": null, "trial": null },
  "stop_reason": "completed",
  "turns": 7,
  "usage": {
    "input_tokens": 0,
    "output_tokens": 0,
    "reasoning_output_tokens": null,
    "cache_read_tokens": null,
    "cache_write_tokens": null
  },
  "tool_calls": 5,
  "duration_ms": 12345,
  "result": {
    "text": "final assistant text",
    "structured": { "...": "task_complete argument, explicit mode only" }
  },
  "error": null
}
```

`schema_version` is the document's and follows the transcript's rule: it rises when a reader of the old form could misread the new one. `OUTCOME_SCHEMA_VERSION` is 1, and reading an outcome refuses any other. `labels` echoes the task, the experiment and the trial the run request named, each `null` when it named none. `turns` is the number of turns in the transcript, which is the number of model responses the run received, so a run whose first provider call fails has `turns: 0`. `result.text` is the concatenated `Text` blocks of the last turn's response (`Transcript::final_text`), or `""` if there is none. `result.structured` is always present: the `task_complete` argument when the run completed in explicit mode, `null` otherwise, natural mode included. `error` is `null` or a string, and is likewise always present. What the two hold follows from the stop reason. A run that failed (`retries_exhausted`, `provider_error`, `context_exhausted`, `invalid_calls_exhausted`) always has an `error`: the provider's text, or lablet's own sentence when there is none, which names the context window for `context_exhausted`, the cap on invalid turns for `invalid_calls_exhausted`, and a failed provider call otherwise. Every other run has `error: null`, and only a `completed` run has a `result.structured`. A document that breaks these rules is refused when it's read. `duration_ms` is a whole number of milliseconds. The document is `OutcomeDocument`, built from a `RunOutcome` (§3), and `lablet/tests/fixtures/outcome.json` holds one example that a `lablet-documents` test reads, compares with a value built in code, and writes back unchanged. `lablet/tests/fixtures/transcript.json` holds the transcript's, which is built in code and compared byte for byte, since nothing reads one back. `usage` totals are summed over every successful provider call. What a failed attempt reported is kept apart, in the summary and the wide event, and counts toward the token budget and the cost, so a variant that fails more often doesn't look cheaper than it was. `lablet.provider.retries` counts the attempts made beyond the first of a call. A run whose only provider call fails fatally reports zero retries. Chat spans whose `lablet.chat.purpose` is `turn` number `turns + retries`, plus one when the run ended on a failed provider call, an attempt the run was cancelled during among them. `turn` is the only purpose until a later phase adds a provider call that isn't a turn, such as one that summarises the conversation. `input_tokens` **includes** cached tokens, as the GenAI semantic conventions require; `cache_read_tokens` and `cache_write_tokens` are subsets of it, so consumers that want uncached input subtract them. `reasoning_output_tokens` is likewise a part of `output_tokens`, billed at the output rate by both providers. Each of those three is `null` when the provider didn't report it, which isn't the same as zero.

Exit codes: `0` completed, `2` ended with any other stop reason (`refused` included, and `provider_error` when the provider rejected the credentials), `1` the run never started (config error, MCP server failed to start, arguments the command line refuses).

### Wide event

When a run ends, every observer emits exactly one wide event to each of its destinations: a single record carrying everything worth knowing about the run, so an analyst can answer most questions from one row without joining spans. It's emitted after `RunFinished`, whatever the stop reason, and is the last thing the run produces. Its content is `RunContext`, what only the composition root knows, plus `RunSummary`, what the loop knew and measured (§3), flattened to the attribute names below. One attribute is neither: `lablet.telemetry.dropped_records` is the observer's own count (§6).

Naming rule: a GenAI or core semantic-convention attribute is used wherever one exists. A `lablet.*` attribute is added only when the run can't be described without it, and every one carries a one-line justification in the registry. Per-tool values use Weaver `template[int]` attributes, which allow a dynamic suffix only; there are no map-typed attributes. `gen_ai.usage.input_tokens` includes cached tokens and `gen_ai.usage.output_tokens` includes the reasoning tokens, so neither subset is ever added to its total; `run.max_total_tokens` counts `input + output` over every call. A run reports the rates it was priced at beside its cost, because a derived number a consumer can't recompute is a number it has to trust. Extensions considered and deferred are listed in the research catalogue, not here.

The wide event is an OTel log record. Each destination, OTLP over the network and the OTLP/JSON file, gets its own, made when that destination has flushed the run's spans and records, so its `lablet.telemetry.dropped_records` counts what that destination lost (§6). Spans remain the per-step detail; the wide event is the per-run row.

Aggregatability rules: the wide event has a fixed flat shape (no nested maps; template attributes with a bounded key set for per-tool values: a key exists only for a call the tool executor resolved to a tool it serves, and a call to a name it can't resolve, which the model is free to invent, counts in the totals and in `lablet.tool_calls.unknown`. What bounds the key set is the executor's own tool set, which §5 makes the port's contract; `lablet.tools.names` is the same set, reported separately); the join keys `gen_ai.conversation.id`, `session.id`, and `lablet.config.digest`, and the run's labels when it has them, appear on the wide event, on every span, and on every other log record so any consumer can group by them without a join; the three labels are declared in the registry because a run is grouped by its task, its experiment and its trial more than by anything else, and every other composer-supplied `telemetry.resource` attribute lives on the OTel Resource only, which travels with every export batch as OTLP defines, because their keys are chosen by the composer and can't be declared in the registry, and live-check reports undeclared span attributes as violations; only raw counts, bytes, tokens, and durations are emitted, never ratios or averages, since those belong to the aggregation.

## 2. Architecture

Explicit architecture, in the shape of the UsefulBytes repository, sized down. Rings are directory prefixes inside the `lablet/` workspace; directory `foo/bar/` is package `lablet-bar`, with three exceptions: `apps/lablet` is `lablet`, `tests/conformance` is `lablet-conformance`, and `tests/mcp-server` is `lablet-test-mcp-server`.

```
lablet/
  crates/domain/model            one module per idea: id, message, tool, usage, price, provider, transcript, run, stop, outcome, summary
  crates/domain/policy           pure stop and retry decisions, pricing
  crates/application/run         RunService (the loop) and its secondary ports
  crates/adapters/secondary/
    provider-anthropic           ModelProvider over the Anthropic Messages API
    provider-openai              ModelProvider over OpenAI's Responses API and OpenAI-compatible chat completions (Ollama, vLLM, gateways)
    provider-fake                ModelProvider that plays scripted responses; a product feature, not test scaffolding
    tools-builtin                ToolExecutor for bash, read_file, write_file (task_complete lives in the loop)
    tools-mcp                    ToolExecutor over rmcp (stdio and streamable HTTP clients)
    telemetry-otel               RunObserver mapping events to OTel spans and logs once, with pluggable exporters: OTLP network, OTLP/JSON file
    transcript-json              writes the transcript document to a file; no port, since the composition root does the write
    shared/telemetry-registry    generated from the Weaver registry: attribute name constants and enums
    shared/documents             the transcript and outcome documents and the shapes the fake provider's script shares with them
  apps/lablet                    composition root: config, build(), CLI. Library and binary.
  telemetry/                     Weaver registry (YAML), vendored upstream registries, policies, templates
  tests/conformance              package lablet-conformance: shared ToolExecutor and RunObserver cases
  tests/mcp-server               package lablet-test-mcp-server: a tiny rmcp stdio server for tests
  tests/test-support             package lablet-test-support: the scratch directory, clock, cancellation and run builder the adapters' tests share
  xtask/                         (repo root, not a member) lint-layers, gates
```

Dependency direction, enforced by `cargo xtask lint-layers` (a workspace crate is placed by its path, an external crate is matched by name; dev-dependencies aren't held to the ring rules):

| Ring                                | May depend on                                                                          | May not use                                                                 |
| ----------------------------------- | -------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| domain                              | domain                                                                                 | tokio, reqwest, tracing, opentelemetry, rmcp, tonic, axum, hyper            |
| application                         | domain                                                                                 | tokio, reqwest, opentelemetry, rmcp, tonic, axum, hyper (`tracing` allowed) |
| adapters and adapter shared kernels | application, domain, and the shared kernels of their own ring; never a sibling adapter | (no restriction)                                                            |
| composition root                    | everything except test support                                                         | (no restriction)                                                            |
| test support (`tests/*`)            | anything                                                                               | (no restriction)                                                            |

A listed name forbids its whole family: a crate matches when any `-` or `_` separated part of its name equals the listed name, so `opentelemetry` also forbids `opentelemetry_sdk` and `opentelemetry-otlp`. Every dependency of a member is inherited from `[workspace.dependencies]` (`lint-manifests` allows nothing else), so that table is where a rename (`package = "..."`) is resolved to the real crate name and where a workspace crate's path places it in a ring; a dependency that can't be read from it's an error, not a pass. Target-specific tables are walked. No crate outside `tests/` may list a `tests/` crate in `[dependencies]` or `[build-dependencies]`. A workspace member that falls in no ring is an error.

`serde` and `serde_json` are allowed in every ring, and what each ring does with them differs. The domain and the application are in-memory models: `serde_json::Value` is there because a tool's arguments are JSON by definition, and the domain derives `Serialize` only on what the loop measures with, the messages and the tool specs whose compact JSON it counts and hashes. No domain type has a published form. The documents lablet writes and the script the fake provider reads are types of `lablet-documents`, a shared kernel of the adapter ring, and a provider's wire format is a type of its own adapter.

There are no primary adapters. The composition root calls `RunService` directly, which is also the library surface.

Ports are object-safe `async_trait` traits, `Send + Sync`, injected as `Arc<dyn Trait>` through constructors. Ports live in the application crate that consumes them. Errors are `thiserror` enums owned by the layer that defines the contract; adapters map their own errors into the port's error at the `impl` boundary and never leak their types inward.

Windows isn't supported. Paths, the `bash` tool, and the musl release build assume a Unix host.

## 3. Domain model (`lablet-model`)

Pure types, in memory. `serde_json::Value` is the JSON data currency. A rule about one value or about an aggregate is held by the type: fields are private wherever a rule would otherwise be a convention (identifiers, a provider response's content, the transcript and its turns, an outcome's stop reason, result, and error, a `Cost`, an `UnknownReason`), and a document that's read into such a type is built through the same checked constructor, so the rule is enforced once. A type whose fields are private gives them up by value, through `into_parts`, which is how `lablet-documents` takes one apart by pattern: a field added to the domain is then a compile error in the mapping until it says whether the field is published. The transcript has no read form at all, and the reason is the brief's: lablet emits what it saw and reading one back belongs to the side that consumes it. `Run` keeps its fields private too. Every other field is public.

impl RunId { pub fn ulid(value: u128) -> RunId }   // every ULID is a run id, so whoever generates one has no error path; the value is the caller's to make, since the domain reads no clock and draws no random number
impl RunId { pub fn salt(&self, turn: u32, attempt: u32) -> u64; }   // FNV-1a over the id's bytes and then the two numbers', little-endian: a hash this crate writes out, so a retry's jitter is the same on every toolchain

    pub const CLOSING_MAX_BYTES: usize = 256;
    pub fn close(&mut self, line: &str);                             // a line about the whole output, which every cut sends last; at most CLOSING_MAX_BYTES of it are kept, and a second close replaces the first
    pub fn total_bytes(&self) -> u64; pub fn kept_bytes(&self) -> u64;   // the size of everything fed with the closing line, and of what's held of it
}

    pub fn new(secrets: Arc<Secrets>, keep: Option<OutputKeep>) -> RedactedOutput;
    pub fn push(&mut self, text: &str);                              // what may still begin a value is held back until what follows settles it
    pub fn close(&mut self, line: &str);                             // hands on what was held back, and closes with `line`, cut as a text of its own
    pub fn kept(self) -> KeptOutput;
}

}

`RunContext` holds what only the composition root knows and hands to the loop. `RunSummary` holds what the loop knew and measured: the limits and request parameters it was built with, the model and endpoint its provider reports, and everything it counted. Observers don't reconstruct it, so every observer reports identical numbers. The wide event is the two flattened together. The labels are the run request's, and the composition root fills them in with the rest of `RunContext`, the wall-clock time the run started among it, since the domain reads no clock. The two digests are the loop's. It takes them from the system prompt and the tool specs it sends and hands them to `RunSetup`, with the size of the specs, so no caller of the loop can pair a digest with a prompt it wasn't taken from. `failed_usage` is `None` when no failed attempt reported any. The run id and the labels are in `RunContext` and, through `RunSetup`, in `RunOutcome`; the loop copies both from the one into the other when it starts the run, and an observer reads them from the context. `RunSummary` doesn't repeat what its `outcome` already holds: `gen_ai.usage.*` comes from `outcome.usage`, `lablet.tool_calls.total` from `outcome.tool_calls`, `lablet.run.turns` from `outcome.turns`, `lablet.run.duration_ms` from `outcome.duration_ms`, and `lablet.run.stop_reason` and `lablet.run.error` from `outcome.stop_reason()` and `outcome.error()`. `lablet.tools.count` is the length of `tools`, so no two fields can disagree.

**Transcript.** `Transcript` is the conversation of one run, the loop's working state, and the document a grader or a composer reads. It's made of turns, not messages. A `Turn` is the `input` the user supplied, the model's `response` to it, the `TurnRecord` of the provider call behind the response, and the `ToolCallOutcome` of each tool call it made. So a response can't be without its record, a result can't be without its call, and the roles aren't data that could be wrong. The first turn's input is the task prompt. A run takes one prompt, so every later turn's input is empty today; the shape keeps room for multi-turn user input, which the loop doesn't offer yet. Input is `UserContent`, which is text, so a tool call or a tool result in it isn't representable: results are rendered from outcomes and never stored as input.

`Run::messages()` renders the flat form for the next provider call, borrowing everything. Before each turn's response comes one `User` message that holds the results of the previous turn's tool calls, in call order, and then the turn's input, whichever of the two there are; the last message is the one the next turn will answer, made of the last turn's results and the input that's waiting; a finished run has neither, so its rendered list ends with the assistant. Anthropic accepts both in one user message, results first; an OpenAI-compatible server gets one `tool` message for each result and then a user message for the input. The rendered result's `is_error` is `ToolCallStatus::is_error`, true for every status but a tool that ran and ended `ok`, so the flag can't disagree with the status it comes from. Blocks are stored and rendered verbatim and in order, which Anthropic requires of `Thinking`, `RedactedThinking`, and `Opaque` blocks in the latest assistant turn. `Message` is an enum of the two roles, so `ContentBlock` needs no tool-result variant that a response could misuse.

Four rules remain that the transcript's fields don't hold, and the run's states hold three of them. A run is a `Run` while it waits for a response, and recording one consumes it and returns a `Responded`: `Final` when the response called no tool, and `Pending` when it called at least one. `Final` can only finish. `Pending` can finish, which is how point R stops a run, or be answered, which gives back a `Run`. So no method exists for a sequence the rules forbid, and nothing is left to refuse; `TranscriptError` doesn't exist:

- Something from the user comes before every response: a turn has input, or the turn before it has tool call outcomes. Otherwise two assistant messages would be adjacent, or the conversation would open with one. A `Run` is made in two ways, by `Run::start` with a task that `Prompts::new` has refused to let be blank, and by `Pending::answer` with at least one outcome, so every response has something before it. `Final` offers no way on, which is also what point R decides for a response that calls no tool.
- The tool calls of one response have distinct ids. `ProviderResponse::new` refuses a repeat (`ResponseError::DuplicateToolUse`), which an adapter reports as `Malformed`, and a completion's `content` can't be set any other way.
- A turn's outcomes answer exactly the tool calls of its response, each call id once and in call order, or the turn has no outcomes at all because its tools never ran: the response was cut short or refused, its `task_complete` call was intercepted, or the run was cancelled or reached a limit first. A `task_complete` call that came with other calls isn't intercepted: it has an outcome, `rejected`, like every other call of its turn. `Pending::answer` walks the turn's own calls, awaits one `Answer` for each, and adds each call's id itself, so the loop never holds a list whose length or order could be wrong. `Pending::finish` leaves the turn with no outcomes.
- Only the last turn may have tool calls and no outcomes, whatever input the next turn would bring. A `Pending` that finishes is a run that ends, so an unanswered turn is always the last.

`Pending::answer` is the domain's one function that returns a future. It reads no clock and names no runtime, and the only futures it makes wrap the ones `answer` returns with the id of their call: it runs those in the groups §1 describes, using `schedule` to tell a shared call from an exclusive one. A group is a pool on `futures-util`'s `FuturesUnordered`, so a call starts as soon as any call ahead of it in the group ends, and each answer carries its place so the outcomes are put back in call order. It's in the domain because the thing that collects the answers has to be the thing that knows the calls, or the count could come back short (see `decisions.md`, 2026-09-23). `answer` takes each call by value and returns a plain future rather than being an `AsyncFn` over a borrowed call, because the future of an async closure over a borrow can't be shown `Send` when several are held at once (see `decisions.md`, 2026-09-23).

Whether a turn without outcomes called no tools or its tools never ran is read from whether its response holds tool calls; nothing else records it. The name and input of a call are in the response's `ToolUse` block and nowhere else, and an outcome's sizes are measured rather than stored (`ToolUse::input_bytes`, `ToolCallOutcome::output_bytes`), so nothing is written in two places that could disagree. The one size it stores is `truncated_from_bytes`, what the output measured before the cap cut it, which nothing left can measure.

**Empty text.** When a provider response becomes a turn, `Text` blocks that are empty or only whitespace are dropped from the response, and from the turn's input by the same rule, which is why a prompt of only whitespace is nothing from the user. This is the only way a stored turn differs from what the provider sent and from what the loop was handed. Models do emit such blocks, typically just before a tool call, and Anthropic refuses both kinds when the response is replayed; rejecting the completion instead would mark it `Malformed` and spend a retry on a block that carries nothing. The drop happens once, before anything reads the turn, so `final_text()` and every byte count taken from `Run::messages()` describe what's replayed, and a published document never holds a blank block.

**Time.** The domain reads no clock. The loop passes each offset and latency as a `Duration` measured on its `Clock`, and the model turns it into whole milliseconds in one function, so a total and the values it sums are cut the same way and no observer rounds for itself. A turn's record holds `started_ms`, the offset from the start of the run at which the successful attempt began, its `latency_ms`, and `attempts`, the number of attempts the call took; an outcome holds `started_ms` and `latency_ms` of its tool call. A duration that reaches telemetry as a `*_ms` attribute is a `u64` field named `*_ms` (`duration_ms`, `timeout_ms`, the latency fields). No serialised type holds a `Duration`; `RunSetup`, `Progress`, and the parameters of `Run` and `Answer::measured` do.

**ATIF.** The transcript maps onto an ATIF v1.8 trajectory, so the phase 10 export is a map and not a reconstruction. It doesn't map field for field: the shape is the run's, and what ATIF has no slot for goes in `ObservationResult.extra` and `Metrics.extra`, as the table's `extra` rows say. `system` is the `system` step that opens the trajectory, a turn's input, when it has any, is a step with source `user`, and the rest of the turn is one `agent` step with `llm_call_count` 1:

| ATIF                              | From                                                                                                                                                               |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `Step.message` of the `user` step | the text of the turn's `input`                                                                                                                                     |
| `Step.timestamp`                  | the run's start plus `record.started_ms`                                                                                                                           |
| `Step.model_name`                 | `record.response_model`                                                                                                                                            |
| `Step.message`                    | `Turn::text()`                                                                                                                                                     |
| `Step.reasoning_content`          | the text of the response's `Thinking` blocks                                                                                                                       |
| `Step.tool_calls[]`               | the response's `ToolUse` blocks: `tool_call_id` is `id`, `function_name` is `name`, `arguments` is `input`                                                         |
| `Step.observation.results[]`      | the turn's `tool_calls`, in the same order: `source_call_id` is `call_id`, `content` is the text of `content`                                                      |
| `ObservationResult.extra`         | the outcome's `status`, which holds the source, and its `started_ms`, `latency_ms`, `truncated_from_bytes`: ATIF has no slot for an error, a time, or a truncation |
| `Step.metrics`                    | `prompt_tokens` is `usage.input_tokens`, `completion_tokens` is `usage.output_tokens`, `cached_tokens` is `usage.cache_read_tokens`, a subset in both              |
| `Metrics.extra`                   | `usage.cache_write_tokens`, and the record's `finish`, `response_id`, `latency_ms`, `attempts`                                                                     |

`RedactedThinking` and `Opaque` blocks are replay material for the provider that sent them and have no place in a trajectory.

**Tool calls.** A `ToolCallOutcome` is what happened to one call, and one value feeds the transcript, the totals, and the `execute_tool` span. `status` says in one value whether a tool ran: `Unknown`, no configured tool has the name; `MalformedInput`, the arguments didn't parse; `Rejected`, the loop declined a call it won't act on, which is a `task_complete` call whose arguments parsed and that wasn't the response's only call, and from phase 10 one whose argument doesn't fit the schema; `NotRun`, the call's turn came when the run had no time left, or once the run had been cancelled, so nothing was started for it; or `Ran { source, ended }`, where `ended` is `Ok`; `ToolError`, the tool ran and reported an error, as MCP's `isError` does; `Timeout`; `Failed`, the executor failed; or `Cancelled`, the run was cancelled while the call ran, and the loop stopped it. The first three are the invalid calls of §1, the ones the model got wrong. A call that was never run is in the transcript and nowhere else: it's in no total, and the loop emits no event for it, so it has no span. `as_str` flattens the two levels to the `lablet.tool.status` values, of which every one but `ok` is the span's `error.type` (§5), and `source()` is a source exactly when a tool ran. So "the model called a tool the run doesn't have" is one fact, not a status, a missing source, and a name absent from `RunSetup::tools` that could disagree: `finish` reads the outcome's own status, and the executor, which resolved the name against the run's tools, is the only thing that decides it. The loop builds an `Answer` with `Answer::measured`, and `Pending::answer` turns it into an outcome by adding the id of the call it asked about. `measured` converts the two durations and applies the output cap, so every tool's output is cut the same way. An output no longer than the cap is sent whole. A longer one is cut as `OutputCut` says, at a character boundary, with one line that says what was left out, worded once in the model like the omitted-content line: `Head` sends the start up to the cap, `HeadTail` half the cap from each end, rounded down, and `Preview` its own few bytes of the start (§1). The cap is on a call's text as a whole, its items in order, as it was before there was more than one way to cut.

An executor doesn't hold a whole output to have it cut. It feeds the text to a `KeptOutput` made from the call's `OutputKeep`, which keeps the first `head` bytes, counts everything after them, and holds the last `tail` bytes of what it counted. `OutputCap::keeps` makes `head` the cap whatever the cut, so an output within the cap arrives whole and is sent whole, and `tail` half the cap for `HeadTail`, since a preview and a head need no end. So an executor holds at most one and a half caps plus `CLOSING_MAX_BYTES`, and a command that never stops writing can't take lablet's memory and the run's record with it. `measured` cuts what was kept: the end `HeadTail` sends is the last half-cap of the whole output, which is the kept tail, with the end of the head before it when less than half a cap followed the head. The start keeps the items it was fed as items, and the end is one item whatever items its text came from, so a cut output is its start, the line, its end, and its closing line when the tool gave one. The closing line is held apart from the start and the end, counts in the size of the whole, and isn't counted against the cap or as left out, since it's sent on top of what the cap allows. No cut falls inside a character: a start ends at the last character boundary its bytes allow, and an end begins at the first. `truncated_from_bytes` is the size of the whole output when it was cut, `None` when nothing was cut, and `output_bytes()` is the size the model was sent, the line included, which is why it can exceed what was kept. Capping an output twice therefore cuts it twice; the loop applies the cap once, as each answer is measured. Every other field of an outcome is the answer's, so `ToolCallFinished`, which the loop emits from the answer before handing it over, reports what the transcript holds. The cap is loop configuration (§5), not a model field. An executor that knows lablet's secrets feeds the text through a `RedactedOutput`, which replaces each value with `Secrets::MARKER` before the `KeptOutput` sees it, so the size and the cut count the text the model is sent. It cuts a value that one piece of the text begins and a later one ends as it would the whole text: the end that may begin a value is held back until the text that follows settles it, and that's always less than the longest value. Where two values begin at one place the longer is cut, and copies that overlap are one cut: a value that begins inside a cut stretches it to its own end, so no byte of either copy is shown, and adjacent copies are two cuts. It's in the model because every executor makes the same cut with the same words, and one adapter can't use the code of another.

**The run.** The loop doesn't assemble a `RunSummary` or a `Transcript` by hand. It starts a `Run` from a `RunSetup` and the two prompts, tells it each thing that happens, and `finish` turns it into the `FinishedRun`. It keeps the transcript and, beside it, only what a transcript doesn't hold: the input that waits for the next turn, which is the prompt until the first turn takes it, and what failed provider call attempts cost: their latencies, the usage they reported, and how many the call in progress has had. Every total of the summary is computed from those when the run ends (usage, finish reasons, provider latency, retries, tool counts, bytes, per-tool shares, `result.text`, and the prompt sizes, where the task prompt's is the size of the first turn's input, or of the waiting input when no turn took it), so no quantity is held in two places and a summary always agrees with the transcript beside it. `progress` is computed the same way each time it's asked: a sum over the turns and the failed attempts, and a walk back over the turns that made calls for as long as every call of a turn is one `is_invalid()` says the model got wrong, which is cheap next to a provider call. `turns` is the number of turns. A turn's `attempts` is the failed attempts since the turn before plus one, and the retries of a run are each turn's `attempts - 1` plus, for a call that never succeeded, its failed attempts less one: a retry is an attempt made beyond the first of its call, so a failure that nothing follows isn't one. Per-tool statistics exist for every call that named a tool the run offered, whether or not the tool ran: a call whose arguments didn't parse, or one the loop rejected, counts against the tool it named, `task_complete` included. The model can call any name, and a call to one no tool has counts in the totals and in `tool_calls.unknown` and creates no per-tool key. A call that was never run counts nowhere. So the `lablet.tool.*.<name>` keys are bounded by what the executor resolves, not by `RunSetup::tools`. The two are the same set in a run, because a `ToolExecutor` resolves only the names it offered in `specs()` (§5) and `RunSetup::tools` is those names; the run reads the outcome rather than asking the tool list a second question it could answer differently. The intercepted `task_complete` call has no outcome, so it's in no total.

**Outcome.** `StopReason::class` sorts the stop reasons into `Completed`; `Failed`, a run that an error ended (`retries_exhausted`, `provider_error`, `context_exhausted`, `invalid_calls_exhausted`); and `Stopped`, every other reason. A `RunOutcome` has an `error` exactly when its reason is `Failed` and may have a `result.structured` only when it's `Completed`. The three fields the rule ties together are private and read through methods: `Run::finish` is the one way to build an outcome, and it keeps of the `structured` and `error` it's given only what the class allows, giving a failure that came without text the reason's own sentence (for `context_exhausted`, that the response was cut short at the context window). So the loop passes what it has at hand, for example the argument of a `task_complete` call in a truncated response, and the outcome is still one a run can have. Reading an outcome from its serde form refuses a document that breaks the rules (`OutcomeError`). The class isn't written to the JSON or the wide event; the JSON is unchanged.

**Usage.** `input_tokens` includes the cached tokens; `cache_read_tokens` and `cache_write_tokens` are subsets of it. `total()` is `input_tokens + output_tokens` and is what `run.max_total_tokens` counts; `uncached_input_tokens()` is `input_tokens` less both cache fields. An adapter builds a `Usage` through the constructor named for its provider's convention, so the addition can't be forgotten: `from_uncached` for a provider that reports uncached input separately, as Anthropic does, and `from_inclusive` otherwise. The reasoning count and the two cache counts are `None` for a provider that doesn't report them, so a zero is a count of zero and never a gap: several servers answer to one provider name and report different things, and a consumer couldn't otherwise tell which zeros to believe. A sum of usages is `None` in a field only when none of them reported it. `total()`, `uncached_input_tokens()` and `Pricing::cost` read a count that's missing as nothing.

**Cost.** `Cost::new` takes a finite `f64` of at least 0 and refuses anything else, on both the code and the serde path. JSON has no infinity or NaN, so serde writes either as `null`, which is also how a run with no pricing configured writes the field: a cost that overflowed would be indistinguishable from one never asked for. `Pricing::cost` (§4) is the only producer in a run and answers `Option<Cost>`, `None` when the rates and counts multiply out past an `f64`, which takes rates no real price list has.

**Finish reasons.** `FinishReason::from(String)` is how a provider's string becomes a reason, and serde reads through it. Every spelling either provider API uses for a known reason gives that reason (the table is in §6), so `Other("end_turn")` or `Other("stop")` can't come out of the conversion, and a fake script may use whichever spelling its author knows. A reason is written as its `as_str`: `end_turn`, `tool_use`, `max_tokens`, `context_window`, `refusal`, or the provider's own string for `Other`. `Other` carries an `UnknownReason`, whose string is private, so `From<String>` is the only way to build one and `Other("refusal")` isn't expressible: a refusal that skipped the conversion would read at point R as an ordinary end and complete the run.

**Serde form.** The forms below are those of `lablet-documents`, which the transcript, the outcome and the fake provider's script share, and of the model's own `Serialize` where the loop measures with it. Derives and serde attributes only, and a document that's read is built through the domain's checked constructor (`ProviderResponse::new`, `RunOutcome::closing`). A `UserContent` is `{"text": "..."}`. Enums are externally tagged with `snake_case` names: a `ContentBlock` is `{"text": "..."}` or `{"tool_use": {"id": "...", "name": "...", "input": {}}}`, and the other variants follow the same pattern; a `ToolSource` is `"builtin"` or `{"mcp": {"server": "docs"}}`; a `ToolCallStatus` is `"unknown"`, `"malformed_input"`, `"rejected"`, `"not_run"`, or `{"ran": {"source": "builtin", "ended": "ok"}}`; a `ToolInput` is `{"json": {...}}` or `{"unparsed": "..."}`, the two levels the type holds rather than the flattening `as_str` does for telemetry; a `Thinking` is `"provider_default"`, `"adaptive"`, `{"budget": 2048}`, or `"disabled"`, and a budget of 0 is refused. `Effort::XHigh` is `xhigh`. `Cost` is a bare number. An `Option` that's `None` is written as `null`, never left out; read, it may be left out, which is how a block of thinking without a signature is written by hand. A `Message` only serialises, as `{"user": {"tool_results": [{"call_id": "...", "content": [{"text": "..."}], "is_error": false}], "input": [{"text": "..."}]}}` or `{"assistant": [...]}`; that form is what the loop measures request bytes from (§5), and nothing reads it back. The forms a fake-provider script holds are strict where a slip would otherwise pass in silence: a script's entries and everything they nest refuse a key they don't know and a key written twice, so `input_token: 12` is an error, not a zero, and each refusal names the entry and the block it's in. What may be left out reads as nothing: a `Usage` count of input or output as zero, any of its other three as not reported, and a completion's `usage` as two zeros and nothing reported. The outcome document, the labels it nests, and a `ToolCallOutcome` refuse an unknown field for the same reason. `StopReason`, `CompletionMode`, `ToolSource` (the variant only), `ToolCallStatus`, `ToolCallEnd`, `FinishReason`, `ProviderKind`, and `Effort` each have an `as_str` that gives the serde spelling and a `Display` that prints it, except that a `ToolSource` prints an MCP tool's server too, as `mcp:docs`. A unit test in the model pins the wire spellings, and a test in `lablet-conformance`, which may depend on both crates, compares `StopReason`, `CompletionMode`, `ToolSource`, and `ToolCallStatus` with the generated registry enums through exhaustive matches, so a variant added on either side doesn't compile until the other has it.

**Tool results are text.** Lablet doesn't carry image, audio, or binary resource content from a tool. An executor replaces such an item with the one line `ToolResultContent::omitted` renders from its kind, MIME type, and byte length, for example `[image omitted: image/png, 48213 bytes]`, so the model and a reader of the transcript see one wording. `ToolUse::input_bytes`, `ToolCallOutcome::output_bytes`, and `Transcript::final_text` are each the one definition of the quantity they name: `lablet.tool.input.bytes`, `lablet.tool.output.bytes`, and `result.text`.

## 4. Domain policy (`lablet-policy`)

Pure functions over plain state, fully unit-testable without async:

```rust
pub struct StopPolicy { pub max_turns: Option<NonZeroU32>, pub timeout: Duration, pub max_total_tokens: Option<u64>, pub max_consecutive_invalid_turns: Option<NonZeroU32> }
impl StopPolicy {
    pub fn before_call(&self, progress: &Progress) -> Option<StopReason>;                        // point A of §1
    pub fn after_final(&self, finish: &FinishReason, completion: CompletionMode) -> StopReason;   // point R for a response that called no tool, which always stops
    pub fn after_response(&self, finish: &FinishReason, completion: CompletionMode, calls: Calls) -> Option<StopReason>;   // point R for one that called a tool; the mode is passed, not held, so the run keeps one copy of it
    pub fn after_tools(&self, progress: &Progress) -> Option<StopReason>;                        // point B
    pub fn allows_wait(&self, elapsed: Duration, wait: Duration) -> bool;                        // false when elapsed + wait reaches the timeout
    pub fn time_left(&self, elapsed: Duration) -> Option<Duration>;                              // what a call's deadline is taken from; None once elapsed has reached the timeout
}

pub struct RetrySettings { pub max_retries: u32, pub base: Duration, pub max: Duration, pub factor: f64, pub hint_max: Duration, pub jitter: f64 }   // named, because three durations passed in a row swap silently
pub struct RetryPolicy { settings: RetrySettings }
impl RetryPolicy {
    pub fn new(settings: RetrySettings) -> Result<RetryPolicy, RetryPolicyError>;
    pub fn next(&self, attempt: u32, kind: ProviderErrorKind, hint: Option<Duration>, salt: u64) -> Option<Duration>;   // the whole rule: the wait after one-based attempt `attempt` failed; None when the kind isn't retried, the call has had all its retries, or the server asked for a wait longer than hint_max
}
pub enum RetryPolicyError { BaseAboveMax { base: Duration, max: Duration }, Factor(f64), Jitter(f64) }

pub struct Pricing { rates: Rates }                       // the rates are a model type (§3), because a run reports them
impl Pricing {
    pub fn new(rates: Rates) -> Pricing;                              // Rates::new is where a rate is checked
    pub fn rates(&self) -> Rates;                                     // what the run reports beside its cost
    pub fn cost(&self, usage: &Usage) -> Option<Cost>;   // None when the amount overflows an f64
}
```

**Stop policy.** The methods hold the order and the boundaries §1 gives for each point. Each takes only what its point reads, so an input can't contradict itself: the two limit checks take the `Progress` the run produces (§3), and the token budget reads `Progress::usage.total()`, the tokens of every call so far, failed attempts included (§1), while the two point R methods take the finish reason and the completion mode, `after_response` a `Calls` as well, and see no limit at all. Point R is split along the run's states (§3). A response that called no tool always stops the run, so `after_final` returns a `StopReason` rather than an `Option`: `refused`, `output_truncated`, or `context_exhausted` when the finish reason says so, and otherwise `completed` in natural mode and `ended_without_completion` in explicit mode. A response that called a tool goes to `after_response`, which returns `None` when the run goes on. The mode is passed rather than held, so a run has exactly one copy of it: the `ToolSet` whose shape it decided (§5). `Pending::calls(mode)` (§3) builds the `Calls`, and is the only thing that does, so the loop can't read a response differently from how the policy expects it: `TaskComplete` when the response's only call is `task_complete` with arguments that parsed, which only explicit mode offers; a `task_complete` call among other calls is read as `Tools`, and so is any call in natural mode. `Progress` lives in the model because the run produces it, and the policy depends on the model, never the reverse; the loop's call is `stop.before_call(&run.progress(elapsed))`. `StopPolicy::time_left` backs the question asked between point R and the tool phase. The policy decides nine of the stop reasons, `context_exhausted` among them when a response was cut short at the context window. The rest aren't its to decide: `cancelled` comes from the loop's poll of the `Cancellation` port, and `retries_exhausted`, `provider_error`, and `context_exhausted` for a rejected request from a failed provider call (`RetryPolicy::next` returning `None`, and the failure's `ProviderErrorKind`). `allows_wait` is here because stopping with `timeout` instead of sleeping is a reached-the-limit decision like the others, and `time_left` because a deadline is one too: it's the only place a call's deadline is taken from the run's timeout, and its `None` is what stops a tool phase from starting and what answers a call `not_run`. Every `StopPolicy` value is meaningful, so its fields are public and nothing is validated. `Prompts` is the exception on the other side of the boundary: a blank task is refused by `Prompts::new`, because the first response needs something from the user before it (§3), and refusing the task here costs nothing where a run built from one would buy a provider call first. The two counted caps are `Option<NonZeroU32>`: `None` is no cap, and a cap of zero can't be written, since it has no reading other than one and two fields shouldn't reach that by two different routes; a zero `timeout` or token budget does stop the run at the first point A, which is a reading of its own.

**Retry policy.** `max_retries` is `run.max_retries`, and 0 is valid: it never retries. `new` refuses a `base` longer than `max`, a `factor` that isn't a finite number of at least 1, and a `jitter` that isn't a finite number from 0 to 1. `next(n, kind, hint, salt)` is a wait when `kind` is one another attempt could answer, `n` is at most `max_retries`, and the hint, when the server gave one, is no longer than `hint_max`; it's `None` otherwise. The wait is the longer of the hint and the backoff, where the backoff is `base * factor^(n - 1)` capped at `max`, and the wait, whichever of the two it came from, is then raised by a share of itself that's at most `jitter` and is read from `salt`. So the policy draws no random number, the same salt always gives the same wait, and a wait that came from a hint is spread like any other. The loop's salt is `RunId::salt` of the turn and the attempt (§3). It answers `None` at once for a failure another attempt can't change, so the policy owns the whole retry rule rather than half of it. It's total: attempt 0 is read as 1, and an attempt number or a factor large enough to overflow gives `max` with its jitter, or zero when `base` is zero and there's no hint, never a panic or a NaN.

**Pricing.** `Rates::new` (§3) refuses a rate that isn't a finite number of at least 0, so `Pricing::new` takes rates that are already checked and can't fail. The loop prices `spent()`, so what failed attempts reported is in the cost. `cost` prices `Usage::uncached_input_tokens()` at the input rate and each cache field once, at its own rate, because `input_tokens` already includes both (§3); pricing `input_tokens` whole and adding the cache fields would bill the cached tokens twice. A cost is never negative and never NaN.

The loop emits `ToolCallStarted`, then asks the observer for a `TraceContext` for that call id and places it on the `ToolCall`, so the MCP adapter can inject it into `params._meta`. The fan-out observer (kept so library users can register their own `RunObserver` beside the built-in one) returns the first `Some`; observers without spans return `None`. The OTel observer keeps open spans in a map keyed by call id, starts every child with an explicit parent context rather than the task-local current context (since `on` runs on arbitrary tasks), and marks every span sampled so the propagated flags are `01`. It builds a span as finished data when the call ends and hands that to the batch processor, without a tracer: a span is timed by what the loop measured, which the event that ends it carries, and a tracer would time it by the observer's clock. The span context is fixed when the call starts and readable synchronously, and batch processors only see ended spans, so the handoff needs no coordination with export. `error.type` is defined per span: on the root it's the stop reason when the run didn't complete, on a chat span the `ProviderError` variant name (`retryable`, `context_exhausted`, `auth`, `fatal`, `malformed`), or `cancelled` for an attempt dropped when the run was cancelled, and on a tool span the call's `ToolCallStatus` (§3) whenever it isn't `ok`: `tool_error`, the value the MCP conventions give, when the tool ran and returned an error result; `timeout` or `failed` when the executor did; `cancelled` when the run was cancelled while the call ran; and `unknown`, `malformed_input`, or `rejected` when the loop answered the call itself. The loop settles the status once for each call: `Ok(output)` is `ok`, or `tool_error` when `output.is_error`, and `Err(error)` is the namesake of `error.kind`. The same span carries `lablet.tool.output.truncated` and, when the output cap cut the output, `lablet.tool.output.original_bytes`; `lablet.tool.output.bytes` is the size the model was sent.

`ToolCallStarted.source` is `None` when the model calls a well-formed name that no tool has: there's no spec to read a source from. The `execute_tool` span of such a call carries neither `lablet.tool.source` nor `gen_ai.tool.type`, which the registry requires only for a tool the run offered, as it already does for `gen_ai.tool.description`; the span's `error.type` is `unknown`. Neither enum gains a member that names no source.

The two digests of `RunSetup` are SHA-256, written as lower-case hex, of the system prompt, and of the tool specs as compact JSON in the model's serde form, in the order they're offered and with nothing between one spec and the next: the same bytes `request_bytes` counts, hashed once, before the first call. The loop computes both, which is why `lablet-run` takes `sha2`. `request_bytes` is measured by the loop, not the adapter, so it's the same for every provider: the byte length of the system prompt, plus the length of each message in the request and of each tool spec as compact JSON in the model's serde form. The loop measures the system prompt and the tool specs once per run and each message once, the first time `Run::messages` renders it whole, which for a user message is when the results it holds are in, and keeps a running sum and a count of the messages it has measured, so a provider call costs the serialisation of what the last turn added, not of the conversation. It's a measure of context growth, not of the wire body.

Every per-step event carries `turn`, which observers emit as `lablet.turn` on the corresponding span. There is no turn span; the trace is `invoke_agent` with `chat` and `execute_tool` children directly beneath it, as the conventions describe, and turns are recovered by filtering on the index. A turn span can be added under the root later without changing anything else.

Content-bearing fields on events (`system_prompt`, `prompt`, `response`, `input`, `output`) are `None` unless `telemetry.capture_content` is on. The loop decides, so observers never see content they shouldn't. When content is off the attribute is omitted, not written as a placeholder; the byte-count attributes are always present. The intercepted `task_complete` argument appears in the outcome and transcript regardless, and in telemetry only when content is captured.

Observers never fail the run and never block it: `on` must return promptly, exporters buffer and batch, and export failures (an unreachable OTLP endpoint, an unwritable file) go to lablet's diagnostic log. The composition root flushes every observer before exit and reports flush failures on stderr without changing the exit code.

The `Clock` port is the only source of time for the loop, so `lablet-run` tests drive timeouts and backoff with a fake clock. Adapters enforce their own per-call deadlines with real time, and each has a limit of its own that the deadline can only shorten: a run has one timeout, but a shell command and a call to a remote server don't deserve the same one.

### Use case

```rust
pub struct RunService { provider: Arc<dyn ModelProvider>, tools: Arc<ToolSet>, observer: Arc<dyn RunObserver>, clock: Arc<dyn Clock>, cancel: Arc<dyn Cancellation>, stop: StopPolicy, retry: RetryPolicy, request: RequestParams, pricing: Option<Pricing>, calls: CallLimits }
pub struct CallLimits { provider_timeout: Duration, output_cap: Option<OutputCap>, max_concurrent_tool_calls: NonZeroU32 }   // run.provider_timeout, tools.max_output_bytes with tools.output_cut, tools.max_concurrent_calls
impl RunService { pub async fn run(&mut self, context: RunContext, prompts: Prompts) -> FinishedRun }
pub struct ToolFilter { allow: Vec<ToolName>, deny: Vec<ToolName> }   // an empty allow list offers everything; a name in both is denied
pub enum ToolSetError { DuplicateName { name: ToolName }, UnknownFilterName { name: ToolName, list: FilterList }, Specs(Box<ToolError>) }
pub enum FilterList { Allow, Deny }
impl ToolSet {
    pub async fn build(executors: Vec<Arc<dyn ToolExecutor>>, filter: &ToolFilter, completion: CompletionMode, completion_schema: Option<Value>) -> Result<ToolSet, ToolSetError>;
    pub fn specs(&self) -> &[ToolSpec];  pub fn source(&self, name: &ToolName) -> Option<&ToolSource>;  pub fn completion(&self) -> CompletionMode;
    pub async fn execute(&self, call: ToolCall) -> Result<ToolOutput, ToolError>;   // routed to the executor that offered the name
    pub fn concurrency(&self, call: &ToolUse) -> ToolConcurrency;   // Shared for a call the loop answers without an executor: a name this run doesn't offer, arguments that didn't parse, or a call the mode intercepts
}
```

`run` never returns `Err`: every failure is a `RunOutcome` with a stop reason, so the caller always gets telemetry-consistent output. It returns one value, the model's `FinishedRun` (§3), which `Run::finish` builds: the `RunSummary`, whose `outcome` is the outcome document, and the `Transcript`, which is how the conversation leaves the loop. When `pricing` is set, the loop fills `RunSummary.cost` with `Pricing::cost` of the run's usage; otherwise it's `None`. The limits and request parameters in the summary come from the service's own `StopPolicy` and `RequestParams`, so they can't differ from what the run enforced. `CallLimits` holds what bounds the calls and isn't a stop decision: the provider timeout, of which a request's `deadline` is the shorter with the time the run has left; the tool output cap, which the loop hands to `Answer::measured` for every call, so no executor decides how output is cut, and whose `keeps` it hands to the executor, so none holds more than the cut can use. A tool call's `deadline` is `StopPolicy::time_left`, the time the run has left when the call begins, once the observer has been told of it; and how many calls of one group may run at once, which the loop hands to `Pending::answer`.

The loop body, in the model's and the policy's terms. Every offset and latency is a `Duration` read from the `Clock`; the model turns them into milliseconds.

```
tools = ToolSet::build(executors, &filter, completion, completion_schema)?        # settled once; the only place a ToolSource is learned
run = Run::start(RunSetup { run_id, labels, model, endpoint, the names of tools.specs(), tools_bytes, tools_digest, system_prompt_digest, tools.completion(), max_turns, timeout, request }, prompts)   # the size and the digests are taken from what the loop is about to send
loop:
    turn = the number of turns so far, plus one;  attempt = 1
    (response, began, latency) = loop:                                     # one provider call
        if cancelled: stop cancelled;  if let Some(r) = stop.before_call(&run.progress(elapsed)): stop r   # point A, asked before every attempt: a retry is a provider call
        if stop.time_left(now) is None: stop timeout                        # the clock is read again after point A: no attempt is made, or announced, in a run whose time has gone
        emit ProviderCallStarted;  began = now                                # a second reading, after the observer's work, so the attempt's start and latency are its own
        result = { messages = run.messages(); provider.complete(ProviderRequest { system: run.transcript().system(), &messages, cache_key: the run id when request.cache_scope is Run, deadline: the shorter of provider_timeout and what was left less what the observer took, which is zero when it took it all, .. }) }   # raced against cancel.cancelled(): cancelled first drops the attempt, run.failed_attempt(began, latency, None), emit ProviderCallCancelled, stop cancelled
        latency = now - began
        Ok(r)  -> break (r, began, latency)                                # the attempt's timing leaves with it: only here knows either
        Err(e) -> run.failed_attempt(began, latency, e.usage), whose timing ProviderCallFailed carries; ContextExhausted -> stop context_exhausted, e; Auth or Fatal -> stop provider_error, e
                  if cancelled: stop cancelled;  if let Some(r) = stop.before_call(&run.progress(elapsed)): stop r   # the attempt may have used up the run's time or its budget: that's the reason then, with a retry left or without
                  retry.next(attempt, e.kind, e.retry_after, run_id.salt(turn, attempt)): Some(wait) if stop.allows_wait(elapsed, wait) -> sleep(wait), unless cancelled first: stop cancelled; attempt += 1   # and round again, through point A
                                               Some(_) -> stop timeout
                                               None -> stop retryable and malformed as retries_exhausted, a hint past hint_max among them,
                                                       context_exhausted, auth and fatal as themselves, with e.message
    match run.responded(response, began, latency):                         # the transcript's new turn; it takes the waiting input, and its record counts the attempts
        Final(f)   -> stop stop.after_final(&f.turn().record().finish, tools.completion())    # a response that called no tool always stops the run
        Pending(p) -> structured = p.completed_with(tools.completion()): the argument of a task_complete call that came alone and parsed
                      if let Some(r) = stop.after_response(&p.turn().record().finish, tools.completion(), p.calls(tools.completion())): stop r
    if stop.time_left(elapsed) is None: stop timeout                       # no tool starts in a run that has no time left; the turn's calls stay unanswered
    run = p.answer(Schedule { max_concurrent: max_concurrent_tool_calls, concurrency: |call| tools.concurrency(call) }, |call| async:   # the name is resolved before the arguments are read
        left = stop.time_left(now)                                         # read when the call's turn comes, which for a later group is after the groups before it
        if cancelled: return Answer::measured(NotRun, whole("the run was cancelled before this call started"), None, now, zero)   # nothing started, so no event; cancellation comes first, as at points A and B
        if left is None: return Answer::measured(NotRun, whole("the run reached its timeout before this call started"), None, now, zero)
        emit ToolCallStarted;  trace_context = observer.trace_context(&call.id);  began = now   # a second reading, after the observer's work: the call's start and latency are its own, and its deadline is what was left less what the observer took
        (status, output, mcp) = match tools.source(&call.name):          # the loop is the only hop from executor to observer, so mcp travels with the result
            None          -> (Unknown, whole("no tool named ... is offered by this run"), None)
            Some(source)  -> match call.input:
                Unparsed(text) -> (MalformedInput, whole("the arguments weren't valid JSON ..."), None)
                Json(_) if tools.completion().intercepts(&call.name) -> (Rejected, whole("call task_complete on its own, once your other calls have returned"), None)   # it wasn't the only call, or the run would have stopped at point R
                Json(input)    -> match tools.execute(ToolCall { id, name, input, deadline: left, keep: output_cap.map(OutputCap::keeps), secrets, trace_context }), raced against cancel.cancelled():
                    cancelled first -> (ran(source, Cancelled), whole("the run was cancelled while this call ran, and the call was stopped"), None)   # the call is dropped where it is
                    Ok(out) -> (ToolCallStatus::ran(source, if out.is_error { ToolError } else { Ok }), out.output, out.mcp)
                    Err(e)  -> (Unknown for ToolErrorKind::Unknown, else ran(source, e.kind), bounded(whole(e.message)), e.mcp)   # whole() is every text the loop writes itself, with the run's secrets cut out of it as a result's are: an executor's message and the arguments the model sent show no value; an executor's message is bounded to ERROR_MESSAGE_MAX_BYTES only after the cut, since a value the bound chopped would be no value to the cut and every byte of it before the bound would be sent
        answer = Answer::measured(status, output, output_cap, began - start of run, now - began)
        emit ToolCallFinished from answer and mcp;  answer
    ).await                                                                # outcomes in call order, whichever call finished first
    if cancelled: stop cancelled;  if let Some(r) = stop.after_tools(&run.progress(elapsed)): stop r
# `stop` leaves the loop holding the state it stopped in: a Run, a Final, or a Pending, each of which can finish
rates = pricing.map(Pricing::rates); cost = pricing.and_then(|p| p.cost(&state.spent()))   # both from one Option<Pricing>; cost is None when the amount overflows
return state.finish(reason, elapsed, structured, error, rates, cost)       # FinishedRun { summary, transcript }
```

A call whose arguments didn't parse never reaches an executor, so it has no latency of its own and no `ToolCall` is built for it; the model is sent its own text back, which is what lets it correct itself. A call the mode intercepts reaches `answer` only when it didn't complete the run, which is when its arguments didn't parse or when it wasn't the response's only call, and the loop answers both. `CompletionMode::intercepts` is the one reading of which call that is, so a tool an executor serves under the name `task_complete` in natural mode is run like any other. The messages are rendered inside the attempt because they borrow the run, which a failed attempt changes; rendering is one allocation and no copy of the conversation. The loop passes `finish` whatever `structured` and `error` it has, and the outcome keeps what the stop reason allows (§3), so the loop has no rule of its own about which stop reason carries which. Nothing in the loop can be refused by the transcript, because the run's states (§3) offer no method for a sequence it would refuse, which is why the pseudocode has no `?`. Point R is asked in the arm that knows the state, so neither arm holds a case that can't happen: a `Final` always stops, which `StopPolicy::after_final` returns as a bare `StopReason`, and a `Pending` stops when `after_response` says so and is answered otherwise.

One `RunService` executes one run at a time, which `run` taking `&mut self` makes a compile error rather than a race. This ring has no runtime, so there's no mutex to reject a concurrent call at, and `run` returns a bare `FinishedRun` with nowhere to report a refusal; an exclusive borrow is the same answer the domain gives everywhere else.

`ToolSet` is a composite over several `ToolExecutor`s in this crate that routes a call by name, applies the config allow and deny lists, and rejects duplicate names at build time. It's deliberately not a `ToolExecutor` itself: the loop needs `source(&name)`, which the port can't answer. It also holds the run's `CompletionMode`, the one value whose shape depends on it, and everything else that needs the mode reads it back from there. The `task_complete` tool spec is defined in this crate, registered by `ToolSet` only in `explicit` mode regardless of `tools.builtin.enabled`, and never executed: the loop intercepts it. Its name is claimed before any executor is asked, so an executor serving `task_complete` in `explicit` mode is a duplicate-name error rather than a tool offered twice. Its input schema is `run.completion_schema` when set, otherwise a free-form object.

From phase 10 the loop has a second tool of its own, `skill`, registered by `ToolSet` when the run has skills and `prompt.skills_mode` is `tool`. The system prompt then lists each skill by the name and the description its `SKILL.md` gives, and a call to `skill` with a name returns that skill's body, which is how every harness surveyed that has skills loads them. The loop answers the call itself, as a built-in tool that ran, and a name no skill has is an error result. The `execute_tool` span of a call carries `lablet.skill.name`, and the wide event lists the skills that were loaded, in the order they were first asked for, so a skill's author can see whether its description got it loaded. With `skills_mode: inline` there's no tool, and every body follows the system prompt. Phase 10's design commit settles the wording of the list and its size, which the capture of the primary reference informs, and gives the three attributes their sources in the summary and the tool events. `ToolSet` is where "what happens when a tool is missing" is expressed: the tool is simply absent from `specs()`.

A `ToolExecutor` resolves only names it offered in `specs()`, and `ToolSet` fixes that set when the run is built, so no tool appears to a run part-way through. This is the port's obligation rather than a rule the model can hold, because a `ToolCallStatus` of `Ran` carries the source the executor resolved and the run believes it (§3). It's what keeps the per-tool attribute keys bounded, and it's the rule to hold an MCP executor to at phase 8, where a server may announce `notifications/tools/list_changed` mid-run: the tool set is fixed when the `Lablet` is built, so the new tool belongs to the next `Lablet`, and not to this run or to the runs after it.

A turn's tool calls run in the groups §1 describes: consecutive calls whose tool is `Shared` run concurrently, at most `tools.max_concurrent_calls` at a time, and each `Exclusive` call runs alone, with groups in call order. The loop emits `ToolCallStarted` and `ToolCallFinished` from inside the future it gives `Pending::answer` for each call, so the events of calls in one group interleave. Observers key them by `call_id`, and an observer mustn't assume any order between the events of two calls in one group. The transcript, the rendered results and the count of consecutive invalid turns read outcomes in call order and don't depend on timing. With `tools.max_concurrent_calls: 1` every call runs alone and the event stream is the one the sequential loop produced, which is what a test that asserts events exactly uses. Once calls overlap, `lablet.tool_calls.latency_ms.total` still sums each call's latency, so it can exceed the run's wall time: it's call time, not the time the tool phases took.

`ToolSet::build` refuses a name in `allow` or `deny` that no executor serves (`UnknownFilterName`), since a misspelt `deny` entry would otherwise leave the tool it meant to deny on offer. In explicit mode `task_complete` isn't served by an executor, so naming it in either list is refused too: the filter doesn't apply to it.

## 6. Adapters

### Finish reasons

Both provider adapters hand the provider's own string to `FinishReason::from` (§3), which holds this mapping, so neither adapter keeps a table of its own and a fake script may use either spelling:

| `FinishReason`  | Anthropic `stop_reason`         | OpenAI-compatible `finish_reason` | Stop policy at point R    |
| --------------- | ------------------------------- | --------------------------------- | ------------------------- |
| `EndTurn`       | `end_turn`, `stop_sequence`     | `stop`                            | decided by the tool calls |
| `ToolUse`       | `tool_use`                      | `tool_calls`                      | decided by the tool calls |
| `MaxTokens`     | `max_tokens`                    | `length`                          | `output_truncated`        |
| `ContextWindow` | `model_context_window_exceeded` | none                              | `context_exhausted`       |
| `Refusal`       | `refusal`                       | `content_filter`                  | `refused`                 |
| `Other(string)` | anything else, as `pause_turn`  | anything else, as `function_call` | decided by the tool calls |

### `provider-anthropic`

Messages API via `reqwest` with `rustls`. Maps `ContentBlock` both ways, including `thinking` and `redacted_thinking`. With `model.cache: true` it sets cache breakpoints on the system prompt, the last tool spec and the latest message, so each call reads the conversation before it from the cache and writes what the last turn added. Every harness surveyed that sets breakpoints covers the conversation, and the placement is checked against the primary reference's at the phase 7 capture. With `model.cache_scope: run` the request carries the run id as its `cache_key` (§5), and the adapter sends it as a system block of its own, ahead of the system prompt, so no two runs share what's cached from there on. Anthropic caches the tool specs ahead of the system prompt, so those stay shared between runs: nothing can come before them without changing the tools under test. With `shared`, the default, runs share the whole prefix, as they do in the references. The line isn't part of the system prompt the transcript holds, nor of its size or its digest. Reads `cache_read_input_tokens` and `cache_creation_input_tokens` into `Usage`; the latter is reported as `gen_ai.usage.cache_write.input_tokens`, the semantic-convention name, not Anthropic's. Anthropic's own `input_tokens` leaves both out, so the adapter builds the `Usage` with `Usage::from_uncached`, which adds them in: `Usage.input_tokens` includes cached tokens (§3). Thinking: `ProviderDefault` sends nothing, `Adaptive` sends `thinking: {type: adaptive}`, `Budget(n)` sends `thinking: {type: enabled, budget_tokens: n}`, `Disabled` sends `type: disabled`; `effort` is a separate request parameter that maps to `output_config.effort` and is reported as `gen_ai.request.reasoning.level`. `temperature` is sent only when set; the build step warns that models from Opus 4.7 and Sonnet 5 onward reject a non-default value. Validates that a `Budget` is below `max_tokens` at build. Classifies 429, 529, 5xx, transport errors, and per-call timeouts as retryable, reading a `retry-after` header into the error's hint; the `prompt is too long` invalid-request error as context exhausted; 401 and 403 as auth; and any other 4xx as fatal. `seed` is refused at build, since the API has no such parameter (§7).

### `provider-openai`

Two APIs behind one adapter, chosen by `model.api`. `responses` is for OpenAI's own models and is the default when `base_url` is unset. `chat_completions` is for every other server (Ollama, vLLM, gateways) and is the default when `base_url` is set.

**Responses.** `POST /v1/responses` with `store: false` and `include: ["reasoning.encrypted_content"]`. A reasoning item in a response is kept as an `Opaque` block and sent back unchanged in every later request, as the secondary reference does, so a reasoning model builds on what it thought in the turn before and doesn't start again. Chat completions never returns OpenAI's reasoning, so a loop built on it alone makes an OpenAI model reason from nothing every turn, which no production harness does. A function call maps to `ToolUse`, and a tool result to a `function_call_output` item. `effort` maps to `reasoning.effort`.

**Chat completions.** `/v1/chat/completions` with function calling. Sends `max_completion_tokens` and falls back to `max_tokens` if the server rejects it, once for a `Lablet` and not once for each call. One user message holding N `ToolResult` blocks becomes N `role: tool` messages on the way out. `reasoning_content` and `reasoning` fields are mapped to `Thinking` with no signature on the way in. `model.reasoning_replay` says whether a `Thinking` block is sent back as `reasoning_content`: `false` by default, because some servers refuse it, and `true` for a server that needs it. Message fields the adapter doesn't know are dropped, with a line on the diagnostic log at `debug`: `Opaque` is a content block, and chat completions has no block to hold them.

**Both.** Function `arguments` that aren't valid JSON are kept as the model wrote them, as `ToolInput::Unparsed`, and the call is answered `malformed_input` (§1); they aren't a `Malformed` response, so the same mistake is measured the same way on both providers. `Usage` is built with `Usage::from_inclusive`, since the prompt count already includes the cached tokens, and a count the server doesn't report is left out. `seed` is passed when set. `thinking` is refused at build, since neither API has the parameter, and so is `effort` with `chat_completions` (§7). A request's `cache_key` is sent as `prompt_cache_key` to OpenAI's own API, and as the first line of the system message to any other server. `api_key_env` is optional; no header is sent when it's unset. The wide event reports the API as `lablet.request.api` and whether reasoning was sent back as `lablet.request.reasoning_replayed`.

Errors are classified by this table, and a response it doesn't name is fatal:

| Response                                                                                                      | Kind                                                                                     |
| ------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| 401, 403                                                                                                      | auth                                                                                     |
| 429 whose code is `insufficient_quota`                                                                        | fatal                                                                                    |
| any other 429                                                                                                 | retryable, with the hint from `retry-after` or from a message that says how long to wait |
| 5xx, a transport error, a per-call timeout                                                                    | retryable                                                                                |
| 400 whose code is `context_length_exceeded`, or whose message names the context length or the maximum context | context exhausted                                                                        |
| a response the adapter can't map to the model                                                                 | malformed                                                                                |

Ollama cuts a prompt longer than its context size short and reports no error, and its OpenAI-compatible API has no parameter for the size. So the example and the docs say how to set it on the server, and why a run against a default Ollama can lose its system prompt without a sign.

### `provider-fake`

Plays a scripted sequence of `ProviderResponse`s from a YAML or JSON file, read into the domain through `ProviderResponse::new` by this adapter's own types (§3), with optional per-call latency (real time) and injected errors of each `ProviderError` kind, each with the usage and the retry hint the script gives it. Selected with `model.provider: fake` and `model.script: path`. Reports usage from the script so token accounting is exercised end to end. Used by lablet's smoke tests, doctests, and examples, and by users testing their own frameworks. `lablet init --provider fake` writes both a config and a script. A script is a list of entries, each a `response` or an `error`, and a run takes them in order. An entry whose latency would outlive the deadline the loop handed it fails as `retryable` at the deadline, and the entry is used up, as a real call that timed out would have been. A run that outlasts its script fails as `fatal`, which ends it with `provider_error` and a message that says the script ran out: a kind that's retried would wait out real backoff and report a short script as a flaky provider. The port names no run, so the composition root rewinds the script at the start of each run on the same `Lablet`. An empty script is refused when it's read.

### `tools-builtin`

Each tool is a small struct; the executor holds only those enabled in config, and none is enabled by default, since a run that measures an MCP server has no use for a shell. Initial set: `bash`, `read_file`, `write_file`. They're a convenience for tasks that need a shell or files, and they don't reproduce any harness's tool suite. With one enabled, `tools.builtin.root` is required, and `build` refuses a root that holds the config, a prompt or skill file, the transcript, or the telemetry file, where each would be read or written: a `..` after a directory that doesn't exist yet leads back to where it's made, and a link at the transcript's path is replaced, not followed. The check keeps a config from pointing lablet's own files into the root and keeps `read_file` and `write_file`, which are confined to it, off them. It isn't a boundary against `bash`, which isn't confined and can reach any path lablet can, or make a link under the root after `build` has checked it; a dangling link passes it too. The task prompt's file is one of them when the caller names it with `Config::with_prompt_file`, as `lablet run --prompt-file` does. All paths are resolved under the root after symbolic links are followed, and rejected if they escape it.

`bash` starts a new process for each command, in the root and in a process group of its own. So no working directory and no variable carries from one command to the next. The secondary reference and mini-swe-agent do the same, and the primary carries the working directory over inside the project, which is a known difference (`product/research/parity/`). It inherits lablet's environment, less the variables lablet reads its secrets from, with what `tools.builtin.env` adds on top. So what a framework prepared for its commands, such as `JAVA_HOME`, a proxy or a virtualenv, reaches them, and the model can't read lablet's API key with `env`, nor send it by name, as `curl -d "$ANTHROPIC_API_KEY"` would without the value ever reaching a result. No harness surveyed is known to keep its model's key from its commands (for the primary reference that's likely until a probe settles it), and lablet differs here on purpose, for safety. Lablet's secrets are defined by the config's fields and never found by a name's pattern: the model's key, the variable `model.api_key_env` names or `ANTHROPIC_API_KEY` for `anthropic` when it names none; every value of `telemetry.otlp.headers` and of an HTTP server's `headers`, written or substituted; the user information of `model.base_url`, `telemetry.otlp.endpoint` and a server's `url`; and every variable substituted into `tools.builtin.env` or a stdio server's `env`. The composition root derives the set in one place, from the config as it's written and as it runs, and holds the values only when a run has an executor. A variable in the set is withheld from every command, and reaches a child only where its `env` names it, with the value the config gives: a task that needs the key gets it only when the config says so. A framework's other secrets are the framework's: a `GITHUB_TOKEN` it sets and the config doesn't name reaches the command and is never cut; the framework chose lablet's environment, and leaves out of it what no command should have. The one exception is what the exporter reads from the environment: the OTLP header variables, `OTEL_EXPORTER_OTLP_HEADERS` and its per-signal forms, whose values are cut, and the OTLP endpoint variables, `OTEL_EXPORTER_OTLP_ENDPOINT` and its per-signal forms, whose user information is cut when they have any, in the forms the config's endpoint's is; every command inherits them, as it does the rest of the OpenTelemetry environment (§7). A command can still find a secret another way, since it runs as the user lablet runs as: in a file, or in lablet's own environment through the process table. On Linux the `lablet` binary clears the process's `PR_SET_DUMPABLE` flag (§7), so a command it starts can't read lablet's environment through `/proc`. On macOS a command still can, and so can a command lablet starts as a library, since the caller's process is left as the caller made it. The flag closes lablet's own entries in `/proc` to other processes of the same user, and a same-user `ptrace`; the environment of the process that started lablet stays readable, and so does lablet's through the process table on macOS. So the value of each of lablet's secrets is cut out of every tool result, and out of every executor's error message, before the model, the transcript or telemetry sees it, and `[secret withheld]` stands in its place (§3). What's cut is the value as lablet holds it and its bounded parts: each line of a value that has several and its `\n`-escaped form, the remainder after a scheme word `Bearer`, `Basic` or `Token`, and each decoded header value of a variable shaped as OTLP headers are. A part is cut only when it's at least 16 bytes long without the whitespace around it: a shorter value could be ordinary text, and its cuts would show what it is. A copy that's encoded or changed isn't cut. The secrets travel on the `ToolCall` (§5), so no executor can skip the cut, and `lablet-conformance` holds the case that every executor passes. Its result is what the command wrote, standard output and standard error in the order they were written, then one line with the exit code, which is the output's closing line (§3), so a cut never drops it. A non-zero exit is an ordinary result and not an error: a failing test is something a command reports, not a tool that failed. At the shorter of the call's `deadline` and `tools.builtin.timeout` the whole process group is killed, and `execute` returns once it has gone. A group that hasn't gone 5 seconds after it was killed ends the call as `Failed` and never as `Timeout`, because `Timeout` says the work has stopped. A command that exits and leaves a process in the background leaves it running; only a call that reached its deadline, or was dropped, kills its group. A dropped call, which is how the loop stops one when its run is cancelled, sends the kill and doesn't wait for the group to go, so a cancelled run stops in the time its futures take to drop. A process that leaves the group, as one started with `setsid` does, is beyond the kill. `write_file` makes the directories its path is missing, and the file tools read and write regular files only. `read_file` takes an `offset` and a `limit` in lines, so a file longer than the output cap can be read in parts. The root bounds the file tools and is where `bash` starts, and nothing more: `bash` is as free as the environment lablet runs in, and that environment is what isolates it.

`read_file` is `ToolConcurrency::Shared`; `bash` and `write_file` are `Exclusive`, since either can change what another call reads. `task_complete` isn't here; see §5.

Both executors report how a call ended in the port's terms, and the loop turns that into the call's `ToolCallStatus` (§5): a tool that ran and reports a failure of its own, such as a path outside the root or a file that can't be read, returns `ToolOutput` with `is_error: true` (`tool_error`); a name the executor doesn't have is `ToolErrorKind::Unknown`; a call that outlives the shorter of its `deadline` and the executor's own limit is `Timeout`; and an executor that couldn't run the tool at all is `Failed`. Neither executor decides how output is cut. Each feeds what the tool writes to a `KeptOutput`, which keeps what the call's `keep` allows and counts the rest, and the loop applies the cut to every result the same way (§3).

### `tools-mcp`

One `rmcp` client per configured server (version pinned in the workspace `Cargo.toml`). A tool is offered as `mcp__<server>__<tool>`, which is how the primary reference names it, and every harness surveyed that documents its naming adds the server's name. So a model sees in lablet the kind of name it sees in use. `names: own` on a server offers its tools under the names it reports. A tool is `ToolConcurrency::Shared` exactly when the server annotates it `readOnlyHint: true`, and `Exclusive` otherwise, including when it has no annotations: the hint is the server's word, trusted as its tool names are. A reported name, or a prefixed one, that isn't a valid `ToolName` (1 to 64 of `[a-zA-Z0-9_-]`, which is what both provider APIs accept) is a build error with the `mcp:` prefix naming the server and the tool, since no provider would accept it. A server's `name` is held to the characters of a tool name and may not hold `__`, so a prefixed name reads one way only. Two tools offered under one name are a build error, which only `names: own` can then cause. The server's `instructions`, when it has any, follow the system prompt under a heading that names the server, cut at `tools.max_description_chars`, as each tool's description is. The cap is 2,048 characters, the primary reference's, and `null` lifts it. `instructions: false` on a server leaves them out. `execute` forwards the call and maps `isError` results to `is_error: true`, which the loop records as the status `tool_error`; a JSON-RPC error, a broken transport, or a dead server is a `ToolError` of kind `Failed`; a call that outlives the shorter of its `deadline` and the server's `call_timeout` is one of kind `Timeout`, returned once the server has been sent a cancellation notice for the request. Tool results are text (§3): a `text` item is carried unchanged and a text resource as its text, and an `image`, `audio`, or binary resource item becomes the one line `ToolResultContent::omitted` renders from its kind, MIME type, and decoded byte length, for example `[image omitted: image/png, 48213 bytes]`. When a result carries `structuredContent`, the MCP specification has the server repeat it as JSON text in `content`, so the model is sent one of the two and never sees the same data twice. `tools.mcp_result` says which. `structured`, the default and what the references send, is the structured value as one item of compact JSON text, with the items of `content` that aren't text. `content` is the `content` alone, and the structured value only when `content` is empty. A resource link is sent as one line of text that holds its name, its URI and its description. It injects the `ToolCall`'s `trace_context` into the request's `params._meta` as unprefixed `traceparent` and `tracestate`, per MCP SEP-414, and fills `lablet-run`'s `McpCallMeta` (§5: method, session id, protocol version, JSON-RPC request id, RPC status code on error, transport `pipe` for stdio or `tcp` for HTTP) on the output or error so the OTel observer can put `mcp.*`, `jsonrpc.*`, `rpc.*`, and `network.transport` on the `execute_tool` span; the conventions want one span carrying both `gen_ai.tool.*` and `mcp.*`, not a nested MCP span. `build` starts the servers, with `tools.mcp[].startup_timeout`, because it has to list their tools to check the config. With `tools.mcp_lifetime: run`, the default, those servers serve the first run, and every later run on the same `Lablet` stops them and starts them again before it begins. So no run is served by a server that served another, which is how every MCP host surveyed behaves. With `lablet` they live until `Lablet::shutdown`, and one found dead at the start of a run is started again. The tool set is fixed when the `Lablet` is built, so a server that comes back offering other tools has failed to start. How a run ends when a server can't be started is an open question (§10). The wide event reports the lifetime, and the name and version each server gave when it started. A stdio server starts with the short list of environment variables `bash` gets and what its `env` adds. That short list is `HOME`, `PATH`, `SHELL`, `USER`, `LANG`, `TERM`, `TMPDIR` and `TZ`, and phase 8 decides between it and the rule `bash` follows, after a probe of the primary reference. Its stderr is forwarded line by line to the diagnostic log at `debug`. HTTP servers receive `headers` verbatim. If a server exits or its transport breaks mid-run, every call to its tools returns a tool error naming the server, and the run goes on as it would in a reference; its tools stay listed so the model's behaviour is observable.

### Telemetry contract (`lablet/telemetry/`)

Telemetry is contract-first. An OpenTelemetry Weaver registry under `lablet/telemetry/registry/` in the v2 syntax (`file_format: definition/2`) declares every attribute, span, and log record lablet emits. The approach follows `product/research/weaver/`, which verified it against Weaver v0.26.1:

- `manifest.yaml` (the `registry_manifest.yaml` name is deprecated) depends on the core semantic conventions (`v1.44.0`) and `semantic-conventions-genai` (pinned commit) through **relative paths** to `model/` trees vendored under `lablet/telemetry/deps/` by `cargo xtask weaver vendor`, each with a `SOURCES` file recording the repository, the ref, the commit and its date, and the paths copied. The paths are relative to the repository root, because Weaver resolves them against its working directory and `cargo xtask weaver` runs it there. Weaver has no dependency cache and clones every git dependency on every run, including the GenAI registry's own dependency on the core conventions, so the committed manifest never uses git URLs and the vendoring script points that one line of the vendored GenAI manifest at the vendored core tree. Every other vendored file is byte-identical to its source. The shared naming and stability policies and the Markdown doc templates from `opentelemetry-weaver-packages` are vendored the same way, without the test fixtures that sit beside them. The pinned commits live in `lablet/telemetry/vendor.sh` alone; `cargo xtask weaver vendor --check` fetches them again and fails on any difference, and a weekly CI job runs it. The gates need no network.
- The registry declares `lablet.*` attributes, each with a `note` beginning `Justification:`, and **lablet-owned** spans (`lablet.invoke_agent`, `lablet.chat`, `lablet.execute_tool`) and events (`lablet.run`, the wide event, and `lablet.retry`) that `ref` the `gen_ai.*`, `mcp.*`, `jsonrpc.*`, `rpc.*`, `network.*`, `server.*`, `session.*`, and `error.type` keys with explicit requirement levels. It doesn't refine or import the GenAI events, which core semconv's deprecated copies make unreachable. The provider-failure record and the content record are therefore declared in lablet's registry under the GenAI event names they're emitted with, `gen_ai.client.operation.exception` and `gen_ai.client.inference.operation.details`, so a consumer that knows the conventions finds them and live-check matches them by name. Resource entities are imported (`service`, `telemetry.sdk`).
- `cargo xtask weaver check` runs `weaver registry check --v2` with the lablet policies (Rego, after resolution) and the vendored naming and stability policies; the justification policy fails any `lablet.*` attribute without a note. The policy allows Development stability for imported `gen_ai.*`. It runs in pre-commit. Diagnostics render through lablet's templates under `lablet/telemetry/templates/diagnostics/`, as text or, when `CI=true`, as GitHub workflow commands: Weaver's own GitHub format prints policy violations only, so a reference that doesn't resolve would fail the check in silence, and its text format buries a finding under one warning for every v2 file.
- `cargo xtask weaver generate` runs `weaver registry generate --v2` with the MiniJinja templates under `lablet/telemetry/templates/registry/rust/` (filters are jq, not JMESPath), starting from the spike's templates, producing the sources of the `lablet-telemetry-registry` crate: a name constant for every attribute on a lablet signal or resource, an enum for each of lablet's closed value sets (the semantic-convention enums are open, so they get none), and for each span and event the list of its required keys and of all its keys. The `lablet.run` wide event also gets two enums, `EventLabletRunKey` with a variant for each of its keys and `EventLabletRunTemplate` with one for each of its template keys, which the observer matches on with no wildcard arm, so a key the registry gains doesn't build until the observer says what it holds. No span or event builders. It formats them with rustfmt and renders the vendored Markdown templates into `lablet/docs/telemetry/`. Both are rendered under `lablet/target/` and only then moved into place. `cargo xtask weaver generate --check` renders the same way and fails, naming the files, when the tree differs; it runs in pre-commit after `weaver check`.
- `cargo xtask weaver live-check` starts `weaver registry live-check` **without `--v2`** (the v2 index ignores dependency attributes and reports every `gen_ai.*` sample as missing; Weaver issue 1456) on a random free port pair, runs the fake starter and the two-turn example against it over OTLP gRPC with content captured and every `OTEL_*` variable stripped, stops it through the admin endpoint, keeps the report under `lablet/target/`, and fails on a violation or on a report that saw less than the runs emit. Live-check validates attributes (presence, type, enum) and matches log records to events by name; it doesn't match spans to definitions, so span names and required span attributes are held by unit tests in `telemetry-otel` against the generated key lists.
- Upgrading Weaver or bumping the GenAI commit is its own PR; `weaver registry diff` lists renamed `gen_ai.*` attributes and the generated-crate diff makes each one visible.

The tables in this document are the human summary; the registry is the source of truth. When they disagree, the registry wins and this document is corrected. Renames upstream in `gen_ai.*` are tracked as breaking changes to lablet's telemetry contract. Fallback if Weaver becomes unusable: the registry YAML and policies stay, codegen becomes a small xtask step over the committed resolved JSON, and live-check becomes an in-process observer test against the generated key lists.

### `telemetry-otel`

The only telemetry observer. It maps `RunEvent`s to OTel spans and log records exactly once, through `opentelemetry` and `opentelemetry_sdk`, and hands them to the SDK's pluggable `SpanExporter` and `LogExporter` implementations selected by config; there is no second rendering of the contract anywhere. Exporters: **OTLP network** via `opentelemetry-otlp` (gRPC via tonic or HTTP/protobuf, both on `rustls`), and the **OTLP/JSON file** exporter below. Both may be active at once. Over TLS each checks the collector's certificate against the platform's trust roots, the HTTP client through `rustls-platform-verifier` and the gRPC exporter through `rustls-native-certs`, which reads the certificates `SSL_CERT_FILE` or `SSL_CERT_DIR` names in their place; tonic's own default trusts no root, so the gRPC exporter is given the roots for an `https` endpoint, and for one without a scheme unless `OTEL_EXPORTER_OTLP_INSECURE` makes it `http://`, and loads them when it's made, which `build` does and `check` doesn't, so TLS that can't be set up refuses a build alone, under `telemetry.otlp.endpoint` and shown as a refused endpoint is (§7). Batch span and log processors keep export off the loop's path. Every attribute name comes from `lablet-telemetry-registry`. A string literal for one in this crate is a review finding and not a lint failure, since no gate checks for it (`contributing/README.md`). Unit tests assert each span's name and required attribute set against the generated per-signal key lists, since live-check doesn't. Follows the GenAI semantic conventions; anything the conventions lack uses the `lablet.` namespace. The wide event is a log record emitted through the logs API with the root span's trace context set on it. It goes through a log processor of its own, so it's never in a batch with a content record, and a batch a collector refuses for its size can't take the wide event with it: with content captured, every chat record holds the conversation so far, and the records of a long run outgrow a batch. `on` only hands records to the processors and keeps the summary `RunFinished` brought. `Lablet::run` flushes the observer once the loop has returned: the other records are exported first, and the wide event is made then, in an export of its own, so its count of dropped records is whole. An attribute value longer than 1 MiB is cut, so that a record fits in the 4 MiB a collector accepts by default. Each destination, the file and the network, has queues of its own and is flushed on a thread of its own, and each gets its own wide event, whose `lablet.telemetry.dropped_records` counts the records that destination's exporters had refused or dropped by the time the wide event was made, so the file's wide event never waits on the network and counts nothing the network lost. The instrumentation scope carries the registry's schema URL, so a consumer can tell which version of the contract a record follows. The flush after a run and the shutdown each run from a blocking task and each wait at most five seconds for a destination; the SDK's batch processors wait on an export for as long as it takes, and the exporter's own timeout, ten seconds unless `OTEL_EXPORTER_OTLP_TIMEOUT` says otherwise, is what bounds one export, so a port that refuses costs about a second of retries and a collector that accepts a connection and never answers costs at most both bounds, ten seconds, before the process exits. The config's `headers` are set on each request after the exporter has merged `OTEL_EXPORTER_OTLP_HEADERS` over what its builder was given, through a gRPC interceptor and a wrapper of the HTTP client, so the config's win by name; with the config's endpoint the environment's headers aren't sent at all.

The exporter is flushed before the process exits.

### OTLP/JSON file exporter (in `telemetry-otel`)

A `SpanExporter` and `LogExporter` pair that writes each export batch as one line of OTLP/JSON, the protobuf JSON mapping of `ExportTraceServiceRequest` and `ExportLogsServiceRequest`, to `lablet-<run_id>.otlp.jsonl` in the working directory by default, any path, or stderr with `-`. This is the format the OpenTelemetry Collector's file exporter writes and its OTLP JSON file receiver reads, so a file written without a collector can be replayed into one later, or into any tool that speaks OTLP. Each line carries the full resource and instrumentation scope, so a file is byte-for-byte the data a collector would have received: spans with start and end times, status, events, and attributes; log records including the wide event and, when captured, the content records. No lablet-specific envelope exists; the registry describes the attributes and OTLP describes the structure. Always available, no endpoint needed, and the default whenever the network exporter is off, by the config or the environment (§7). Flattening is the consumer's first step, which DuckDB, DataFusion, jq, and the collector all do directly.

Lifecycle: the providers and exporters are built once per `Lablet`, before any run id exists. On `RunStarted` the observer hands the file exporter the run's path (the `lablet-<run_id>` default); a fixed `telemetry.file.path` receives every run of that `Lablet`, appended. The file is opened at the start of each run, so a file that was moved between two runs keeps the first and the path gets the second. After a write that failed partway, the next line starts on a line of its own. That holds of standard error too, across runs, since every run writes to the one stream. `Lablet::run` flushes the observer before it returns, which exports the run's other records and then makes the wide event and exports it, so the file is complete when `run` returns and a caller may read it immediately. Serialisation uses `opentelemetry-proto` with the `with-serde` feature and the same `group_spans_by_resource_and_scope` and `group_logs_by_resource_and_scope` transforms the OTLP HTTP/JSON path uses, written compact (`serde_json::to_string`, one request per line, newline terminated), which yields hex ids, stringified 64-bit integers, and camelCase names as the OTLP/JSON mapping requires. Readers dispatch on the top-level `resourceSpans` or `resourceLogs` key, as the Collector does, because the prost serde derives don't reject unknown fields.

Library and binary in one package. `lib.rs` exposes:

A `Lablet` may run many times. Each `run` gets a `RunContext` of its own: the run id the request names or a fresh one, the request's labels, and the time it started. So a caller that runs many tasks on one `Lablet` can say which run is which, in the record and before the run starts. MCP servers are started again for each run after the first unless `tools.mcp_lifetime` is `lablet` (§6), and `shutdown` is the last teardown. `run` takes the `FinishedRun` that `RunService::run` returns, writes its transcript to `run.transcript_path` when that's set, and returns it whole, the outcome in its summary. `RunFinished` is emitted inside `RunService::run`, before the write, and the wide event is made from it: `lablet.run.transcript_path` names where the transcript is written rather than reporting a file that already exists. A write that fails is reported on the diagnostic log and leaves the outcome alone, as an observer's export failure does (§5); the run measured what it measured either way. Runs on one `Lablet` are sequential.

While the build is in progress, a config that selects an adapter whose crate doesn't exist yet makes `build` return `BuildError::Unsupported { kind, phase }` naming the build-plan phase that delivers it; config validation, including the `api_key_env` check, runs before adapter selection and doesn't depend on the adapter. `check` is that validation and no more: it substitutes `${VAR}`, checks every setting, the key's variable, the files the config names and the root, and builds the tool set, and it stops before the provider is selected, so a config whose provider has no adapter yet passes it. `BuildError::class` says which of the three prefixes below a refusal takes; every refusal `build` and `check` make is `config:`. Two outcomes are "identical" when they're equal after removing `run_id` and `duration_ms`. A relative path in a config starts at the working directory. `telemetry.resource` goes to the observer when it's built, so the resource is one for every run of a `Lablet` and a run's context holds none.

`main.rs` only does effects: clear the process's `PR_SET_DUMPABLE` flag on Linux, so a command can't read lablet's environment through `/proc` (§6), parse args with `clap` derive, install a `tracing` subscriber on stderr filtered by `RUST_LOG` (default `warn`) for lablet's own diagnostics, load config, install Ctrl-C and `SIGTERM` handling into the `Cancellation` port, since `SIGTERM` is what a container sends, so either fires the run's `CancelHandle` and the run stops with `cancelled`, `build`, `run` (which writes the transcript), print outcome, flush telemetry, print one human-readable summary line on stderr (stop reason, turns, tokens, tool calls, duration, as `completed: 7 turns, 12,345 tokens, 5 tool calls, 12.3s`; suppressed by `--quiet`, and by a telemetry file path of `-` once `${VAR}` is substituted, which `telemetry_on_stderr` says before the build, so that OTLP lines and the summary don't share stderr), exit. For a `max_total_tokens` stop the line gives both numbers and says what they count, as `token budget reached: 100,412 of 100,000 tokens`. Diagnostics and telemetry are separate: the diagnostic log is about lablet, the telemetry is about the run. A telemetry file path of `-` turns the diagnostic log off too, unless `RUST_LOG` is set and not empty, so nothing of lablet's own lands between two OTLP lines. What a command writes on standard output, the outcome, `check`'s answer or the schema, is written in one place; a reader that closed its end, as `head` does, is said on standard error, and the exit code stays what the command's work says. Clearing the flag is the one thing only `main.rs` does: it's a setting of the whole process, so it's the binary's to make and not the library's, whose caller owns the process.

```
lablet init [--provider anthropic|openai|fake] [dir]    # write a working starter config into dir, . by default (and a script for fake), writing over nothing
lablet run --config lablet.yaml [--prompt "..." | --prompt-file f | stdin] [--run-id id] [--task id] [--experiment id] [--trial id] [--set key=value ...]

```

`check` never contacts the model provider. It validates the config, checks that `api_key_env` names a set, non-empty variable when required, starts every MCP server and lists their tools, then exits. It prints the name of each tool a run is offered on stdout, a line each, or with `--resolved` the resolved config as YAML, which reads back as a config with the same digest, and ends on stderr with three lines: `withheld:` and the variables no command inherits; `cut:` and the names whose values no result shows, a variable's name or the key of a value written in the config, with a note after a variable whose value is unset, empty or under the 16-byte floor and so isn't cut, as `OTLP_TOKEN (under 16 bytes, not cut)`; then `passed: 2 tools`. A list with nothing in it reads `none`, and no line holds a value. A refusal exits 1. A provider rejecting the credentials is a run that ends with `provider_error`: `RunStarted` is emitted before the first call, so the run has begun, its outcome is printed, and the exit code is 2 (§1). `run` with no prompt source reads stdin; a blank prompt, empty or only whitespace, is a config error. `--run-id`, `--task`, `--experiment` and `--trial` fill the run request, so the CLI labels a run as the library does; they're flags and not config keys, because they name a run and the config describes every run made from it.

Error messages name the config key, line, offending value, and accepted values, and distinguish config errors, MCP server startup failures, and provider rejections. A message shows a config value as it was written, before `${VAR}` substitution, so nothing from the environment reaches stderr. `model.api_key_env`'s value, which must be the name of a variable, is shown only when it's written in capital letters, digits and `_`, as environment variables conventionally are and few key formats are, so the message for an unset `ANTHROPIC_API_KEY` names it. Any other value may be a key pasted there by mistake, and a message about it names `model.api_key_env` and not its value. Each class has a fixed prefix (`config:`, `mcp:`, `provider:`) so tests and scripts can match them. A provider rejection is a run that began, so its message, `provider:` and the error its outcome holds, is printed on stderr beside the outcome, unless the telemetry is on stderr; `--quiet` leaves it, since it isn't the summary line. A value set by `--set` is named as set by an override, and so is a setting that holds one, where a value in the file is named by its line.

A line of the diagnostic log holds no content, no header value, and an endpoint only as the config writes it. The OpenTelemetry crates log through the same subscriber, and their targets, `opentelemetry`, `opentelemetry_sdk` and `opentelemetry_otlp`, are held to `warn` unless `RUST_LOG` names one of them, since at `debug` the exporter prints the endpoint it resolved; so are the network crates under the exporter, `tonic`, `tower`, `hyper`, `hyper_util`, `h2`, `reqwest` and `rustls`, which print the address they connect to.

Lablet inherits the OpenTelemetry environment, and a field the config states wins (`decisions.md`, 2026-10-01). The exporter reads the `OTEL_*` variables itself, and lablet calls a setter only for a field the config states, so a field the config leaves out falls through to the signal's variable, the generic one, then the specification's default. What's read, and what for: `OTEL_EXPORTER_OTLP_ENDPOINT`, `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` and `OTEL_EXPORTER_OTLP_LOGS_ENDPOINT`, any of which, set and not empty, turns the network exporter on when `telemetry.otlp.endpoint` is null, each signal going where the exporter resolves it and the environment's headers with it; `OTEL_TRACES_EXPORTER`, whose value `none` turns the exporter off whatever else is set, as `telemetry.otlp.enabled: false` does, while any other value leaves it on, since lablet has one network exporter; `OTEL_EXPORTER_OTLP_PROTOCOL`, read only when the exporter is on and `telemetry.otlp.protocol` is null, which is `grpc` or `http/protobuf`, any other value, `http/json` among them, being refused by `check` and `build` under `telemetry.otlp.protocol`, naming the variable and the value; `OTEL_EXPORTER_OTLP_HEADERS` and its signal forms, which the exporter merges over the code's, so the config's headers are set after that merge and win by name, and which apply only with the environment's endpoint: with the config's endpoint they're taken off every export, so a token set for one collector never reaches another; `OTEL_EXPORTER_OTLP_TIMEOUT` and its signal forms, which bound one export and stay the environment's, since no setting states one; `OTEL_EXPORTER_OTLP_INSECURE` and its signal forms, which the exporter applies only to a gRPC endpoint written without a scheme, so an insecure endpoint writes `http://`, and which lablet reads only to tell whether such an endpoint needs trust roots (§6); and `OTEL_RESOURCE_ATTRIBUTES`, whose attributes every export carries as defaults beneath `telemetry.resource`, which wins a key both name, while `service.name` and `service.version` stay lablet's whichever names them. `telemetry.otlp.enabled: false` beside a stated endpoint is refused by its key as a setting without effect, naming the endpoint as written. Each of the three header variables is a secret of the inherited class whenever it's set, sent or not: inherited by every command, since the exporter in a child reads it too, and its value, whole and as each header it decodes to, cut out of every result; `check` lists it under `cut:` and never under `withheld:`. The user information of each of the three endpoint variables is one too, when it has any: cut in each form the config's endpoint's is (§6), and the variable listed under `cut:`. An endpoint from any of the three variables, or `telemetry.otlp.endpoint`, that the exporter doesn't accept is refused by `check` and `build` under `telemetry.otlp.endpoint`, naming the variable and never its value, and a stated one is shown as the config writes it, or with no value when that holds an `@`, since user information is a secret and where it ends can't be told once it may hold a `/` not written as `%2F`; `telemetry.otlp.endpoint` set to nothing states none. Not read: `OTEL_EXPORTER_OTLP_TRACES_PROTOCOL` and `OTEL_EXPORTER_OTLP_LOGS_PROTOCOL`, since one transport serves both signals; `OTEL_LOGS_EXPORTER`; `OTEL_SERVICE_NAME`, since the service is lablet; `OTEL_EXPORTER_OTLP_COMPRESSION` and its signal forms, which the exporter reads and can't apply, since neither `gzip` nor `zstd` is compiled in, so a value other than `none` is ignored with a warning in the diagnostic log; and `OTEL_SDK_DISABLED` and the TLS certificate variables, which the Rust SDK doesn't read either. The SDK's batch variables, `OTEL_BSP_*` and `OTEL_BLRP_*`, change nothing: the queue size, the batch size and the delay are lablet's, and the processors lablet uses never apply the export timeout (§6). `check --resolved` prints the config as written, `endpoint: null` and `protocol: null` included, and nothing the environment holds; the digest leaves the `telemetry` section out, `enabled` with it.

`--set` applies dotted overrides to the raw config tree before deserialisation; values are parsed as YAML scalars, and a value that YAML would read as a list or a mapping, such as `-`, is the text as it's written. A number in the key is a place in the list before it, and an override that gives one where the config writes no list is refused. Environment variable substitution `${VAR}` is applied to string values after that; an unset variable is a config error. It applies to the settings that hold text, and it's made when a config is checked or a `Lablet` is built, so a `Config` holds `${VAR}` as it's written and the digest and every message see it that way. A `${VAR}` written in any other setting, such as a duration or a provider, is that setting's value, and the setting refuses it. `$${` is the text `${`, and a `${` that begins no variable's name is a config error. Durations use humantime syntax. No provenance tracking, retired-key roster, or inert-key warnings: unknown keys are errors and that's the whole config policy.

A setting exists where the references behave differently on something that changes a measurement, or where an experiment needs one factor held apart (`decisions.md`, 2026-09-28). Each default is the primary reference's behaviour where the reference has one. `product/research/parity/matrix.md` has the evidence for each, and marks the defaults that wait on a capture.

A setting the config states and the selected provider can't apply is a `config:` error that names the setting and the provider: `seed` with `anthropic`, `thinking` with `openai`, `effort` or `reasoning_replay` with the wrong API, `cache` with anything but `anthropic`, `base_url` with `fake`. A setting that was ignored would make two runs look different that weren't, and an experiment on it would measure nothing. The rule is about what a config states. A default the provider can't apply isn't an error: it's left out of the resolved config, and so out of the digest.

A profile is a config file and not a config key. The defaults above are the primary reference's, and lablet ships an example config for the secondary, which sets the values where it differs. So a profile can only set values, and a behaviour no setting reaches is a known difference (`product/research/parity/`).

Config digest (`lablet.config.digest`) is a SHA-256 of the canonical JSON form of the **resolved** config (defaults filled in) after `--set` overrides but before `${VAR}` substitution. It covers the settings that say what a run does and leaves out the ones that say where its output goes, `run.transcript_path`, `run.transcript_format` and the `telemetry` section, and the ones that are credentials: every value of an HTTP server's `headers`, and the user information of `model.base_url` and a server's `url`. So two runs that differ only in where they write, or only in a rotated token, share a digest, and the digest groups them. `tools.builtin.env` stays in it, since what a command starts with is part of what a run does. Any value injected from the environment never enters the digest. Two configs that state the same settings in other words share a digest: a default spelled out or left out, a duration written another way, keys or built-in tools listed in another order, and `tools.allow` and `tools.deny` in another order or with a name twice, since each is resolved as a set. So do two that differ only in settings the resolved config marks as not applied and leaves out: the `model` settings the selected provider can't apply, `tools.output_preview_bytes` unless the cut is `preview`, `tools.output_cut` with it when `tools.max_output_bytes` is null, `tools.mcp_lifetime` and `tools.mcp_result` when `tools.mcp` is empty, and the `root`, `timeout`, and `env` of `tools.builtin` when no built-in tool is enabled. Any other setting changes the digest whether or not it has an effect, as the retry settings do when `run.max_retries` is 0 and `prompt.skills_mode` does with no skills. A default change in a new lablet version changes the digest, which is why `gen_ai.agent.version` sits beside it in the wide event.

Two more digests say what the config can't, and the loop takes both from what it sends (§5). `lablet.tools.digest` is of the tool specs as offered, in order, and `lablet.prompt.system_digest` of the system prompt. Two variants that differ in a tool's description, in the build of a server started by the same command, or in the text of a prompt file have the same config and different digests, so the variable under test is in the record. A skill loaded through the tool puts only its name and description in the system prompt, so from phase 10 `lablet.skills.digest` covers the skill files themselves.

## 8. Versioning

- One workspace version, semver. The config schema, the outcome JSON, the transcript JSON, and the telemetry registry are the public contract; a breaking change to any of them is a major bump. Each document carries a `schema_version` of its own, which rises with a change a reader of the old form could misread.
- `CHANGELOG.md` in keep-a-changelog format with an `Unreleased` section. `cargo xtask changelog` fails when `lablet/schema.json`, `lablet/telemetry/registry/`, `lablet/tests/fixtures/outcome.json`, or `lablet/tests/fixtures/transcript.json` differ from `main` and `Unreleased` has no entry. The base is the merge-base with `origin/main`; on `main` itself CI sets `LABLET_CHANGELOG_BASE` to the commit before the push. Uncommitted and untracked files count. "No entry" means the body of `## [Unreleased]` is unchanged since the base or has no list item. An unresolvable base warns and passes. CI checks out full history so the comparison works.
- Every third-party crate is pinned to an exact version in `[workspace.dependencies]`; a version bump is its own commit, never mixed with feature work. A member's manifest only inherits (`name.workspace = true`, with at most `features`, `optional`, or `default-features` beside it), so no version, path, git source, or rename exists outside that table, and each entry there has a comment on the line above it saying why. `xtask` is its own workspace and pins its own dependencies exactly; `lint-manifests` requires a crate pinned in both places to carry the same version. The lints refuse the Cargo features lablet doesn't use (member globs, `exclude`, a root package, `[patch]`, `[replace]`, cargo-config `patch`, `paths`, `source`) rather than model them.
- `rust-version` in the workspace `Cargo.toml` is the MSRV; policy is the pinned toolchain minus two minor versions, raised only in a minor release.

## 9. Testing

- Unit tests live beside the code in a sibling file declared `#[cfg(test)] mod tests;` (`src/foo.rs` with `src/foo/tests.rs`, or `src/tests.rs`), never as an inline `mod tests { ... }` body, so the coverage floor can exclude test code by file name instead of parsing Rust. The gate enforces this in the three floor crates (`lablet-model`, `lablet-policy`, `lablet-run`); elsewhere it's the convention. Policy and model crates are the bulk and need no runtime: `Pending::answer`, the model's one async function, is polled to completion in its tests with `std::task::Waker::noop()` and futures the test controls.
- `lablet-run` is tested end to end with hand-written fakes for every port, including a fake clock. No mocking framework.
- Provider adapters are tested against `wiremock` with recorded payloads, including error classification and content-block round trips.
- `lablet-conformance` holds case sets for `ToolExecutor` and `RunObserver`, pulled in as dev-dependencies by each adapter.
- `lablet-test-mcp-server` is an rmcp stdio binary with tools that echo, sleep for N seconds, return an image, return `structuredContent` beside its text, report the server's environment, and make the server exit after N calls, one of them annotated `readOnlyHint`, and with server instructions; cargo sets `CARGO_BIN_EXE_lablet-test-mcp-server` only for the server package's own tests, so how tests in other packages locate the binary is an open question (§10). A `--hang-startup` flag never completes initialisation.
- One integration test target per crate (`tests/it/main.rs`).
- A smoke test in `apps/lablet` runs a full loop with `provider-fake` and the OTLP/JSON file exporter and asserts on the spans and log records read back from the file. Cancellation scenarios drive the `Cancellation` port directly.

## 10. Open questions

Recorded here so they're not lost; none block the first build.

- Streaming responses. `run.provider_timeout` is ten minutes so that a response of `model.max_tokens` can finish; an idle timeout on a stream would be the better bound.
- A `lablet.run` metric set alongside traces, once there is a consumer for it.
- A `check --probe` flag that makes one minimal provider call.
- Which MCP server served a tool call isn't on the tool span as an attribute of its own. A prefixed tool name holds the server's, but a server with `names: own` leaves no trace of itself on the span: `ToolSource::Mcp` knows the server, and the wide event lists the servers, but no attribute joins a call to its server. The conventions have none, so it would be a `lablet.*` extension.
- How `lablet-tools-mcp`'s tests locate the `lablet-test-mcp-server` binary: cargo sets `CARGO_BIN_EXE_<name>` only for tests of the package that defines the binary, so a cross-package mechanism (a build through `escargot`, or hosting the MCP scenarios in the server's own package) must be chosen in phase 8. An artifact dependency isn't an option on the pinned stable toolchain: cargo rejects it without nightly `-Z bindeps`. Nor is a plain dev-dependency on the server package, which cargo ignores because the package has no library.
- A `turn` span under `invoke_agent`, if per-turn grouping in trace viewers proves worth an extra span level.
- The deferred `lablet.*` extensions in the research catalogue (working time, cache hit ratio, time split, event sequence).
- Exporting the transcript as an ATIF v1.8 trajectory, planned for phase 10.
- How a run ends when an MCP server can't be started at the start of a run, or comes back offering other tools than `build` listed, which `tools.mcp_lifetime: run` makes possible after a `Lablet`'s first run. Phase 8's design settles it.
- Whether explicit mode reminds the model when a response ends with no `task_complete` call, as several harnesses do, where lablet stops with `ended_without_completion`. The capture of the primary reference says what it does.
- The features of phase 12: tool search, summarising the conversation, resuming after a response is cut off, reconnecting a remote MCP server, and passing an image in a tool result through. Until each is built it's a known difference from the references (`product/research/parity/`).
- A Parquet exporter for developers without a collector: a third `SpanExporter` and `LogExporter` pair beside OTLP and the OTLP/JSON file, probably in the OTel-Arrow (OTAP) layout. Deferred because choosing the file layout is a contract decision; the OTLP/JSON file covers the lightweight case today.
