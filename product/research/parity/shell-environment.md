# Command and server environments

What a shell command and a stdio MCP server inherit from the harness that starts them, in the eight loops of lablet's parity research, and what lablet decided for its own. A claim both of them labelled carries the weaker of the two labels, a claim the check didn't uphold is left out, and a fact that only the check supplied carries the check's own label. Lablet's own documents are cited as `product/...` and its workspace as `lablet/...`, as they stood on 2026-09-29.

## The question

At the survey, lablet's `bash` started every command with a cleared environment plus eight variables (`HOME`, `PATH`, `SHELL`, `USER`, `LANG`, `TERM`, `TMPDIR`, `TZ`) and what `tools.builtin.env` adds, and a stdio MCP server was specified to start the same way, so that the model can't print the API key with `env` (`product/spec.md` section 6, `tools-builtin` and `tools-mcp`; `product/acceptance.md` T16 and T20). The owner wants the environment a framework prepared for a task to reach those commands, and wants lablet secure by default as far as it can be. So the question is what the eight loops pass to a command and to a stdio server by default, whether they keep their own credentials out, and which of lablet's four options that evidence and the two scope rules ([README](README.md), What lablet copies) support.

**Claude Code.** Pinned at 2.1.281 and read from its public sources only. The documents say sandboxed Bash commands inherit the parent process's environment, credentials included, and point to `sandbox.credentials` or the scrub to remove them (sandboxing, Scope, likely). A settings `env` value is written into the process environment and reaches every subprocess, which is why the documents send API credentials to `apiKeyHelper` instead (env-vars, Precedence; settings-reference, the `env` setting; likely). Since 2.1.128, subprocesses (Bash, hooks, MCP servers and LSP) no longer inherit `OTEL_*`, so an instrumented command doesn't pick up the CLI's own endpoint (`CHANGELOG.md@v2.1.281`:4011, likely). Nothing public removes `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN` or cloud credentials by default, so they reach commands (likely: the scrub's entry, which removes them only when it's set; issue 62156, where a user reported a command printing the key at 2.1.150). The scrub, `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB`, is opt-in. It removes Anthropic and cloud provider credentials, any other variable Claude Code recognises as a credential, and credentials in package registry URLs, from Bash, hooks and stdio servers, and on Linux it runs Bash in its own PID namespace (env-vars, the scrub's entry; `CHANGELOG.md@v2.1.281` sections 2.1.83 and 2.1.98; likely). Whether the harness also withholds its own claude.ai OAuth token, `CLAUDE_CODE_OAUTH_TOKEN`, or other internal variables from commands isn't in its public sources (unknown), and the probe at the end shows it for any that are set. `CLAUDE_CODE_PROVIDER_MANAGED_BY_HOST` is set by platforms that embed Claude Code and route its model provider for it, and makes it ignore provider, endpoint and credential variables in settings files. The documents say nothing of subprocesses (env-vars, the flag's entry, read in revision, likely), so whether the flag changes a child's environment is unknown, and the probe settles it. Run through the Python Agent SDK, as the primary is pinned, the CLI gets the application's whole environment with no credential filtered. The SDK sets `CLAUDE_CODE_ENTRYPOINT` to `sdk-py` unless the caller sets it, adds its own version variable, and never sets the host flag (anthropics/claude-agent-sdk-python src/claude_agent_sdk/_internal/transport/subprocess_cli.py@v0.2.159:810-866). So a key a framework hands the pinned primary reaches its commands (likely). A stdio server inherits the shell's environment unless `CLAUDE_CODE_MCP_ALLOWLIST_ENV` is set to 1, which gives it a minimal baseline the documents don't list, plus its `env` (env-vars, the variable's entry, likely). A server also gets `CLAUDE_PROJECT_DIR` (mcp, likely), and since 2.1.154 `CLAUDE_CODE_SESSION_ID` and `CLAUDECODE` (`CHANGELOG.md@v2.1.281`:3404, likely). A command gets `CLAUDECODE`, `CLAUDE_CODE_SESSION_ID` since 2.1.132, and `CLAUDE_CODE_CHILD_SESSION`, which tells a command from a server (env-vars, the `CLAUDECODE` entry; `CHANGELOG.md@v2.1.281`:3940; likely). A server's environment wasn't observed, and one report says the Windows desktop app at 2.1.240 started servers with about sixteen names (issue 90074, unknown), so some entrypoint may narrow it. The sandbox is off by default (settings-reference, `sandbox.enabled`, likely). The secure-deployment guide puts isolation on the deployer, and suggests keeping credentials outside the agent's boundary behind a proxy that adds them to its requests (agent-sdk/secure-deployment, Security boundaries, likely).

A second snapshot that filters through the policy and writes no file exists, and it's off (codex-rs/features/src/lib.rs:1020-1025). The sandbox is on by default: `workspace-write` when the project has a trust decision and `read-only` otherwise, and both let a command read any file (codex-rs/config/src/config_toml.rs:792-801; codex-rs/protocol/src/permissions.rs:594-612). The responses-api-proxy keeps the key out of Codex entirely: a privileged user runs it with the key on its stdin, and Codex is pointed at it as a provider (codex-rs/responses-api-proxy/README.md). ## The pattern

### Shell commands

The primary inherits its whole environment and withholds `OTEL_*` (likely). `ANTHROPIC_API_KEY` isn't withheld, so in its ordinary entrypoints, and through the Agent SDK as it's pinned, the provider's key reaches every command (likely). It withholds the provider's keys only under the opt-in scrub. Whether it also withholds its own OAuth token, and whether the host flag or any of its product entrypoints changes what a command gets, is unknown. Nothing in the evidence makes the scrub lablet's position. Lablet makes its own provider calls with the key it's given, which is the CLI's place and not the host's.

The secondary does the same: everything less five internal names, with `OPENAI_API_KEY` passed on. Its opt-in filters are the richest of the eight, none of them is on by default, and on its default path they don't hold, because the snapshot re-exports what they removed and writes the values to disk (likely).

The field agrees. All eight inherit by default: Codex, mini-swe-agent, OpenCode, Goose and Gemini in source, OpenHands on its default tmux path (likely), and the primary and Copilot by their documents (likely). None clears a command's environment by default on an ordinary install. The nearest are Gemini's strict mode, which only a GitHub CI run triggers, Codex's opt-in `core` policy, and Goose under Flatpak, by the way `flatpak-spawn` works (likely). None is known to remove the model provider's key by default in its ordinary entrypoint. For the primary that's likely, and for Copilot only `GITHUB_TOKEN` is known to pass (likely), while `COPILOT_GITHUB_TOKEN`, `GH_TOKEN` and `COPILOT_PROVIDER_API_KEY` are unknown. Codex withholds its own internal secrets by name. OpenHands does on its subprocess backend and probably not on its default tmux path (likely). Whether the primary does is unknown.

Defaults tighten in some entrypoints. Gemini switches to its strict allowlist under GitHub CI (environmentSanitization.ts:17-20). claude-code-action turns the primary's scrub on when users without write access may trigger it (env-vars, the scrub's entry; anthropics/claude-code-action action.yml@v1.0.236:301; likely). Whether any of the primary's own entrypoints tightens its defaults isn't in its public sources (unknown). No other loop was found to tighten, and Copilot's Actions guide only warns (likely). So two of the eight tighten under CI, one of them only for untrusted users. Lablet is always started by automation, but by the framework that prepared its environment and not by a CI run that others can trigger, so whether those cases are lablet's is a reading, and it's the owner's.

They split on the opt-in filters: a named list with recognised credential names (the primary's scrub), substring patterns (Codex's default excludes, Gemini's redaction), a check of values (Gemini), and an allowlist (Codex's `core` and `include_only`). The primary's scrub removes named credentials and other variables it recognises as credentials (env-vars, the scrub's entry, likely). How it recognises them isn't documented (unknown).

The primary also withholds `OTEL_*`, so an instrumented command doesn't export to the harness's collector (likely). No other loop is known to, and Goose does the reverse. Lablet's network exporter isn't built yet (phase 6), but the crate it pins, opentelemetry-otlp =0.33.0 (`lablet/Cargo.toml` line 143), reads `OTEL_EXPORTER_OTLP_HEADERS` or its per-signal form from the process environment and adds it to the export's headers beside the configured ones, and takes the endpoint from `OTEL_EXPORTER_OTLP_ENDPOINT` when none is given (open-telemetry/opentelemetry-rust opentelemetry-otlp/src/exporter/tonic/mod.rs@opentelemetry-otlp-0.33.0:221-226, 357 and 603-613; opentelemetry-otlp/src/exporter/http/mod.rs:294-297; read in revision). So a collector credential in lablet's environment is a secret lablet may read without its config naming it. Whether phase 6 builds its exporter on that path is unknown, and it's settled when phase 6 builds it. What the harnesses add to a command's environment (markers such as `CLAUDECODE` and `GEMINI_CLI`, a pager set to `cat`) is a separate behaviour and isn't put to the rules here.

### Stdio MCP servers

The primary's servers inherit the shell's environment plus their `env` and a few markers, unless `CLAUDE_CODE_MCP_ALLOWLIST_ENV` narrows them to a baseline (likely, from the documents and the changelog and not observed). The secondary gives a server eleven names, custom-CA paths and what its config names, in a cleared environment. So the two references split in their ordinary entrypoints.

The field splits too. OpenCode and Goose inherit everything. Gemini inherits less its redaction, which it forces on for servers. OpenHands gives the MCP Python SDK's six names. Copilot's documents and one commenter's two wordings disagree (unknown), and mini-swe-agent has no MCP client. Of the seven that start stdio servers, four inherit in some form (the primary likely), two allowlist, and one is unknown. That's most of the seven whatever Copilot does, as long as the primary's servers inherit.

The recorded tie-break points the same way. `product/decisions.md` (2026-09-25, Lablet's behaviour follows named reference loops) has OpenCode, Copilot CLI, Goose, OpenHands and Gemini CLI break ties where the references are silent or split, and on servers they come out three to one for inheritance, OpenCode, Goose and Gemini against OpenHands, with Copilot unknown. So parity favours inheritance for servers (likely, until the primary's server environment is observed).

The MCP SDKs lean the other way. The TypeScript SDK at v1.29.0 and the Python SDK at v1.28.1 give a server six names unless the host passes more. rmcp, the Rust SDK lablet pins at =3.4.0 (`lablet/Cargo.toml` line 113), leaves the environment to the caller's command: its child-process builder sets only standard input, output and error (modelcontextprotocol/rust-sdk crates/rmcp/src/transport/child_process.rs@rmcp-v3.4.0:115-165, read in revision, and the same at 3.3.0, read for Goose). The hosts that inherit pass the environment on themselves.

Three loops start a server differently from a command: Codex and OpenHands give servers less, and Gemini filters servers and not commands. The primary by default, OpenCode and Goose treat the two alike, though the primary's allowlist switch applies to servers only. So starting both alike is lablet's own reason, below, and not a pattern.

## Against the first rule

### Shell commands

The behaviour is that a command starts with the environment the harness was started in.

1. **It changes what the model is sent and how a run proceeds.** A command that can't find its toolchain, its virtual environment or its proxy fails, and the model is sent the failure and acts on it. What `env` prints is sent to the model, and written to the transcript when one is configured.
2. **It bears on what a user varies,** whenever a variant runs commands: a bash tool surface, a skill that names the commands to run, bash against an MCP server. With the short list, a variant that depends on the task's toolchain fails in lablet and works in the harness its result is meant to carry over to. It doesn't bear on a comparison of models or prompts over MCP tools alone.
3. **It's a pattern.** Every loop inherits: the secondary and four of the evidence loops in source, OpenHands on its default path (likely), and the primary and Copilot by their documents (likely).
4. **It can be specified and checked.** The primary's documents say commands inherit its environment (likely), the secondary's source shows it, and a scenario that sets a variable in lablet's environment finds its name in what `env` returns, which the recorded request holds.

So inheritance is inside the line, and the short list is a difference that no loop surveyed has by default.

Withholding lablet's own secrets isn't what either reference does as pinned. The primary run through the Agent SDK passes the provider's key to commands (likely), and the secondary passes `OPENAI_API_KEY`. It can bear on a variant, too: a skill whose script calls the provider's SDK, a command that runs `claude -p` as a sub-agent, or a task whose tests call the API works in the primary's ordinary entrypoint and fails in lablet unless the config passes the key on. Part 3 fails, since no loop withholds the provider's key by default in its ordinary entrypoint. So it's lablet's own safeguard, taken for safety and recorded as a known difference from both references, as the run timeout is (matrix row B7), with `tools.builtin.env` as the way to pass the key on by name. The same holds for every safeguard below: redacting values from results, withholding the variables lablet substitutes, and the rest. They're lablet's, outside the parity rules, and each is recorded as a difference. The references' own lists of internal names aren't copied, since they're their names and not lablet's.

### Stdio MCP servers

1. **Holds.** A server that lacks a variable it needs fails to start or fails its calls.
2. **Holds,** more directly than for bash, because the server is often the variant.
3. **Holds on the count, if the primary's servers inherit.** Four of the seven loops that start stdio servers inherit in some form, which is most, whatever Copilot does. That's so whether the rule's other reference means only the secondary or the six evidence loops too, since its alternative, most of the loops surveyed, is met either way. Counting mini-swe-agent, which starts no server, would give four of eight, but a loop with no MCP client has no behaviour to count for either side. The primary's part is likely, from its documents and changelog and not observed, and a count near six in the probe takes it away. The recorded tie-break points the same way (above).
4. **Holds.** A scenario with a server that returns its environment's names in a tool result puts them in the recorded request.

So server inheritance is inside the line if the probe confirms the primary, and outside it if the probe shows an allowlist, since the references would then agree. Rule 1 is a condition for building and not an order, so the owner can still keep the short list for servers on security grounds: a server is code the config's author chose and whose needs they know, while a task image's needs are open-ended. Lablet's own reason points the other way. A shell served over MCP and the built-in `bash` should start alike, so that comparing them measures the surface and not the environment. That's lablet's reason and not a pattern, since the field is three and three on starting the two alike.

## Options for lablet

Every option shares one limit. A command runs as the user lablet runs as, so it can read lablet's own environment from the process table (`product/spec.md` section 6, `tools-builtin`; `product/decisions.md`, 2026-09-29, Phase 4, closed). The primary closes that read only with an opt-in: its scrub puts Bash in a PID namespace on Linux (env-vars, the scrub's entry, likely), and its sandbox is off by default (likely). The secondary's sandbox is on by default, and where it runs it mounts a fresh `/proc` on Linux, denies `ptrace` and reading another process's memory while the network is restricted, which is also the default, and leaves reading another process's arguments and environment out of its macOS policy (codex-rs/linux-sandbox/src/bwrap.rs:369-383; codex-rs/linux-sandbox/src/landlock.rs:106-127; codex-rs/sandboxing/src/seatbelt_base_policy.sbpl:24-77). That this stops a command reading Codex's environment is read from the policies and not observed (likely). Lablet has levers of its own that work under any option, listed after the four.

### 1. Keep the short list

- **Matches** no loop's default for shell commands. It's close to Codex's opt-in `inherit = "core"` and to Gemini's strict mode under GitHub CI. For servers it matches the secondary, whose eleven names include all of lablet's eight, and OpenHands, and Copilot if its documents are right, and it's close to the primary with `CLAUDE_CODE_MCP_ALLOWLIST_ENV` set.
- **Protects** the key from `env`, and every other variable the framework set, its own secrets included.
- **Breaks** task environments a framework prepared. In a container, the variables an image sets with `ENV` are in the environment of every process run from it (moby/buildkit frontend/dockerfile/docs/reference.md@90b8639e:1306, the source of the Dockerfile reference, read in revision, likely), so they're in lablet's environment and a command can get them only from lablet. The short list drops a toolchain's home, a virtual environment, a proxy and its CA path. Codex forwards custom-CA path variables to its servers even under its allowlist. A config can pass a named variable through `tools.builtin.env` with `${VAR}`, but an unset variable is a config error (`product/spec.md` section 7), so one config can't serve task images that set different variables. T16 and T20 pass.
- **Costs** nothing. `bash` has it since phase 4, and phase 8 specifies it for servers.

### 2. Inherit everything except the variables lablet reads secrets from

- **Matches** the shape of the references' defaults, which inherit less some names of their own: five internal names for the secondary, and at least `OTEL_*` for the primary (likely). OpenHands' subprocess backend has the same shape. The names differ: both references pass the provider's key in their ordinary entrypoints (likely for the primary), so withholding it is lablet's safeguard and a known difference (above).
- **Protects** what lablet itself reads. That's the variable `model.api_key_env` names, and any variable the config substitutes into a value lablet sends: a `headers` value (an HTTP server's, or `telemetry.otlp.headers`) or a URL (`model.base_url`, an HTTP server's `url`, `telemetry.otlp.endpoint`), which the spec already keeps out of error text (M20, `product/decisions.md`, 2026-09-28). `${VAR}` works in any string value, so lablet knows all of these at build. It's also `OTEL_EXPORTER_OTLP_HEADERS` and its per-signal forms, which the pinned exporter may read. A variable the config substitutes into `tools.builtin.env` or a server's `env` is passed on deliberately, and it reaches only the children whose `env` names it, unless it's one of the eight short-list names. So a token meant for one stdio server doesn't reach `bash`, as it already doesn't when it's in an HTTP server's `headers`. A variable substituted into a path, such as `tools.builtin.root`, isn't a secret and stays. Removing an inherited variable whose value equals the key or a header value catches a copy under a second name, at the cost of a comparison per variable at spawn. It has to be limited to values of some minimum length, 16 bytes say, so that a short header value such as an org id or `true` never removes `SHLVL` or `CI`. Gemini's check of values is the nearest precedent, and an exact match is lablet's own. It doesn't protect a copy inside a longer value, such as a bearer header, a URL or a JSON blob, which output redaction catches (below). And it doesn't protect the framework's other secrets: a `GITHUB_TOKEN` or a cloud credential set for the task reaches commands.
- **Breaks** nothing a task environment needs, unless a task needs lablet's own key, as one whose tests call the provider does, or a variable the config routed to one server. The config then names it for `bash` or that server. T16 passes.
- **Costs** little. The `bash` executor starts from lablet's environment and removes names, where it now clears and adds eight. Stdio servers aren't built, so phase 8 builds this in place of the short list. The spec's `tools-builtin` and `tools-mcp` paragraphs, which promise nothing else of lablet's, and the config comments that name the short list change, and so does the mechanism of the builder's decision that a child process gets none of lablet's secrets (`product/decisions.md`, 2026-09-28, What the builder took from the design review; first review, finding 4). Its goal still holds. T16 keeps its assertion. T20 is rewritten to assert that the withheld names are absent and a harmless inherited variable is present, and a new scenario asserts the same of `bash`.

### 3. Inherit everything

- **Matches** mini-swe-agent, OpenCode, Goose and Gemini by default, and the primary and the secondary except for their lists of internal names.
- **Protects** nothing of lablet's.
- **Breaks** T16 and T20, and reverses the builder's finding. Whenever a model runs `env`, the key is sent to the model and lands in the transcript whenever one is configured, and issue 62156 on the primary shows a command printing the key into a session (likely).
- **Costs** the least code, and a decision reversed.

### 4. Inherit everything less names that match patterns

It's judged here on the patterns the owner named, `KEY`, `SECRET` and `TOKEN` as case-insensitive substrings, which are Codex's three (4a), and on a variant of lablet's own that matches a longer list of credential words, most of them only as whole parts of a name, and keeps proxy names (4b).

- **Matches** Gemini's redaction, which is off for commands and always on for its servers, and Codex's default excludes, which are off and which its snapshot undoes on the default path (likely). No loop applies patterns to shell commands by default. The primary removes the variables it recognises as credentials only under the scrub (likely).
- **Protects** the framework's secrets as well as lablet's, as far as their names follow convention. T16 passes for `ANTHROPIC_API_KEY` and `OPENAI_API_KEY`, but `model.api_key_env` may name any variable, so T16 holds for every config only if the configured names are removed too, which puts option 2 inside option 4.
- **Breaks** variables a task needs whose names happen to match, and which ones depends on the pattern. These are reasoned from the patterns and not observed. Under 4a, `SSH_AUTH_SOCK`, `SSL_CERT_FILE` and `NODE_EXTRA_CA_CERTS` survive, and `TOKENIZERS_PARALLELISM` and `PYTHON_KEYRING_BACKEND` are removed, while `PGPASSWORD`, `SENTRY_DSN` and a `GITHUB_PAT` get through. Under 4b, `TOKENIZERS_PARALLELISM` and `PYTHON_KEYRING_BACKEND` survive and `PGPASSWORD`, `SENTRY_DSN` and a `GITHUB_PAT` are caught, but `SSH_AUTH_SOCK` is removed through `AUTH`, which cuts git and ssh off from the agent. Gemini's substrings `AUTH` and `CERT` drop `SSH_AUTH_SOCK`, `SSL_CERT_FILE` and `NODE_EXTRA_CA_CERTS`, the last two of which a proxy with its own CA needs, but that's Gemini's list and not the owner's. A secret a task does need can still be passed by reference: lablet can expand a deliberate `${VAR}` against its whole environment under any option, as option 2 does. Gemini's documented way of passing a host token to a server fails only because Gemini expands against the redacted environment.
- **Costs** a pattern list and a fixed list to choose and keep, and an escape hatch that would be lablet's own design. For commands, neither Gemini's nor Codex's allow list brings back an inherited name its patterns removed: Gemini drops a matching name from the allowed list and checks values first, and Codex's includes don't restore excluded names while its `set` takes only literal values (codex-rs/config/src/shell_environment_policy.rs:13-38 and 92-131). Gemini's servers are the exception, since there the allowed list applies as given. It also needs documents that stay true to the code, where one section of Gemini's configuration reference contradicts its code and another matches it.

### Levers that work under any option

- **Redact lablet's known secret values from every tool result,** before the model and the record see it. Lablet knows the value of every secret it reads: the key, the header values and URL credentials. Cutting them from each result catches what removing names or values from the environment doesn't: a read of lablet's own environment from the process table, `ps eww`, a copy under a second name, and a key inside a longer value. It doesn't catch an encoded copy, since Copilot's users report the agent reading masked values through their raw bytes (likely). Copilot redacts its own token values from output by default (likely), and OpenHands masks every registered secret in every observation. Neither reference does (likely for both), and a user's report of the primary printing the key was closed by a bot as stale (issue 62156). It needs the same minimum length as the check of values. Applied before a result enters the context and the transcript, it keeps H7's promise that the record says what the model was shown (`product/decisions.md`, 2026-09-28). It runs on what the executor keeps, so a cut has to drop a partial match at its edge.
- **Redact by name pattern.** Values of inherited variables whose names match a credential pattern, such as 4b's, are cut from results the same way, while every variable stays in the command's environment. That covers the framework's other secrets against a printout, and a false positive costs one masked string, not a broken tool. It doesn't stop a command using a secret or sending it anywhere. No loop does it, so it's lablet's own design.
- **Withhold the OTLP header variables,** as option 2 does, or have phase 6 build its exporter so that it never reads the environment.
- **Clear `PR_SET_DUMPABLE` on Linux,** which the phase 4 review left open for phase 5's `main.rs` (`product/decisions.md`, 2026-09-29, Phase 4, closed). It stops a same-user command reading lablet's environment from `/proc` (likely, not tested here). Whether anything stops the same read on macOS is unknown.
- **Take the key from a file descriptor, a file or a command** instead of an environment variable. The primary has `apiKeyHelper` (settings-reference, likely). Codex's responses-api-proxy reads the key on its stdin, Copilot has `COPILOT_PROVIDER_API_KEY_COMMAND` (likely), and OpenCode has `{file:path}`. A key that never enters lablet's environment can't be read from it, though a file stays readable by a same-user command. Whether it's in scope is the owner's call.
- **Record what a child inherited,** names only and never values: a digest of the names on the wide event and the names in the transcript document, as H7 does for tool specs. Once commands inherit, their environment varies from host to host (`CI`, the locale, a pager, `OTEL_*`, a proxy), and all of it changes what tools print. Without the record, two runs of one config can differ with nothing to show why.
- **Masking,** set aside. The primary's `mask` mode gives a sandboxed command a placeholder and swaps in the real value at its proxy, on requests to the hosts allowed (sandboxing, Mask environment variables, likely), and Codex's credential broker does the same behind an experimental flag (likely). It serves both wishes in full, and it needs a proxy that terminates TLS, which is more than lablet should carry.

### A setting to choose between policies

The criterion for a setting is in `product/decisions.md` (2026-09-25, Profiles): a setting exists only where a reference behaves differently, or where an experiment needs that factor isolated. The [README](README.md) restates it as a reference behaving differently on something inside the line (Profiles and settings). Rule 2 (2026-09-28) adds that a profile configures behaviours lablet has for other reasons and is never the reason to add one.

For shell commands the references agree on the default, so no reference behaves differently, and there's no policy setting. An experiment that needs a clean or a particular environment gets it from the framework, which decides what lablet starts with. `tools.builtin.env` stays, since it adds variables for other reasons. A safeguard is lablet's own, and like the run timeout and the token budget it may have a setting of its own (matrix row B7). The framework can already remove a name from lablet's environment when it starts lablet, so a list of names to withhold would add nothing but a second place to say it.

For servers the secondary's allowlist is a reference behaving differently, so the criterion allows a switch, `inherit` as the primary does (likely) or `short_list` as the secondary does. Lablet has to start servers with some environment for other reasons, so under rule 2 the switch configures a behaviour lablet has. Once bash inherits, though, the short list's only remaining reason would be the switch, which comes close to what rule 2 forbids. Nothing in the survey shows a comparison that needs it, so it waits for a transfer check that does, as the setting for malformed arguments waits (matrix row C2).

Name-pattern redaction is the one lever lablet could add for the framework's other secrets without removing anything, and it would get an on and off setting, as the run timeout has its own.

## What lablet decided

On 2026-09-30 the owner decided the case of shell commands and left the case of servers open, and `product/decisions.md` records it.

- **Bash inherits, less lablet's own secret variables.** That's option 2: a command starts from lablet's environment, less the variables lablet reads secrets from, with `tools.builtin.env` on top. It's a known difference from both references, which pass the provider's key on (likely for the primary as pinned), taken for safety as the run timeout is. A task that needs the key gets it by name through `tools.builtin.env`. There's no policy setting, because the references agree on the default. The exact set of withheld names is the spec's to state (`product/spec.md` section 6, `tools-builtin`).
- **Lablet's known secret values are cut from tool results,** before the model and the record see them, as the first lever above describes, with one difference: the cut runs before the output reaches `KeptOutput`, and a possible match at the end of a piece is held back until what follows settles it, rather than dropped. See `decisions.md`, 2026-09-30.
- **The framework's other secrets are left to the framework.** A `GITHUB_TOKEN` or a cloud credential set for the task reaches commands, which can use it and send it anywhere, and it reaches the model whenever a command prints it. Keeping it out is the job of the framework, which decides what lablet starts with, as the primary's secure-deployment guide puts isolation on the deployer (likely).
- **Stdio servers wait for phase 8 and a probe the owner runs.** Phase 8 builds servers, and the probe decides between option 2 and the short list for them, as the analysis of the first rule sets out.

The probe is one run of each harness. Each run makes a few model calls, at least one for the tool call and one for the reply, so it's the owner's to run, in a shell where the key is already exported and `claude --version` prints 2.1.281. `claude -p` stands in for the Agent SDK, which starts the same CLI with the application's environment (subprocess_cli.py@v0.2.159:810-866), and whether the SDK's entrypoint changes what the CLI passes on is unknown. The probe writes the names of its environment to a file, and the last two lines print names and counts only, never a value:

```sh
d="$(mktemp -d)"
cat > "$d/probe.sh" <<'EOF'
#!/bin/sh
awk 'BEGIN { for (k in ENVIRON) print k }' | sort > "$(dirname "$0")/names-$1.txt"
EOF
chmod +x "$d/probe.sh"
printf '{"mcpServers":{"probe":{"command":"%s","args":["mcp"]}}}\n' "$d/probe.sh" > "$d/claude-mcp.json"
printf '{"mcpServers":{"probe":{"type":"local","command":"%s","args":["copilot-mcp"],"tools":["*"]}}}\n' "$d/probe.sh" > "$d/copilot-mcp.json"
cd "$d"
PROBE_PLAIN=1 PROBE_TOKEN=1 claude -p "Run $d/probe.sh bash with the Bash tool, then reply done." --mcp-config "$d/claude-mcp.json" --allowedTools Bash
PROBE_PLAIN=1 PROBE_TOKEN=1 copilot -p "Run $d/probe.sh copilot-shell with the shell tool, then reply done." --additional-mcp-config "@$d/copilot-mcp.json" --allow-all-tools
grep -H -x -E 'ANTHROPIC_API_KEY|ANTHROPIC_AUTH_TOKEN|CLAUDE_CODE_OAUTH_TOKEN|GITHUB_TOKEN|GH_TOKEN|COPILOT_GITHUB_TOKEN|PROBE_PLAIN|PROBE_TOKEN' names-*.txt
wc -l names-*.txt
```

`ANTHROPIC_API_KEY` in `names-bash.txt` confirms that the primary passes the provider's key to commands at the pin. `CLAUDE_CODE_OAUTH_TOKEN` there, from a shell that has it set, means it passes its own token too. `PROBE_PLAIN` in `names-mcp.txt` confirms that its servers inherit, and a count near six means an allowlist applies, which takes away both the majority and the tie-break for servers. `PROBE_PLAIN` in `names-copilot-mcp.txt` means Copilot's servers inherit, and a handful of names means its documents are right. `PROBE_TOKEN` missing where `PROBE_PLAIN` is present means a name filter. A missing file means that child never started. Repeating the Claude Code line in a new directory with `CLAUDE_CODE_PROVIDER_MANAGED_BY_HOST=1` in front shows whether the host flag changes what commands and servers get.
